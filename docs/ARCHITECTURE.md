# Hive Architecture

This document explains how Hive is put together, for anyone changing the code. Product decisions live in [SPEC.md](SPEC.md).

## Processes

```
┌──────────────────────────── Electron main process ───────────────────────────┐
│ index.ts        app lifecycle, window, quit flow, settings side-effects      │
│ workspace.ts    open workspace, .hive folders, project list, git exclude     │
│ sessions.ts     launch/stop sessions, status from hooks, backups, usage      │
│ providers/      ProviderAdapter registry; claude/, codex/, copilot/ adapters │
│ providerService.ts  each provider's install info, setup tasks                │
│ ptyHost.ts      node-pty processes, output buffers                           │
│ agentProcesses.ts  each launch's process tree (a job object), leftovers      │
│ processSupervisor.ts  the job host (C#) agents and the merge queue share     │
│ launchGate.ts   holds a terminal's command until its job is made             │
│ servers.ts      hook server (random port) + Agent API (configured port)      │
│ skills.ts mcp.ts notes.ts git.ts files.ts   feature services                 │
│ ipc.ts          typed IPC handlers        tray.ts   system tray              │
│ updater.ts      Hive's own updates (electron-updater, GitHub Releases)       │
└──────────────┬───────────────────────────────────────────────▲──────────────┘
               │ IPC (preload bridge: window.hive)              │ HTTP hooks
┌──────────────▼───────────────┐                  ┌────────────┴─────────────┐
│ Renderer (React + zustand)   │                  │ claude/codex/copilot CLIs│
│ xterm.js terminals, Monaco   │◄── pty output ───│ one per running session  │
└──────────────────────────────┘                  │  └─ hive MCP server ─────┼──► Agent API
                                                  └──────────────────────────┘
```

- The **renderer** never touches the filesystem or processes. Every request goes through `window.hive.invoke(channel, …)`; channels and their types are declared once in `src/shared/api.ts` (`HiveRequests`) and implemented in `src/main/ipc.ts`, so both sides are type-checked against the same contract.
- **Events** flow the other way through `emit()` in `src/main/events.ts` (`HiveEvent` in `src/shared/types.ts`). The Agent API's SSE stream subscribes to the same events: `apiEventFor()` in `main/apiEvents.ts` decides which it sends and to whom (a project agent's token: its project's), and builds each payload from an allowlist (`publicSessionState`, `publicRun`, shared with `GET /v1/progress`), so nothing private (prompts, messages, CLI output, command lines, notice bodies) reaches any token. A notice told as a Windows notification reaches it through `tellListeners()` (marked `windows`), which no window gets. Apps that only show Hive use read-only viewer tokens (`main/viewerTokens.ts`: every request but a GET refused in `serveApi`) and find the API by the discovery file (`main/apiDiscovery.ts`, written while the API listens, cleared on quit).
- **Several windows** (`windows.ts`): each `BrowserWindow` has its own `WorkspaceService` (`createWorkspaceService()` in `workspace.ts`). The `workspace` everyone imports is a stand-in: a method given a project or worktree path goes to the workspace owning it (`workspaceFor()`), anything else to the workspace of the current work, set with `inWorkspace()` (AsyncLocalStorage) by `registerIpc` (the calling window's), the Agent API (the request's: `X-Hive-Workspace`, `?workspace=`, or the only one open) and `sessions.effective()`; without one, the last focused window's (logged once, as it means a call site forgot to say). Background work that knows its project uses `workspaceOf(projectPath)`. `emit()` asks the router in `windows.ts` where an event goes: a project's to the window showing it, a workspace's to its window (or the calling one), app-wide ones to all; `emitTo(win, …)` targets one. Terminal output goes by the pty key (`session:<project>#<agent>` to its window, task terminals to all). Quitting and closing a window (`index.ts`) ask in the window concerned (`HiveWindow.question`); each window reports its own unsaved files.
- **File system access** in main goes through Electron's `original-fs` (`original-fs/promises`), never `fs`: Electron's `fs` opens an `.asar` it stats or reads as an archive and keeps it open until Hive quits, so a project's build output (`dist/win-unpacked/resources/app.asar`) couldn't be replaced (#246). oxlint's `no-restricted-imports` holds `src/main` to it, except `hive-mcp.js` and `hive-progress.js` (plain Node); unit tests alias it to `fs` (`vitest.config.ts`), so `vi.mock('fs')` still reaches main's modules. Dependencies use Electron's `fs`, so chokidar (which stats everything it lists) watches only `.hive`; the workspace root has a plain `fs.watch` whose `rename` events refresh the project list. Electron's own readers that take a path are asar-aware too (`nativeImage.createFromPath`, `net.fetch` of a `file:` URL), so `hive-img:` streams the file through `original-fs` (#261), `attachments:copyImage` decodes the bytes it read (`createFromBuffer`), and a path inside an `.asar` archive is refused by `guardFile` (every file IPC route) and `hive-img:` (`insideArchive()` in `fsutil.ts`: a folder of the path named `*.asar` that `original-fs` finds is a file; a real folder named `art.asar` is just a folder, #261). `tests/e2e/asarfiles.cjs` checks a project's `.asar` files can be deleted while Hive runs.
- **Files tab** operations live in `files.ts`; every path is resolved against the project and refused if it escapes it. Deletes go to the Recycle Bin through `trash()` (`main/trash.ts`, Hive's one caller of `shell.trashItem`; a test copy moves the item into its own trash folder instead, #414). While a Files or Images tab is open, a reference-counted recursive `fs.watch` sends `files-changed` events with the changed folders (not forwarded to the Agent API).
- **Unsaved edits** (drafts) live in a module-level map in `FileView.tsx`, keyed by absolute path, with the root and relative path for saving. The Files tab calls `moveDrafts()` after renames and moves and `discardDrafts()` after deletes; `saveAllDrafts()` saves them all, refusing conflicts. Every change of the set is reported to main (`files:setUnsaved`), which makes `requestQuit()` ask and sends the list with `quit-request`; the quit dialog saves or discards before answering. `actions.saveUnsavedFirst()` guards Reload Window and workspace switches. The other editors (`DocEditor` for notes, skills, instruction and memory files; the MCP view) keep theirs in `editorDrafts.ts`, each with its own save function; `unsavedFiles()`, `saveAllDrafts()` and `discardDrafts()` include them. Their saves pass the text as loaded (`file:write`/`mcp:save` `expected`), and main's `writeTextUnlessChanged()` answers CONFLICT if the file has changed since.
- **Writes that repeat**: plan usage from the status line is kept in memory and saved only when a shown value changes, at most once a minute (`planUsage.ts`); transcript backups run at most once a minute during a turn, plus at `Stop` and exit (`BACKUP_INTERVAL_MS` in `sessions.ts`), and append only what the transcript gained (`syncCopy` in `fsutil.ts`); once the session ends or is archived its backups are gzipped (`compressBackups` in `sessions.ts`, #1110), and everything reading a backup goes through `transcriptFiles.ts` (whole lines from an offset, a range, the first line, plain or `.gz`).
- **File editor**: `components/FileView.tsx` holds the previewer registry (`PREVIEWERS`: match by file name, whether it needs the text, whether it is editable, default view). `files:read`/`files:write` in `files.ts` do the I/O; writes pass the modified time they started from and fail with `CONFLICT` if the file changed. `CodeEditor` ignores values it emitted itself, so React lagging behind fast typing can't overwrite newer keystrokes.
- **Images** are shown through the privileged `hive-img:` protocol (`hive-img://img/<encoded path>`), which only serves image and PDF files inside the workspace; the CSP allows it in `img-src` and `frame-src`. `webPreferences.plugins` is on for Chromium's PDF viewer.
- **Attachments** (#387): a paste or drop on a session's terminal goes through `renderer/attach.ts` (asks about large files, keeps the chips `AttachmentChips` shows) to `sessions.planAttach()`/`attach()`, which copy what comes from outside the session's folder, and images, into the host's `.hive/attachments/<session>` and return the paths to paste. Every use of that folder goes through `attachmentsDir()` (`attachmentsFolder.ts`), which first moves the host's old `.hive/images` into it, once a run. The kinds and how a CLI's chip labels them are in `shared/attachments.ts`; the kinds each CLI reads itself are its descriptor's `capabilities.attachments`. The Attachments tab lists, reads and deletes through `files.ts`.
- **Hive's own files**: `writeJsonAtomic`/`writeTextAtomic` (`fsutil.ts`) write a uniquely named temp file and rename it (retrying briefly while Windows holds the target); a write that fails removes its temp file. What a crash leaves (temp files over a day old) and the project-id migration's `*.before-ids.bak` copies (over a week old) are removed from the workspace's and projects' `.hive` folders as the workspace opens (`leftovers.ts`, #1016), logged in one line. Only the stores it names are looked at, each only where it is a real folder inside its `.hive` (never through a link or junction, nor a linked file), and in each only temp files of that store's own files (`tasks/<n>.json`, `metrics/metrics.json`, a project's `sessions.json`…) and backups of the records the migration changed: the same suffix in the user's notes, attachments or a folder Hive doesn't know is left alone. The workspace and its lifetime are taken together before the sweep awaits anything, so a switch part way stops it. Changes that read a file and write it back go through `withFileLock`: use `workspace.mutateProjectConfig()` / `updateAgent()` for `project.json` and `workspace.mutateSessions()` / `upsertSession()` for `sessions.json`, never read-then-`updateProjectConfig` with a value computed outside the lock (one provider's project settings: `project:updateProvider`, which merges under the lock). The files Hive keeps are read with `readKeptJson()` and written with `writeKeptJson()`, which also writes `<file>.bak`; an unreadable file is set aside (`<file>.corrupt-<time>`), the `.bak` restored and `onCorruptFile` (a notification, set up in `index.ts`; startup reports wait for the window) told.
- **IPC** is accepted only from a Hive window's top-level frame (`registerIpc`), provider ids are checked (`knownProvider`), and `index.ts` refuses every permission request except the clipboard's. A build's CSP drops the dev server's `ws:`/`localhost` (`hive-production-csp` in `electron.vite.config.ts`).
- **File IPC** (`file:read`, `file:write`, open/reveal): paths must be in the workspace or its worktrees (checked by their real location too: `insideReal()` in `fsutil.ts`, also used by `hive-img:` and shared notes), or be one of the provider files Hive shows (each adapter's `fileAllowed()`: Claude Code's user `CLAUDE.md` and auto memory, Codex's user `AGENTS.md`, read-only `SKILL.md`).
- **Session IDs** are validated with `assertSessionId()` (`shared/defaults.ts`) wherever they reach a path: `sessions.start/usage/archive/rename/adopt`, `backupPath`, each adapter's `transcriptPath`, the transcript viewer.
- **Pty output** goes over its own `pty:data` channel for throughput. The main process keeps the last 512 KB per pty so a reloaded window can replay it.

## Providers

A provider is a **descriptor** (`src/shared/providers.ts`, plus `shared/claude.ts`, `shared/codex.ts` and `shared/copilot.ts`; static data used by both processes: names, icon, permission modes, efforts, models, capabilities, reserved terminal keys, instructions file) and an **adapter** (`src/main/providers/<id>/adapter.ts`, `ProviderAdapter` in `providers/types.ts`). `providers/index.ts` is the registry (`allProviders()`, `providerAdapter(id)`). Shared helpers resolve settings: `providerSettings`, `projectProviderConfig`, `agentProvider` (agent → project default → global default), `agentLaunchSettings` (model, effort and an allowed mode), `isProviderEnabled`. The UI reads descriptors and never switches on a provider id; capabilities (`liveModeSwitch: 'cycle' | 'menu'`, `planModeToggle`, `reportsCost`, `promptCacheTtl`, `compactFocus`, `imagePaste`…) turn features on and off.

**Models and capabilities** (#125): each adapter's `listModels(executable, env)` asks the CLI (Claude Code: the `initialize` control request, `providers/claude/models.ts`; Codex: `codex debug models`, `providers/codex/models.ts`; Copilot: an ACP `session/new` of `copilot --acp`, only while it is enabled, `providers/copilot/models.ts`), parsed defensively into `CatalogModel`s (value, name, resolved id, effort levels, default effort, Auto). `providerService.refreshOne()` keeps the answer in `AgentInstallInfo.catalog` and caches the last good one per CLI version in config.json (`modelCatalogs`); `configuredDefaultEffort()` and `observeDefaultEffort()` (fed by `sessions.applyDetails()` for sessions launched without an effort) give each model's default effort. `shared/models.ts` is the one place that resolves them for the pickers, the footer and the Agent API: `modelGroups()` (the catalog, else the fallback: the user's `modelFallback` or the descriptor's groups), `modelCaps()` (a model's effort levels and default, and `supportsAuto` for `modeCaveat`), `fallbackEfforts()`, `effortText()`. `config.setProviderFallback()` stores only an edited list; `null` resets it.

Adding a provider: a descriptor added to `PROVIDERS`, an adapter added to the registry, an icon in `renderer/src/assets/providers/`, prices in `shared/prices.ts`, a `migrate…` step if settings change shape, and tests. Nothing else should need to change; if it does, move that knowledge into the descriptor or adapter.

- **Settings**: `AppSettings.providers[id]` (`ProviderSettings`) and `defaultProvider`; `ProjectConfig.providers[id]` and `defaultProvider`. `migrateConfig()`/`migrateProjectConfig()` in `shared/defaults.ts` read 0.1 files; `withLegacySettings()`/`withLegacyProjectFields()` keep writing the 0.1 fields, and `config.ts` backs the 0.1 file up once.
- **Runs**: each launch gets a `runId` (`LiveSessionState.runId`, `sessions.runs`). Hook and status-line URLs carry `?run=<runId>`, so `findLaunch()` finds the agent even before a provider reports its session id (Codex does so with the first prompt; `recordSession()` then writes the record, including `transcriptPath`).
- **Hooks**: `adapter.normalizeHook()` turns each CLI's JSON into a `NormalizedHook` (session id, transcript path, mode, and an event of kind start / prompt / toolStart / toolEnd / needsInput / stop / signIn / interrupt / compactStart / compactEnd / end; signIn is a turn its CLI refused for the sign-in, which Codex says only in its rollout, `LiveDetails.signIn`); `handleHook()` only sees those, and asks `hookStep()` (`main/hookStatus.ts`, pure and unit-tested per provider) what each one does to the status and which actions to take (notify, release locks, record the turn, compaction). Before that, each hook goes through its launch's **turn ledger** (`main/turnLedger.ts`, pure, #648): the hook's own ids (`NormalizedHook.ids`: the CLI's turn, call and sub-agent) say which turn it is about, so news of a turn that is over is dropped (`stale`), a Stop Hive answered with a continuation (`hookReply()` → `stopReplier`; `adapter.stopContinues()`) isn't an end, and only a start opens or reopens a turn: a prompt, a tool call the latest turn never started after its Stop (from the ids alone, never the screen), or Hive's own continuation; any hook naming a turn that is neither the open nor the latest one, or one Hive doesn't remember, is stale, launch-wide kinds too (but for a compaction the CLI began under its own id, `TurnLedger.compaction`, and a background wake's first tool call when its prompt hook is lost, only while `LiveSession.woke` says the transcript saw the task end); and a turn begins at its first hook's arrival (`handleHook` passes it through the queue). When a turn goes quiet, `checkSilence()` (each 5-second transcript look) ends it from the CLI's own record (`LiveDetails.turnEnded`: Codex's `task_complete` by turn id; `LiveDetails.stopsAnswered`: when Copilot's Stops were answered, against the Stops of the turn Hive got, `unheardStop()`), open tool calls or not, or its idle prompt on screen (`adapter.turnScreen(version)`: idle, working or not sure, read from the launch's `TerminalScreen`; a turn visibly at work counts as heard), and otherwise marks it unknown (`LiveSessionState.turn`), which only the CLI being heard or the user's **Mark idle** (`markIdle()`) ends. The runtime's facts (`LiveSessionState.runtime`: lifecycle, maintenance, attention, composer) are set where Hive learns them (`fact()`, `factsOf()` in `carryOut`, Hive's Compact, `noteComposer()` around `sendPrompt` and `holdForConfirm`); `shared/runtime.ts` gathers them (`agentRuntime()`) and projects the labels (`runtimeLabel()`). Each hook is journaled in `logs/hooks.log` (`hookJournal()` in `logger.ts`). A compaction Hive asked for is a `Compaction` (`main/compaction.ts`), reserved while its `/compact` is typed: its time limits (from the submission) and the transcript and terminal signs that end it when no `PostCompact` comes; however it ends, `compactionOver()` decides the status. An exit before the session started is a failed start or a plain stop by `failedStart()` (`shared/startFailure.ts`). `adapter.lockReply()` shapes the file-lock answer.
- **Hooks health** (`main/hooksHealth.ts`, #1336, #1371): whether a launch's hooks arrive, from three signs, never time alone: none after a Claude Code start; none after an idle prompt its screen shows worked on; none naming a turn its transcript shows the model took. Each adapter's `transcriptTurns` reads its CLI's own turn identity (`providers/{claude,codex,copilot}/turns.ts`: Claude Code's `promptId` and `parentUuid` chain, Codex's `turn_id`, Copilot's `interactionId`, `turnsJoin` 'id' or 'time'); `main/turnsReader.ts` gives it each look's whole new lines, one reading per conversation and file (fresh from the start, else from the end; restarted on another file, a shrink or other first bytes); `hookTurn` marks the ids hooks name in the launch's hook order, and the check (`checkHooks`, synchronous, in that order) only reads what the readings stored.
- **Live details**: Claude Code posts its status line (`handleStatusLine`: model, effort, cost, context window — `usage()` adds the window to a running Claude session's usage); Codex's model, effort, context window, plan limits, preset and Plan mode come from the rollout tail (`readDetails()` → `adapter.transcriptDetails()`, from `detailsOffset`). Both end in `applyDetails()` and `reportPlanUsage(provider, usage)`.
- **Background tasks**: `readBackground()` reads what the transcript gained (from `tasksOffset`) through `adapter.backgroundTasks()` (`providers/claude/background.ts`, `providers/codex/background.ts`) into the launch's `tasks` map, ignoring lines from before the launch. `settleBackground()` drops expired tasks and those past `agents.backgroundTaskMinutes`, sets `backgroundTasks` in the live state and, for providers with `capabilities.backgroundWakes`, moves the agent between `background`, `working` (a task ended, so the CLI starts a turn) and `finished`. A Stop reads the transcript first (`refreshBackground()`) and leaves `background` instead of `finished` while tasks are open (`idleStatus()`), without the finished notification.
- **Mode switching**: `liveModeSwitch: 'cycle'` sends Shift+Tab until the footer (`adapter.footerMode`) shows the target (Claude Code); `'menu'` types the adapter's `modeMenuKeys()` (Codex: Ctrl+U, `/permissions`, arrows, Enter). `setPlanMode()` sends `planToggleKey`.
- **Readiness and setup**: `adapter.readiness()` returns `ReadinessIssue`s (not installed, signed out, sandbox) with a task; `providerService.runProviderTask()` runs install/login/update/setup in a visible terminal, typing `CommandSpec.keys` once `readyPattern` shows (Codex's sandbox setup, through `/permissions`). `KeyGate` (`taskKeys.ts`) decides when: it matches `readyPattern` against the screen the output draws (a `TerminalScreen`, so a word changed in place or output split anywhere is read right) and follows `busyTitle` in the window title and `busyScreen` on the screen (#363); the keys wait until it has been ready and not busy for a second, and each key until it has been idle for half a second. A step with `heldOn` (the Enter after a command) goes in again, at most twice more (`keySteps.ts`), while the screen still shows the command held once the CLI is ready again; `ready` is asked before every write, with nothing awaited between its answer and the write, and answers true or why not, which stops the typing (`KeysStopped`, fail closed): a task's when the CLI stays busy for 30 seconds or closes; a live menu switch's (`sessions.setPermissionMode`) also when the session ended or was replaced, or asks the user something, and the switch then reports it wasn't made.
- **Cost**: `shared/prices.ts` (`SHIPPED_PRICES`, `modelPrice()`, `estimateCost()`) prices sessions without a reported cost; user prices (`ProviderSettings.prices`) win, and shipped ones the user removed (`pricesRemoved`) aren't used. `usageFor()` fills `costUsd`/`costEstimated`, and price changes clear the usage cache.

### Codex

## Launching a session

`sessions.start()` (Claude Code shown; Codex differs as above):

1. Resolves effective settings (`effective()`, run in the project's workspace): every Hive skill in the workspace, the workspace-enabled MCP servers minus the project's opt-outs, narrowed to the agent's own choice when it has one (`agentGetsMcp` in `shared/agentMcp.ts`, #537: every adapter then passes only those, and turns off the user's same-named servers like any other), plus model, effort, permission mode and args. Bypass is downgraded unless the global opt-in is on.
2. Restores the transcript from `.hive/sessions` if resuming and Claude Code no longer has it (a compressed backup, `<id>.jsonl.gz`, decompressed: `transcriptFiles.ts`, #1110).
3. `adapter.prepareLaunch()` — for Claude Code, rebuilds `Project/.hive/launch/` from scratch:
   - `plugin/` — a session-only Claude Code plugin containing copies of the Hive skills (`--plugin-dir`)
   - `mcp.json` — enabled servers plus the built-in `hive` server (`--mcp-config … --strict-mcp-config`)
   - `settings.json` — HTTP hooks pointing at Hive's hook server (`--settings`); `SessionStart`, which can't be an HTTP hook, is a `curl.exe` command posting to the same server
4. Spawns `claude` in a pty with `--session-id` (new) or `--resume` (existing), so Hive always knows the session ID and therefore the transcript path.
5. Records a **launch signature** (hash of the effective settings). `liveInfo()` compares it with the current settings to show "restart to apply".

## Usage

Each adapter's `parseUsage()` reads its transcripts into `SessionUsage` (Codex: `codex/rollout.ts`). `providers/claude/usage.ts` parses Claude Code's JSONL transcripts (`~/.claude/projects/<encoded path>/<session>.jsonl`):

- usage is summed once per API request (Claude Code writes one entry per content block with repeated usage);
- context size is the last request's `input + cache_read + cache_creation`, or `postTokens` after a compaction;
- compactions come from `system/compact_boundary` entries;
- the cache TTL is detected from `ephemeral_1h_input_tokens`.

Those reads (`sessions.usageFor`: a running session's footer, context gauge, compaction count and cost, its row in the Sessions list and the project Overview (#1157), and a session the usage history doesn't have yet) are the usage worker's (#1147: `usageHistory.read()`, the worker's `readUsage`), never main's: it keeps each transcript's parser by path (at most 200, results for `sessions.usageCacheSize`, least recently used first, for this run only), reads 4 MB at a time from where its last read stopped, and one it hasn't read in this run takes its session's saved parser state up from the history (a resume after a restart reads only what was added); its ingest jobs go on from the same parser, and reads of one file take turns with them. It answers at once, not after queued jobs, with the result before costs and without its timeline; main keeps the latest per path (`usageSeen`, by size and modified time) and prices it (`priced()`, again after a price change). Every other session's usage comes from the **usage history** (#1106): `main/usageWorker.ts`, a worker thread with its own `node:sqlite` connection to the workspace's `.hive/usage.db` (`main/usageDb.ts`: `usage_sessions`, `usage_rows`, `usage_meta`), reads only what a transcript added (the parser's state saved with `main/usageParsers.ts`: the CLIs' parsers without their adapters, reading advanced settings through `main/advancedValues.ts`, as the worker can't load Electron) and writes each session's rows (`shared/usageLedger.ts`: per day, model and card, costs priced when read); `main/usageHistory.ts` is main's side: the queue (a session about to be deleted first, then running sessions on a minute's tick and as they end, then each workspace's one-time import and the ten-minute sweeps), the queries (the worker answers them; main prices the rows), and the import's progress (`usage-history` events). In unit tests the worker's code runs in main's thread. While a session runs, a 5-second poll checks the transcript's modified time and size (Codex's appends can leave the reported modified time unchanged on Windows), copies it to `.hive/sessions` at most once a minute during a turn, and emits `usage-changed`; for providers without a reported cost, the estimate (a full parse) is worked out at most every 30 seconds and at turn ends. `sessions.list()` reads `sessions.json` and `project.json` once for the whole list (`ListContext`); the Codex adapter reuses its rollout listing for 10 seconds and remembers missing rollouts for a minute. In the renderer, `useSessions()` (Overview, Sessions tab) reloads per `settings.sessions.overviewRefresh`: live at most every 15 seconds, every minute, or on Refresh. Period totals (`periodFrom`, `sumUsage`, `dailyTotals`, and `stackedDaily` for the chart by project) are in `shared/usageTotals.ts`, shared by the project Overview, the Assistant's summary and the **Workspace Overview** (`views/WorkspaceOverview.tsx`), which loads `workspace:usage`: `sessions.usageItems()` per project and for the Assistant, from the usage history (Hive's records and the history's sessions, deleted ones included; no external sessions, no transcript read or looked up), into `workspaceUsage` in the store, with the same refresh rules while it is shown. A large transcript with no requests at all raises a one-time "may not understand this version" notice (`checkUnderstood`).


## Performance metrics

`main/metrics.ts` (contract and units in `shared/metrics.ts`; SPEC §9.1) keeps one `Store` per open workspace (a WeakMap on the `WorkspaceService`, made on first use and saved and forgotten when its `lifetime` aborts). Stores are also kept by file (`byFile`, canonical path): a workspace reopened while its last store is still saving gets that store under the new lifetime, so writes to one file stay in one order; a store is forgotten after its final save if nobody took it over. Every collection point takes a `MetricsHandle` (`metricsHandle(w)`: that store and that lifetime) before it awaits anything and records through it, so work that outlives its workspace is dropped instead of landing in the window's next one; `metricsReport` checks the lifetime after each await of its usage read and refuses a read the workspace switched under. `roll()` runs on load, on each new hour and before each query (retention however long Hive was idle; buckets more than a day ahead dropped; at most `METRICS_LIMITS.buckets`) and reports whether it changed anything, which is then saved. Projects and series live in prototype-free dictionaries (`dict()`), drops are counted by owner (`droppedBy`) so a project report has only its own, the write cap is in UTF-8 bytes, and `load()` reads through `readCappedSync` (at most the cap plus one byte). `load()` checks the file's size before reading it and rebuilds each bucket through `readBucket`/`readPart` (finite non-negative counters, histogram length, known labels, the bucket caps). A record is a few map updates into the current hour's `Bucket`: `projects[name]` and `workspace` parts (`api`, `mcp`, `guidance`, `catalog` series) and the shared `skills` series; `roll()` folds hours older than a week into days and drops days past 30; `save()` is debounced (30 s, unref'd), chained so saves never overlap, size-capped (oldest buckets first, measured as the old file's text) and saves through `storeTables.ts` (#1019, #1212): a bucket a row of `metrics_buckets` with a row per series in `metrics_series` (keyed by span and start, so a bucket leaving the front moves no other), only the buckets that changed written, with `observed`, `evictedThrough` and `renamesApplied` in `board_meta`. `load()` reads the tables (synchronously, from the reader); before the store has its `imported` mark it reads `.hive/metrics/metrics.json` as before, and the first save writes it all with the mark in one transaction, then keeps the file as `metrics.json.imported-<time>`. A save after its workspace closed opens the database for the save and closes it again. Labels come from fixed sets (`knownRoute()` registers each Agent API template in `route()`; tool names and provider ids by pattern; anything else is "(other)"); per-bucket caps on projects and series count what they drop. Recorders never throw. Where each measurement is taken:
- `servers.ts` `handleApi`: an `ApiRequest` per response (`apiRequests` WeakMap) filled in as it is handled (role and project from the caller, the handle from `requestWorkspace` before the body is read, route template, request bytes per chunk as `readBody` receives them, response bytes as `send` serializes them), recorded on the response's `close` with its outcome (`outcomeOf`: unfinished is cancelled). Unauthenticated requests, event streams (`broadcast` and the `/v1/events` handler) and requests in flight go to the process-wide `appMetrics`. `/v1/health` and `/v1/metrics/mcp` are skipped.
- `hive-mcp.ts`: each `tools/call` reply's final text (chars, UTF-8 bytes, monotonic time, outcome, mode) and the first `tools/list`, batched (at most 50 a post, every 2 s, at once when the CLI closes input and no call is running) to `POST /v1/metrics/mcp` with the session's own token; the route checks and bounds each entry (`recordMcp`, `recordCatalog`) and attributes it by the token.
- `sessions.ts` launch: `recordLaunch` with the session contract (`ctx.guidance`, counted once whichever way the provider gets it), the Assistant's instructions, the delivered skills measured on their copies (`deliveredSkillSizes`: each adapter's `skillCopyPath`, the copy's header through `headerOf` and its `treeSignature` byte total) and the skills asked for that weren't delivered.
- `revisions.ts` / `guidance.ts`: hits, misses, invalidations, too-big outcomes and what each hash read (`HashOptions.count`, scoped instead of the global `readStats`), header bytes (`headerOf`), and each `skillRevisions` scan's time and shared callers (`coalesced(scan, onShare)`).
- `cardCosts.ts` (#602): cost per card and per lane, read on request (IPC `costs:cards`, `costs:lanes`). Each card's holds (`TaskCard.held`, kept by `trackHolds` in `tasks.ts`'s `saveCard`, or from its history) against its agents' sessions' timelines (the parser's `timeline`, rows of a second with the charges covering them): worked out as each session is recorded in the usage history (#1106), so a card's cost is its rows there (`rowsPart`), and a lane's is sliced from the timelines kept there; the slicing and the charge sharing are pure, in `shared/cardCosts.ts` (`sliceSession`, `chargeShares` in `shared/usageTimeline.ts`) and `shared/usageLedger.ts` (`ledgerRows`, `sessionHolds`). Cost per round and role (#1226, #820 item 2; data only, no view yet): `cardRoundCosts` (IPC `costs:rounds`) takes a card's rounds from its facts (`roundSpans`: rounds follow submissions, a verdict counting for the round of the submission it names, never by its own `round`, which counts failures; round 1 begins at its cycle's `Started` or `Adopted`, round k+1 at the first failed verdict on round k or else its first submission; a pass ends nothing by itself, since a second reviewer may still review or a later verdict fail it; the card is worked while its stage is Active or Review, by its `Moved` facts, so a round is the spans it was worked in, a pass made stale and sent back counting on) and in each, per agent and role, what that agent's sessions used while it held the card then (its holds within the round's spans), shared 1/k with its project's live cards it held at the same time (`sharedSpans`, `scalePart`; another project's agent is another agent, whatever its name); a split by time from the timelines, so a round's parts are Hive's (≈) and the card's total stays the ledger's. It reads the card asked for and the live cards' holds (`cardHolds(ws, { live: true })`); a card from before 1.0 has no rounds (`preWorkflow`).
- `metricsUsage.ts`: `metricsReport()` adds the providers' own reported usage (`sessions.usageItems`, sessions active in the range: tokens, requests, compactions, cost) to `queryMetrics()`, for `GET /v1/metrics` and IPC `metrics:query`; `metricsExport()` wraps a report for IPC `metrics:export` (schema, version, units, optional sanitizing).
- The Performance view and tab (`views/Performance.tsx`) share one `PerformancePage`: the scope is in every query (a project's tab asks for its project only), `useScopedLoad` keys results by workspace, scope and range, refreshes are coalesced, and filtering and totals are the pure `shared/metricsView.ts` (`select`, `totals`, `byRoute`, `byTool`). The page's filters go to main with the query (`queryFor()`); `queryMetrics` narrows each bucket's parts with `filtered()` before summing them and before `trendOf()` (so the parts, trend and an export agree), reports `filters.notFiltered`, and reads coverage from the store's `observed` stretches (`touch()` on each record and query and on an unref'd 5-minute tick over the stores some workspace holds (`holders`); `seal()` ends a stretch when recording is turned off (`config.onSettingsChanged`, or a touch that finds it off) or the last holder closes, and a loaded store starts sealed; `evicted()` moves `evictedThrough` and trims observation when `roll()`'s bucket cap or `write()`'s byte cap removes a bucket; saved with the buckets, expired by `roll()`, cleared by `reset()`). `providerUsage()` reads the hosts the scope and filters keep (projects as `agent`, the Assistant's home as `assistant`), counts running sessions from `sessions.projectStates()`, takes context as a snapshot, and counts hosts whose `usageItems()` failed (`providersUnreadable`). `launchParts()` in `guidance.ts` splits a launch's text into core, custom, role and mode for `recordLaunch`.

Compare (#117): `shared/benchmark.ts` reads artifacts as untrusted input (`parseArtifact`: scenario benchmarks, Performance exports reduced to `summaryOf()` totals, a workspace export's project part only when asked), and compares them (`compareArtifacts`: comparability with reasons, per-scenario `Stat`s and statuses, correctness before size). `main/benchmarks.ts` keeps them in `.hive/metrics/benchmarks` (`index.json` plus one file each) behind the `benchmarks:*` IPC. Each handler takes a `BenchContext` (the folder, the workspace's lifetime and path) synchronously before any await, and every step checks it (`live()`): work whose workspace closed or switched is refused. Changes are serialised per folder (a settled chain is forgotten). Every write goes through `commit()`: staged beside the file, the context checked, then renamed. Index entries carry `state` (`adding`, `removing`) and `txn` for changes in progress: `keep()` records the add and the evictions, writes the file, commits the add, then removes evicted files (`removeFile`, ENOENT counting as gone) and drops each entry only once its file is gone; `removeBenchmark()` does the same for one entry. `readIndex()` validates the whole index (damage goes to `recover()`, never acted on), then `reconcile()` rolls back unfinished adds, retries recorded removals, moves files the index doesn't account for to `quarantine/` (`quarantine()`: named `<time>-<seq>-<id>.json`, pruned by time to the newest 100) and drops entries whose file is gone. `recover()` sets the damaged index aside (bounded), adopts every valid file with its old pin and time, and quarantines invalid and overflow files so its result is stable. `writeIndex()` refuses an index the reader wouldn't accept (`acceptable()`: at most `MAX_ENTRIES` in all, 20 kept, ids unique), and `keep()` checks that bound before recording a change. Every rename (commit, quarantine, set-aside) goes through `guardedRename()`: fsutil's `renameRetrying()` with a guard run before each attempt (`live()`) and `benchIo.renameOnce` as the single rename, so tests drive the real retry loop. Notices from recovery and clean-up are returned once by `benchmarks:list`. Reads are capped (`readCapped`); writes and removals go through `benchIo` (tests inject failures and pauses there). A file waiting for the project-part answer is held by a token bound to its context and scope, never a renderer-supplied path. Every call carries the page's `CompareScope` (the whole workspace, its own work, a project) and reads only that scope's; `shared/benchmark.ts` `readKept`/`readEntry` re-read kept files through the same normalisers as imports. `views/PerformanceCompare.tsx` loads the list and each pair with `useScopedLoad` keyed by workspace, scope and pair. The scenario harness (`tests/scenarios/harness.cjs`) reads `/v1/metrics` before the launch and after the turn and writes `measuresOf()` the difference; `benchmark.cjs` writes the artifact, prunes results and rotates baselines; the fakes' scenario steps call the real hive MCP server through `tests/e2e/fake-bridge.cjs`.

Measured (`tests/metrics.test.ts`, `MEASURE=1`; e2e replysize): recording costs about 0.3 µs a request; an hour's bucket filled to its 2000-series cap with Hive's real tool names is about 430 KB on disk and as JSON in memory (so under extreme cardinality the 2 MB file keeps a few such hours; ordinary use is far smaller); 300 sequential API requests took 14.45 ms each recording and 14.73 ms not (noise); idle, an open workspace's store only notes every 5 minutes that it is still observed (no write of its own). Budgets: under 50 µs a record (tested), the file at most 2 MB, a bucket at most 2000 series and 100 projects.

## Developer console

`src/main/devConsole.ts` keeps a ring of events per source (`shared/devConsole.ts`: the ring, redaction, source ids and who may read what), only while a source has a subscriber: capture points call `devConsole.capture([sources], build)`, which returns before building anything when none of the sources is watched. The capture points: `sessions.ts` (hooks after `carryOut`, status lines, transcript reads in `readDetails`, the terminal title, startup and footer markers, `sendPrompt`, launch and exit), `servers.ts` (refused hooks; every Agent API call as it closes, except the console's own routes and the bridge's metrics reports), `mergeSlotHost.ts` (claims, releases, slot changes), `watches.ts` (a wake typed) and `devConsoleSources.ts` (Progress runs, from the event bus). Summaries come from `devConsoleWords.ts`. The window subscribes over IPC (`console:subscribe`, tied to its webContents and ended when it closes, through `senderStore` in `ipc.ts`); the Agent API's `/v1/console/…` routes only read what an open console captures (they subscribe nothing), and `mayRead` decides what each caller sees. `hive_console` in `hive-mcp.ts` is offered only when `HIVE_DEV_CONSOLE=1` (Settings → Agent API → Let agents read the developer console).

The console window (#637) is `consoleWindow.ts`: one `BrowserWindow` per Hive window, loading the same renderer page with `#console`, which `main.tsx` renders as `ConsoleApp.tsx` instead of the app (its view logic, the list's merging, filters and source groups, is `shared/consoleView.ts`). A console is bound to the workspace its owner showed when it opened, and closes on a `workspace-changed` that leaves it; `ipc.ts` likewise ends any window's subscription when its window leaves the workspace it subscribed in, and checks `mayRead` against the current workspace on snapshots. `ipc.ts` lets a console window's page call only `CONSOLE_WINDOW_CHANNELS`, in its owner's workspace (`consoleOwner`); `console:open` is refused unless `advanced.showDeveloperFeatures` is on, and turning it off closes the consoles. The Help command is `hidden` (a `Command` field: left out of the menus, the palette and Tips, and refused by `runCommand`) while the setting is off.

Advanced settings (#367) are `shared/advanced.ts` (the defaults, `ADVANCED_DEFS`, each with what it takes and, for a CLI-facing one, the samples it was recorded reading; checking a value, trying it on the samples, the row Settings lists) and `main/advanced.ts` (the `advanced` store: advanced.json in the profile folder, followed with a watch on that folder, the CLI version each CLI-facing override was made for, from `provider-install` events in `index.ts`). Code reads a value with `advanced.get()`, `number()` or `pattern()`; an override that doesn't check out falls back to the default, warned once. Adapters read theirs where they use them (getters for `startupQuestion` and `readyOutput`), so a change applies at once, or at the next launch for what a launch writes (hooks, title items, Codex's tool timeout). The hive MCP server gets its reply timeout and wait caps in its environment (`mcpAdvancedEnv`), and `servers.ts` holds waits to the same caps (`waitMaxSeconds`). A workspace's own values are in `workspace.json` (`advanced`, `workspace.setAdvanced`). The settings catalog lists each as `advanced.<id>` (hidden rows, drawn by `AdvancedSettings.tsx`), so the Assistant's settings tools read and change them like any other.

Recording (#638) is `consoleRecorder.ts`: a subscription of its own per window (`record:<webContents id>`, with `includeText` when the user ticked it) whose deliveries are appended to a JSON Lines file in `console-recordings`, ended by `stopRecording` (the user, another source, the page destroyed, `ipc.ts` when its window leaves the workspace or stops watching the source, or its bound). Each window has a slot: its starts and stops run one at a time, a generation number cancels a start overtaken on its way (rechecked with the caller's `stillWanted` after each await), the file is reserved with an exclusive open, and a stop detaches the subscription at once with `devConsole.unsubscribe(id, { drain: true })` (its queued events written first) before the end line. The file format, turning a recording into a fixture, the contract comparison and what Copy Diagnostics attaches (`diagnostics.ts`) are in `shared/consoleFixtures.mts`, plain TypeScript with no imports so Node runs it as it is (`scripts/consoleFixture.mjs`, the `contract-*` suites).

## Transcript viewer

The Sessions tab reads the conversation itself through `transcripts.ts` (IPC `transcript:*`), with the parser of the session's provider (`adapter.conversationParser()`). `providers/claude/conversation.ts` has Claude Code's `ConversationParser`, which turns JSONL entries into display items: user messages, replies, thinking, tool calls (matched to their `tool_result` by id), slash and `!` commands with output, notices, and compactions (the `isCompactSummary` message becomes the divider's summary; the next request's usage gives its real size). Sidechain entries, meta messages and attachments are skipped.

Transcripts are append-only, so the parser is incremental: `feed()` takes the bytes after its offset and stops at the last newline, leaving a line Claude Code is still writing for next time. `transcripts.ts` keeps a parser per session (LRU of six), reads only the new bytes when the file grows, and starts again if the file is replaced (for example by Hive's backup). `transcript:read(project, id, { knownSize, from })` returns the items from `from` on (by default the latest `TRANSCRIPT_WINDOW`, 200) with the total, or null when the size hasn't changed; the viewer loads earlier windows as you scroll up (keeping its distance from the bottom), and polls every 2 seconds for a running session only with Follow on (`settings.sessions.followTranscripts`). Tool input and output are shortened to 4,000 characters for display; `transcript:tool` returns the full call. Images are not sent with the items: the parser records each image's line range, and `transcript:image` reads that line and returns a data URL. Search (`searchItems`) and Markdown export (`transcriptMarkdown`), in `providers/conversation.ts`, work on the full items in main for every provider.

The tab's list is a tree (`shared/sessionTree.ts`: provider → agent → session → sub-sessions, from `session:list`). Sub-sessions (Codex guardian reviews and other sessions a CLI starts for another) are found by each adapter's `listSessions()` from the transcript's first line, cached by mtime (`rolloutSubSession()`, `transcriptSubSession()`), as `SessionListItem.sub`. Why a session can't be resumed is `shared/sessionResume.ts`. Archive and delete, one at a time or a branch at once (`session:bulk`), reserve the session (no start, resume or transcript read meanwhile), go through `sessions.inUse()` (running anywhere, a read in progress or a view open in another window: `transcriptReads.ts`; the CLI's transcript held open by another program, checked read-only; or written in the last few seconds by a CLI Hive didn't see exit) and change each session all or nothing: an archive is built aside and its moves undone on any failure (`Moves`); a delete keeps a spare (hard link) of each copy it sends to the Recycle Bin and puts them back if a later step fails.

## Agents in a project

A project has up to four agents, all equal (`ProjectConfig.agents` as added; `projectAgents()` in `shared/defaults.ts`), and a new one has none. Ids are random (`a-<hex>`, `projectAgents.addAgent`) so session records of a removed agent never attach to a new one, and the provider is stored at once. `migrateProjectConfig()` clears 0.1's agents and layout (project.json version 2). Calls that name no agent use the project's only one (`sessions.soleAgent()`; the Agent API answers 400/409 otherwise), and the renderer's `focusedAgentId()` is null without agents: `actions.quickAddAgent()` adds one (the default provider, if on and installed; else the Add Agent dialog), which New Session and Resume use. Adding sets `sessionLayout` from the count (`layoutForAgents`). `SessionManager` keys live sessions by project + agent id; terminals are `session:<project>#<id>` (`agentPtyKey`). Hooks and the status line carry the launch's `runId` (and `session_id`), so they find their agent without any other routing; a prompt hook with another session id for the same run moves the agent to that conversation (`switchSession`). `resumeRecord()` offers an agent its own sessions, then sessions no current agent owns. `ProjectInfo.agents` carries each agent's definition and live state; `ProjectInfo.live` is the first running agent's session. The renderer keeps the focused agent and pane assignment per project in the store (`focusedAgent`, `paneAgents`, `paneAssignment`, `showAgent`) and derives the single project dot with `mostUrgent`.

- **Launch**: each Claude Code agent has its own launch folder (`launch-<id>/`) because `prepareLaunch` replaces the folder. The pty's cwd is the agent's worktree when it has one. A worktree's setup command runs first in the same pty key (`quietExit`, so the renderer doesn't see an exit), then Claude Code continues in that terminal with the setup output carried over (`continueBuffer`).
- **Transcripts**: Claude Code files transcripts by folder, so a worktree agent's live in another `~/.claude/projects` folder. Session records keep `agentId`, `cwd` and `branch` (and, for Codex, `transcriptPath`), and `sessions.providerTranscript()` looks in the record's folder, the project folder and every agent's worktree. Backups and images stay in the project's `.hive`.
- **File locks**: `sessions.preToolUse()` answers the `PreToolUse` hook (Claude Code: matcher `Edit|Write|MultiEdit|NotebookEdit`; Codex: `apply_patch`, every path in the patch; Copilot: `Edit` and `Write`'s `path`) synchronously in the hook server. Locks are a map from absolute path to the holding session, released on `Stop`, `SessionEnd`, exit or after 15 minutes; held files are published as `LiveSessionState.lockedFiles`.
- **Worktrees**: `main/worktrees.ts` wraps git (`worktree add/list/remove`, branch status, `merge-tree` conflict check, squash or `--no-ff` merge with `reset --merge` on failure, copying ignored files by pattern). `main/projectAgents.ts` adds, updates, removes and merges agents. `main/branchWatch.ts` keeps each worktree agent's unmerged work (commits ahead, uncommitted files) up to date from session-status, window-focus and workspace events and sends changes as `branch-status` events; the renderer keeps them in `branchStatus` (by `projectKey`) for Merge… and the agent tab. `workspace.assertRoot()` accepts a project or a registered agent worktree, so the Files and Changes IPC can work in worktrees; `git:status`/`git:diff` take a base branch and compare with the merge base.
- **Lanes** (#483): `shared/lanes.ts` is the logic (a kept lane, `LaneRecord`; how it reads against the board, `laneView`: its cards, the current one, paused while that is blocked; which are listed and kept; the tool's lines), `main/lanes.ts` the service over the workspace's lanes (its database's `lanes`, `lane_cards` and `lane_frozen` through `storeTables.ts`, #1018, #1212; read and written whole under the lanes' lock): `startLane` (one running lane per builder: a start sharing a card updates it, one sharing none ends it), `joinLane` (the reviewer: with cards, a running lane sharing one; else it starts the lane as its builder would), `endLane`, `laneAgentRemoved` (from `projectAgents.removeAgent`), and `refresh`, run shortly after each `tasks-changed` and each change: it ends lanes whose cards are all Done, abandons those whose agent is gone, and sends the window `lanes-changed` when the listed lanes read differently. The Agent API's `/v1/lanes` routes and the `hive_lane` tool are thin over it. Nothing else depends on a lane: it is bookkeeping.
- **Merge slot** (#350): `main/mergeSlots.ts` is the logic, unit-tested with a fake clock: a slot per project path and branch (one object each, kept registered while anything uses it: unused ones are dropped only when a new one is made past a cap), its holder (an agent's launch, by `runId`, or the user's merge, `asUser`; each hold has an id, which the user's Release must name) and its line, synchronous between awaits so a check and its change can't be split. Claims wait in the call (`claim`, woken by any change to the slot, bounded under fetch's 300 s), keep their place between calls, and a turn given between calls lapses after 2 minutes. `sweep()` ends what has run out (a launch gone, a hold past its time unless its Progress run is still reporting), and `settled()` re-arms the slot's one timer, wakes the waiters, sets each agent's status note and tells the window. `main/mergeSlotHost.ts` wires it: `sessions.onLaunchEnded` releases holds, `progress.openRunOf` keeps them, `merge-slots-changed` updates the renderer (`components/MergeSlots.tsx`: Overview, Progress panel, Merge dialog), and a record per workspace in app data (`merge-slots/`) lets `recoverMergeSlots()` report a hold Hive closed under when the workspace opens. `projectAgents.merge()` runs the Merge dialog's merge through the gate the host sets at startup (`setUserMergeSlot`, `asUser`), so `projectAgents` doesn't depend on the slot service.
- **Moved workspaces** (#146): `main/workspaceMove.ts` records where the workspace and its projects were last opened (`lastPath`), checks on open (from `onOpened`, in the background) and sets `WorkspaceInfo.moved` for the banner (`components/MoveRepair.tsx`); `movePlan()` works out the worktrees, session folders, per-path data (the adapter's `copyPathData`, `copyMissing()` in `fsutil.ts`) and Open Recent to repair, and `repairMove()` does it (one at a time per window, refused while agents run). Path rewriting is in `shared/movePaths.ts`. Moves whose data copy failed are kept in project.json (`pendingCopies`) until it works. `main/agentWorktree.ts` makes a missing agent worktree again (on its branch, or new from its base), for Repair and for Start, never pruning another missing worktree's link.
- **Rendering**: `components/AgentPanes.tsx` has the agent strip, `TerminalLayer` (every agent terminal of every project stays mounted and is positioned into its pane) and the pane frames drawn over it. `TerminalView` holds a WebGL renderer only while visible, within a window-wide budget (`WEBGL_BUDGET`, 8): a terminal that becomes visible takes the context of the longest-hidden one if the budget is used up, and hidden ones release theirs after 30 seconds anyway. Chromium's own limit is about 16 contexts per window, beyond which it silently drops the oldest.

## Hive Assistant

The Assistant (`shared/assistant.ts`, `main/modes.ts`, `components/Assistant.tsx`, `components/Modes.tsx`) reuses the whole session machinery by being a **session host like a project**: its home, `<workspace>/.hive/assistant`, has a `.hive` folder like a project's, with a `project.json` holding one agent (`assistant`). Hive never lists it as a project (`listProjectPaths` skips dot-folders), and because it is inside the workspace folder, `workspaceFor()`, window routing (`session:<home>#assistant`), close/switch/quit and the workspace's refresh all find it without anything new.

- **Where it differs**: `workspace.assertSessionHost()` (session calls and `agents:update`) accepts the home besides projects, and `workspace.isAssistantHome()` marks the few differences. `WorkspaceService.projectConfig()` overlays **Settings → Assistant** on the home's config (`assistantProjectConfig()`: its provider as the "project" default, per-provider model/effort/mode/arguments as the "project's" settings, an unset mode → the descriptor's `assistantMode`, one agent always). So `agentLaunchSettings()`, the footer and the settings dialogs work unchanged, and the workspace's own choices (Assistant Settings) are that agent's overrides, plus `mode`. In `sessions.ts` the Assistant works in the workspace folder (`cwd`), gets the workspace's skills for the Assistant (`hiveSkills(false, 'assistant')`, by `metadata.audience`) and only the hive MCP server (`HIVE_PROJECT` empty), is named "Assistant · <mode> · <date>", and its launch carries `instructions` (`assistantInstructions()` in `modes.ts`: its role and `controlRules()` from `shared/hiveGuidance.ts`, then the mode) and `trustedHiveTools` (`assistantTools(control)` from `shared/assistantTools.ts`). Session records keep `cwd` whenever it isn't the host folder, and `liveInfo()` passes the workspace folder to `resumeRecord()`.
- **Adapters**: `LaunchContext.instructions` → Claude Code `--append-system-prompt-file <launch>/instructions.md` (with `--system-prompt-snapshot off` on a resume, from 2.1.267, so the conversation gets the current text rather than the one it recorded, #334), Codex `developer_instructions` after Hive's guidance. `trustedHiveTools` → Claude Code `--allowedTools mcp__hive__…`. Claude Code's Plan mode refuses MCP tools, which is why the Assistant's Claude Code mode is Manual.
- **Workspace info**: `WorkspaceInfo.assistant` is the home's `ProjectInfo` (named "Assistant"). The renderer finds it with `findProject()` alongside projects (actions, Compact, the mode menu, events), `applyLiveState()` updates it, and `actions.reveal()` shows its panel instead of a project.
- **Modes** are Markdown files with a small header (`parseMode()`); `resources/modes` ships four. `WorkspaceService.onOpened` copies them into a workspace without a `modes` folder (`bundled.ts`, which first moves a workspace's `.hive/personas` from before 0.9.3 to `.hive/modes`; until then `workspace.modesDir` is the old folder); `modes:list/create/delete/restore` manage them, the watcher emits `modes-changed`, and they are edited with `DocEditor` (drafts protected).
- **Control** (`main/assistantControl.ts`): per workspace, the Assistant's API token (rotated by `sessions.onAssistantLaunch` before each launch, written to `assistant-api/<hash>.json` in the profile, which `hiveMcp()` passes as `HIVE_API_TOKEN_FILE` with `HIVE_ROLE=assistant` and `HIVE_ASSISTANT_CONTROL`), its list of actions, the per-turn count (reset by `sessions.onAssistantPrompt` on its prompt hook) and the questions waiting on the user (`ask()`/`answer()`, events `assistant-questions`). `servers.ts` tells callers apart (`callerStore`, an AsyncLocalStorage): the Assistant's calls are confined to its workspace and its changes go through `assistantChange()` (control level, the 30-change limit, recording). The API server always listens; with the Agent API off only an Assistant token gets in. `hive-mcp.ts` offers the Assistant's tools by `HIVE_ROLE`/`HIVE_ASSISTANT_CONTROL` (`shared/assistantTools.ts`, no imports, so it can be a chunk). A first task reaches the CLI as `LaunchContext.initialPrompt` (the adapters' last argument, `promptArg()`); `sessions.noteUserInput()` (from `pty:write`) and `userTypedAt()` keep the Assistant from typing over the user. An agent the Assistant adds emits `agent-added`, which the renderer turns into a page dot (`newAgents`) or the project's focus, never a view change.
- **Trust questions**: an adapter's `startupQuestion` (Claude Code and Codex: "trust this folder"; Copilot: "Do you trust the files in this folder?") seen in the output while starting makes the agent `waiting` (`askedAtStart`) until its ready output, start hook or first prompt.
- **Journal** (#1031): `main/journal.ts` is the store (one database per Assistant home, `journal.db`, opened through `db.ts` with a `setup` hook that registers `journal_text()` for the FTS triggers and sets `auto_vacuum` on a new file); `main/journalService.ts` holds the workspace side (settings in workspace.json, Hive's facts from `lanes.ts`, `tasks.ts` and `lastRun.ts`, the inbox notice on a change, delete). The routes are `/v1/journal` in `servers.ts` (Assistant only, refused while off); the tools are in `hive-mcp.ts`, offered when `HIVE_JOURNAL=1` (`index.ts` sets it at the Assistant's start), with their replies in `shared/toolReplies.ts`. `shared/journal.ts` has the kinds, limits and settings; Settings draws `JournalSettings.tsx`. How the Assistant uses it (#1032): `main/startView.ts` gathers the state view (the board, lanes, live agents, the journal's few entries, `digestDue()`) and `shared/startView.ts` writes it within its byte budget; `index.ts` sets `sessions.startContext`, which `sessions.hookReply()` calls for a SessionStart and the adapter's `startContextReply()` carries (Claude Code only). The journal rule in the Assistant's contract is `journalRule()` (`shared/hiveGuidance.ts`); the workflow is the bundled `journal` skill; `journalSuggestion()` adds the once-only suggestion to a handover the Assistant writes with the journal off.
- **Panel state**: `assistantOpen` is saved per workspace as the pane entry `assistant-open:<path>` (`ui:setPane`), its width as `assistant` and the overview's share as `assistantTop`.

## Task board

`main/tasks.ts` keeps every rule of the board; the cards themselves are rows of the workspace's SQLite database, `.hive/hive.db` (#1017; in 1.0's tables since #1209, Storage below), which only `main/boardStore.ts` reads and writes. Lanes, card watches and metrics are in typed tables of the same file (#1212, the 1.0 group's step): `schema/storeCodec.ts` maps a store's entry to its rows and back (in columns when it reads back equal as JSON, else kept whole in `extra` as an array of one, `[entry]`, where extra fields are always an object; an entry no row can hold kept aside in `board_meta`), and `main/storeTables.ts` reads them (0.9's `store_rows` while the upgrade waits), saves only the entries that changed in one transaction under the board's lock, and moves 0.8's files in once (`openTable`); their values are `board_meta`'s `<store>.<key>`. Sessions and deliveries are in typed tables of their own (#1211, the 1.0 group's step 6, the last of `store_rows`' stores: the table goes with it): `schema/sessionDeliveryCodec.ts` maps a record to its columns and back, equal as JSON (what has no column, or isn't of its column's form, kept in `extra` as the record's own keys, `$`-keys escaped; only a record without an id is kept aside, `setAside` or deliveries' `invalid`), `schema/sessionDeliveryTables.ts` reads and writes them (only the rows that changed, in place), and `main/storeRows.ts` gives them `openTable` (a store's old JSON file moved in once, one transaction marked `imported`, the file renamed `….imported-<time>`; a file found after that kept the same way and never read) and `saveTable` (the board's lock, one transaction); their values stay in `store_meta`; while the 1.0 upgrade waits they are read from the file's 0.9 `store_rows`. Deliveries keep their in-memory store, loaded once per host and published after each transaction (#647, #649), with the table as its durable copy, written by key [Darren, #1211]; a session is read by its key where one is asked for (`workspace.sessionRecord`), and the tables' other indexes are for readers that don't load a host (P4's actions, cross-host views; #1236). Session records (#1061, `main/sessionStore.ts`, behind `workspace.sessionsFile`/`mutateSessions`) keep no copy in memory: a change reads the host's records in its transaction (`writeStore`, a key range per kind, the deleted lists only if it uses them) and writes the rows it changed; `exportSessions` (Remove from Hive) writes them back to the folder's sessions.json under the store's lock and in one SQLite write transaction (`withStoreLock`, `BEGIN IMMEDIATE`: read, file, delete; no writer of any process commits between) and marks the scope `exported`; while the project is being removed (`releaseSessions` ends that) or hidden as removed, reads leave the file alone; once it is back, `moveBack` takes it in beside any record made meanwhile. Another workspace finding the file where the project has no records moves it in (`openStore`'s `whenEmpty`). A store keeps its entries in memory and its own lock; its saves take the board's lock (`boardLock`), so they never run inside one of the board's transactions on the shared writer (one attempted inside a board change is refused as a bug), and the board's poll for other processes' commits (`data_version`) doesn't see them. `main/db.ts` is the database layer every Hive database uses (the board now; metrics and the Assistant's journal later, #1019, #989): `node:sqlite` (built into Electron's Node, so nothing native to rebuild), a writer and a reader connection per file, WAL and the settings, the schema's steps (`Migration`, recorded in `schema_version`, a `VACUUM INTO` copy in `.hive/backups` before a step runs on a file with data) and the read-only open of a file from a newer Hive. **A group of steps** (`Migration.group`, the board's `'1.0'`: #1207, SPEC §16.17) runs as one: `migrate()` asks `OpenOptions.approve` once for all of its pending steps (refused, the file opens read-only with `Db.pending`; the board's banner and dialog, `BoardUpgrade.tsx`, ask the user and call `board:upgrade`), then `runGroup()` holds the file with `locking_mode=EXCLUSIVE` for the whole run (granted only while no other connection, so no other Hive, has the file open: `DbInUseError` otherwise), checks `beforeGroup` (the board: no other profile's fresh presence marker, `presence.ts`), keeps a copy that is never pruned (`<family>-before-<group>-v<n>-…`), and runs every step in one transaction. A new file takes the group unasked. `restoreBoardBackup()` (Help → Restore the 0.9 Board Backup…) copies the board aside under the same exclusive lock (`soleCopy`), then puts the group's copy back (the newest from before the group's first step: `copy09`). While the upgrade waits, `assertUpgraded` refuses sessions' starts and stores move no old file in. Each replacement of the file moves the workspace database's generation on (`dbGeneration`, `onDbReplaced`): deliveries, watches, metrics, lanes and sessionStore drop or read again what they keep from it, and a save from an older generation is refused by its `saveStore` guard. A card's row keeps its JSON document (`doc`) as its file held it, with generated columns for queries (`col`, `ord`, `project`, `project_id`, `agent`, `archived`, `updated_at`, indexed), so `clean()` builds the same card from it and the Agent API's JSON is unchanged; moving comments, history, decisions and links into tables of their own later is a schema step and a change to `boardStore.ts` only. **One write path**: `boardWrite(ws, fn)` takes the board's lock (`board-lock:<workspace>`, every window's), runs `fn` in one transaction on the writer (`BEGIN IMMEDIATE`, rolled back if it throws) and emits one `tasks-changed` after it commits if anything changed (`boardChanged`). Every write goes through `writeOp`, which refuses once SQLite has undone the transaction itself (`isTransaction` false: an error that rolls the whole transaction back) and marks the change lost, so a batch that skips a failed card never goes on in autocommit, and the change fails whole as it ends. It is re-entrant: `boardLock`, `cardBatch` and each card change of `tasks.ts` are `boardWrite`, so a batch (Archive All, `updateTasks`, a project's cards) is one transaction told once, and reads inside a write use the writer (they see its own changes) while every other read uses the reader (the last commit, never a batch half done). The board opens when first used (`boardOf`, synchronous, so nothing reads it before its cards are in): the first time, `importFiles()` moves the cards' files in, in one transaction checked before it commits, renames the folder to `tasks.imported-<time>` (tried again at the next open if Windows refuses) and leaves a stub for older versions (`board.json` with the next number, a README); later opens take nothing back from the stub: whatever card files an older Hive saved there are copied, intact, to `.hive/tasks.set-aside` and removed from the stub (`setAsideStub()`: once per content, a different file of the same name beside it under its own name), with one notice; their numbers are reserved. `takeNumber()` keeps the next number (`board_meta`), past every card's and every card file's (damaged ones too), and moves the stub's `board.json` on at once, so an older Hive never reuses one after a crash; the archive batches are a table. A change by another process is noticed by a poll of the writer's `data_version` once a second (`pollOther`; Hive's own commits don't change it). Every change takes a `TaskActor` (`user` from IPC, `assistant` or an agent's name from the Agent API) for the card's history, and is made in its board change, against the card as it is then. The rules are in the service, not the callers: anyone moves a card between columns, Done included (each move is in its history with the actor), but only the user creates a card in Done or puts Done in order, a project agent can't put one On Hold (`checkHold`), a failed verdict can't move a card on, archived cards change only for the user, and `TaskPermissionError` becomes `403` in `servers.ts`. Order within a column is a float (`orderIn()` puts a card halfway between its new neighbours). `main/taskStart.ts` starts a card, one start per card at a time: it takes the card first (`updateTask` with a `check` run in its board change: still startable, same project), then starts an existing idle or stopped agent (`sessions.sendPrompt` or `sessions.start`) or a new one (`addAgent`) with `taskPrompt()` from `shared/tasks.ts`; if that fails the card goes back and a new agent is removed. `deleteTask` is a board change too, so a change waiting for it finds it gone; the card goes to the Recycle Bin as `<n>.json` (`binCard`). `exportBoard()` writes the board as the files were before 0.9 (Export Board to JSON).

Changes emit `tasks-changed` (routed by workspace path), once a board change commits; the board's poll emits it for a change another process committed. The renderer keeps the board in the store (`tasks`, `loadTasks()`, one read at a time): the cards on it in full and archived ones in short (`TaskCard.summary`, made in the query by `archivedSummaryDocs()`), except while a view asks for them in full (`wantFullArchive()`: the Archived view, an archived card's dialog), and derives every view from it: and derives every view from it: `components/Board.tsx` has the board (the six columns of `TASK_COLUMNS`, drag and drop, collapsed columns and folded cards kept per workspace in `ui.boardFold`: `saveFold()` sends a change, `ui:changeBoardFold` applies it in main with `applyBoardFold()` to the window's own workspace's entry, the archived list), the Board view and its sidebar panel, the project Tasks tab and the card and Start dialogs. Agents reach it through the hive MCP tools (`hive_list_tasks`, `hive_read_task`, `hive_create_task`, `hive_update_task`, `hive_reorder_tasks`; `hive_start_task` for the Assistant only). Each agent launch has its own Agent API token (`main/agentTokens.ts`: made by `sessions.start` before the launch, in the pty's `HIVE_API_TOKEN` and the hive tools' `HIVE_API_TOKEN_FILE`, ended on exit by `runId`); `servers.ts` turns it into an `agent` caller, and `taskActor()` gives the board a `TaskActor` with `scope`, its project. The scope is enforced in `tasks.ts` (`scopeOf`, `inScope`, `readTask`, `listTasks({ scope })`, `cardRefs` keeping refs outside the scope, `placement` and `reorderTasks` among the scope's cards); `refsOutside()` gives the API's `elsewhere`.

**Card watches** (#128): `shared/watch.ts` is the pure part, unit-tested: a card's `CardMark` (column, latest comment and verdict times, agent, archived), `changesBetween()` (what changed, as a condition counts it), `movedIntoSince()` (a move into a column from the card's history, for `moveInto`), the `since` token of bounded waits (`encodeSince`/`decodeSince`), and the wake lines (`wakeLine`, `limitLine`: a watch delivery's text) and shows (`watchLabel`). `main/watches.ts` keeps each workspace's watches in its database (`storeTables.ts`, #1018, #1212: a row each in `watches`, with `watch_cards` to find a card's, one transaction a save; loaded on first need, then checked against the board at once): `registerWatch` / `cancelWatch`, `evaluate()` on every `tasks-changed` (a watch that matches gets `fired`, its line), `deliver()` (after the settle, once the agent is idle and nobody types there: makes the line from the cards as they are then and hands it to the delivery service as a `watch` delivery, its id saved on the watch, which ends once the agent has read it, Deliveries below; not idle yet, it is tried again on the agent's next idle `session-status` or the 5-second tick, which also fires wait limits). `SessionManager.watchFor` (set by `initWatches()`) gives an agent's watch to `emitState`, which shows `ready`/`finished` as `watching` while there is one. `POST /v1/tasks/wait` in `servers.ts` registers watches (`wake`) or waits in place on `tasks-changed` events (bounded), and `watchKeepsQuitWaiting()` tells *Quit when agents finish* whether a watching agent counts. The doorbell the service types is confirmed by `lineWriter.confirmTaken`: it waits for the CLI to take it (`sessions.promptsTaken`, counted from UserPromptSubmit) and presses Enter once more if it doesn't (`submitAgain`, #376), never over input of the user's since the line began (#652: `userTypedOverLine`; the line is then the user's, `leaveToUser` holds the composer until a prompt is sent, and `LineFollow.left` puts what it named back to wait). `main/loopCheck.ts` follows agents that have watched cards (`noteLoopWatch`, from `registerWatch`): one idle with no watch past a grace gets its cards in play marked (`sessions.setNotWatching`, shown as stalled through `notWatchingReason` in `shared/tasks.ts`) and one notice; `emitState` clears the mark when it works or watches again.

**The queue's runner** (#1360, SPEC §16.9.3): one per project and target across Hives on a workspace. `QueueRunner.acquire`
takes the target's lease (`queue_runners`, written through `factStore.ts` inside `boardWrite`), from no one or from a

has a job object on Hive's process supervisor (`processSupervisor.ts`: the PowerShell and C# `HiveJobs` host that
agents' launches use too, extracted from `agentProcesses.ts`; in the app the runner is given agents' host): named
`Local\HiveQueue-<lease>`, kill-on-close, no breakaway, swept and followed as agents' jobs are (#543, #659, #678); the
supervisor writes each process it follows to the lease's journal (`<worktrees>/.queue-journals/<lease>.followed`,
flushed through) before following it, and ends one it can't write (`unowned …`, the runner pauses). A lease's duty is
its job (`what = 'job'`), never the supervisor process. Commands start through a detached Node launcher (`queueJobs.ts`)
that the supervisor puts in the job, and that is recorded (`queue_runner_procs`, in a write that checks the lease), before
it is told to run the command. Records are duties per target: `settle` (at every acquire) ends earlier leases' jobs by
name, seals their journals (`sealJournal`: the file moved aside, a folder in its place, so an outlived supervisor can't
append), reads them once, ends the processes their records and journals name still running, waits, removes their
folders, and only then drops their duties and clears the journals (the seals stay); anything it can't rule out (a
journal it can't read, a process or folder that won't go) pauses the queue needs-you, naming it, and leaves all of it
for the next try. A lease's worktree (`queue_worktrees`) is removed once its duties are done. `withWriteFence`
(factStore.ts, an AsyncLocalStorage check run inside every store write) fences everything the queue's work writes,
reconciliation included (`MergeQueue`'s `holds`; a lost lease throws `LeaseLost`). `queueFolderNeeded` keeps a released
runner's worktree while an entry, an unfinished advance or an in-flight card's ruleset needs it. Workspace close
(`WorkspaceService.closingTasks`), quit and project removal release the runners (`releaseQueueRunners`,
`forgetProjectQueues`).

**The one path.** An intent (Agent API route or hive tool) or a user move (IPC) calls `runtime.move(card, request,
actor)`. It asks the platform adapter for the facts the guards need first, outside the transaction (keys, files,
containment, check facts: slow reads). Then, inside one `boardWrite` transaction, it reads the card, its facts and
its ruleset, **re-reads the cheap folder state the guards depend on** (head and dirty for Git; for None the stored
hash against the watcher's write log since it was computed), refusing if it differs from what the slow reads used
rather than racing (P2's protocol: the adapter's `evidence()`, a fingerprint read with no process: Git, the target's
and line's refs from their files, the card folder's own HEAD, its index, an operation under way and each covered
tracked file's and folder's size and time (the builder's own paths in a shared folder); None, its paths' hash; plus
the facts of the cards it waits for. `prime()` lists what it covers once per intent; a card in Todo has no folder yet,
so a start covers its target alone. Taken before the slow reads and again in the transaction, in every intent with
platform inputs (start, submit and its requeue, verdict, answer, report merge); if it changed, or can't be read, the
intent is refused `evidence.changed`, "try again". **Cached stat data alone never refuses** (#1206): the fingerprint stays cheap (sizes and times, no process), and
`evidenceOf` also takes the platform's own answer by content (`content()`; Git: the same refs, HEAD and operations,
`ls-files --stage`'s entries, and `hash-object` of each covered file `diff-files` lists whose content isn't its
entry's, so git applies each path's attributes, filters and line endings, and reads every index version and extension
itself). Just before the transaction (`revalidate`), if the fingerprint moved, the content answer is asked again
outside it: the same answer, with the fingerprint steady across the asking and the cards waited for unchanged, means
likely only stat data moved (an outside `git status` refreshing the index, an editor's git integration, a file
touched). Even then the guards' inputs read in between may have seen another state and back (HR5, round 2: dirty,
clean when they read, dirty again), so the new fingerprint is never adopted for them: the intent is **gathered again**
from the top, once (`regather`), every read afresh; a fingerprint moving again in that pass refuses. Anything else (an edit, a staged change, a checkout, an operation,
an index git can't read) refuses, as before. None's fingerprint is already content (its paths' hash). Each intent,
and each lane's look in a branch-update pass, is one `gitStep` (`platform/git.ts`, #1376): what it asks about fixed
commits (an ancestor, a merge base, by full ids) is asked of git once in it per repository (its common git dir, read
from `.git`: a project and its worktrees share answers, another repository never); nothing about refs, HEAD or files is
kept, so every read of state (a regather's, the move's own at its boundary) asks git again. The Assistant
suggested letting git answer (#1206 round 1) after HR5 found that reading the index in Hive (an earlier round) got
attributes, v4 paths and required extensions wrong. **The practical guarantee:** git, the files and SQLite can't be
one transaction, so the fingerprint proves only that nothing it covers changed between its two reads; a change after
the transaction's read, or one it doesn't cover, is caught afterwards by the watcher and reconciliation (stale marks,
observed facts), never claimed excluded); runs the guards in the ruleset's order; on a refusal appends `Refused` (agents and the Assistant)
and returns the refusal; else writes the facts and `Moved`, updates the card's `column`/`stage` cache, and writes
the side effects as `card_actions` rows (wakes, notifications, the queue, slot work) in the same transaction. A worker
runs them after the commit (`afterBoardWrite` starts it) and again at start for any left pending, so nothing outside
happens for a write that rolled back, and nothing is lost to a crash after the commit (SPEC §16.4.5).

**Same change.** The Git adapter stores each submission's endpoints (base, head), its candidate key
(`git patch-id --stable` of the diff with no context lines, `-U0`) and its files, and never recomputes a submitted
change from the target's current state.
Sameness is a **replay**: `git merge-tree --write-tree --merge-base=<B1> <B2> <R1>` must succeed and give `<R2>`'s
tree; patch-id only rules out a different change quickly; anything unsettled is not the same (SPEC §16.3.2). In a

**A card's work, read (#1223).** `shared/workflow/workView.ts` makes the fold a **work view**: the start's folder,

**Runs as checks** (#1222, `workflow/runChecks.ts`). A progress run for a card is bracketed: `POST /v1/progress/resolve`
(before hive-progress starts the command; a start through the Agent API, at its start) reads what it is checked against
(`checkStart`: the folder settled in the write log first, then its start time, `git status`, and a stat snapshot of its
tracked files and reflog; None: the card's declared paths' revision and the deliverables' snapshot), kept by the link
until the run starts, then by the run's id (at most 200 at once). Its finish (`checkEnd`) reads the end and writes
`CheckRan` in the card's facts inside a board change, counted or with why not (the rules in the module's header; the
write log decides "nothing changed", the snapshots where its record isn't complete), and the run keeps how it counted
(`ProgressRun.counts`) for its details. A `--check` run counts only if it reported the command its link resolved for
that check. The card's revision is read from where it works when the run starts: its own line's folder head (which the
tested checkout must be), or in a shared folder its newest attributed commit (which it must contain); a card with no
start in its facts yet is checked on the run's own checkout. None hashes with the options' exclusions, and its end
reads the card's declared paths again: a list changed during the run is a new revision. The fact is written only while
the card is still its project's (and None's declaration the one the end read), in the board change.

**The watcher** (`src/main/platform/observe.ts`, #1214; its lifetime in `watching.ts`, started in `index.ts`). One
`Observer` follows the open workspaces' projects (each refresh's `ProjectInfo.platform`; a closing workspace's go at
once), each repository and folder watched once however many projects share it:
- **Git, per repository** (its common git dir): its events come from its main folder's watch (which holds `.git`),
  never from watches inside `.git`: Windows won't rename a folder while a handle is open on anything inside it, so a
  watch there (or on any subfolder) stopped the project being renamed. A bare repository has one watch on its git dir.
  `HEAD`, `packed-refs`, `refs/heads`, `logs/HEAD` and `worktrees/<n>/{HEAD,gitdir,logs/HEAD}` count. A burst is read
  once (150 ms quiet, at most 1 s), from the ref files with no git process (`linesOf`, `refSync`), and said to
  subscribers as `lineMoved` (a branch; a target is a line, whose the subscriber's options say) and `folderMoved` (a
  working folder's HEAD). Only a repository's first read takes what it finds silently; every later read (its events, a
  rescan, a refresh's `follow`) says each move, so no move is taken in unsaid. Each read also compares each folder's `logs/HEAD` size, so a reflog entry whose event was lost
  still counts. The minute and window focus read again (`rescan`), for what a watch missed.
- **Every working folder** (a repository's worktrees, at most 64, and a None project's folder) has a **write log**
  from one recursive watch on it (`.git` left out of the log; `node_modules` kept, since a project can track vendored
  files there, what git ignores being dropped when a check asks). Windows hands a watch its changes in
  a small buffer: a burst (a commit writing objects into the main folder's `.git`, from any worktree) can overflow it,
  and Node names no file. The record then restarts, so a check over that moment is unknown and falls back to its
  snapshot. Each HEAD reflog entry (`:reflog`) and each agent's edit hook (`:edit`, `sessions.ts` `preToolUse` →
  `markEdits`) goes in too. Kept 6 hours and at most 20,000 entries a folder.
- **`changedBetween(folder, t0, t1)`** answers checks (§16.13): it lets the folder's events arrive first (until 150 ms
  quiet, at most 2 s), counts those arriving until then (an event is timed on arrival, after its write: the safe
  side), and drops what git ignores (`check-ignore --stdin`; None's adapter passes its deliverables instead). It is
  **unknown** when the record isn't complete for the whole time: the folder not watched, a watch armed less than
  250 ms before t0, an unnamed event (lost events, a watch restarted), a watch down, the folder replaced (a watch
  follows its folder renamed away, silently, so each answer checks the folder's file id). The adapters' `checkRun`
  then fall back to their stat snapshots (`checks.ts` `snapshot`).
- **#964:** a watched folder deleted makes Windows send its full path in an endless stream; that watch ends at once and
  is tried again every 3 s until the folder is back. An error does the same.
- **Letting go:** a folder being deleted or removed (Delete project, `git worktree remove`) is held by no watch meanwhile:
  `observer.suspend(paths)` / `unwatchedWhile` close every watch on or inside it, like `files.ts`'s `suspendWatching`.
  A Git project is watched only at the repository root its detection named: one whose repository is gone watches
  nothing, never a repository above it.
- Measured (`process.cpuUsage` over 20 s, nothing done by the test): following Hive's own repository (1 repository, 7
  working folders) while other agents worked in it, 31 ms of CPU (0.16% of one core).
- The adapters' `observe(onChange)` subscribe to it; None's drops a written deliverable's cached hash first
  (§16.3.3). The Files tab's own watcher (`files.ts`) stays as it is, for the tab.

**The runtime in the app (#1263, P4).** `workflow/service.ts` is the app's one way to a project's runtime:
`workflowFor(ws, projectPath)` gives the `Workflow` of a project of an open workspace (null for a path that isn't one
with a platform), made once per workspace and project and again for the workspace's next lifetime (a close, or its
window opening another), on the board's store (`FactStore.forBoard`). Its `locked` is a change of the board
(`boardWrite`, which joins a change the caller already holds: tasks.ts's `boardLock`), refused once its workspace's
lifetime has ended; `autoRun` is off, so its side effects are only `card_actions` rows the actions worker runs after
the commit (`runActions`/`perform` stay in `runtime.ts` for `tests/workflow`). Its options are the project's resolved
ones, read again at each `workflowFor`: `workflow/rulesets.ts` (`resolveOptions`) lays the platform's all-off, the global
defaults (`settings.workflow`), the workspace's (`workspace.json` `workflow`) and the project's (`project.json`
`workflow.options`) over each other, the first two per platform, with each option's origin, and falls back to all-off
(logged once per project and reason) on an unknown option, a value it doesn't take (each option's check in `TAKES`:
its type and its choices), another platform's options or a contradiction. `optionsFor` gives them with their origins.
Its `reconcileActs` is a getter on the Advanced switch `hive.workflow.enforce` (`workflowEnforced()`, default on,
#1120's table: off is P3's behaviour), read at each use. A None project's kept runtime keeps its paths' hashes, so
each `workflowFor` first syncs them with the watcher (`syncHashes`, one at a time per instance): the paths
`observer.changedBetween` saw written since the last sync are invalidated, or every hash is forgotten when its record
of that time isn't complete. `cardRunRevision` (`runChecks.ts`) takes its runtime from `workflowFor` too.

**Gates at boardWrite (#1265).** `tasks.ts` `runIntent(wf, n, actor, call, zero9)` is the one intent path: it runs a

`Verdict` for it (one owner per fact) but still its `Blocked`, `Decision`s. The user's and the Assistant's column moves
take it when `gateOf` says so (the rules enforced, a card from 1.0, a project with a platform, a stage its ruleset has;
a batch's cards too, in the batch's change): `Workflow.move` with `confirm` for the user (interim until #1290/#1275),
`override.reason` for the Assistant. A refusal is `WorkflowRefusedError` (its `refusal`), which `apiErrorReply` turns
into §16.8.3's 409 body; `tasks:move` returns `moved | ask | refused`. For you (#1269): `tasks:answer` is
`answerTask` (the user's only), `Workflow.answer` on the same path, its checks of what the answer may be (the request's
kind and gate) made first, a Decide answer's decision added with its first write (`zero9`); `tasks:forYou` is
`cardWork.forYou`, every live card's open requests folded from its facts on one snapshot. The round limit is asked by the
runtime's `askAtLimit` (a verdict's fail, the user's decline) and by the recorder's `roundLimit` for a failed review given
on the board (until #1268), from the card's lane's rounds (`CardRecord.rounds`); `lanes.ts` reads `roundLimitCards` to
pause a lane on a card waiting for that answer (`LaneCard.roundLimit`), while the rules are enforced. Runtime writes outside an intent's write (a
refusal's `Refused`, None's declared paths) go through `locked` too, and `start` stores its ruleset only in its write.
Before P7 a builder's own worktree is its card's folder (`cfg.agentFolder`, from project.json; `StartPlan.existing`:
no `prepareSlot`); `cfg.runsOf` is the agent's open Progress runs and background tasks (`setRunsGoing`, from index.ts).

step first (a submission on `predicted`, the state the start would leave), decides on the union of the rules they skip
(`failingOf`), and writes them all in one write, which checks the rules again (`failingIn`) and throws `DragUndone` to
undo itself when one wasn't decided on or the evidence moved. Every write of the app's runtime is a `boardSavepoint`
(boardStore): a part of the change undone on its own when it throws, with the after-commit callbacks it registered; a
batch's card is one too, kept when it is a workflow refusal (its `Refused`). `cfg.enforced` (the Advanced switch) empties
every move's guards (`idsOf`) and `skippedRules`.

**Acting once (#1263).** `reconcile.ts` records an observation once (its dedupe key) and applies what follows from it
apart from that, in the same write, whenever `reconcileActs` is on and it isn't applied yet: an integration
(`integratedOutside`) until the card is Done; a stale pass (`staleEffects`) once per `Stale` fact, its builder's wake
written for that fact (`card_actions.fact`, read with `hasAction`) as the record that it was applied. So an observation
recorded while the rules were off is acted on at the next run once they're on, and repeated runs add nothing.

**Reconciliation in the app (#1217, P3; acting since #1263).** `workflow/reconciler.ts` follows the open workspaces' projects (as
`platform/watching.ts` does) and subscribes to the watcher for each: a line or a folder's head moved, or a write,
reconciles the project once its events settle (`RECONCILE_DEBOUNCE_MS`; one run at a time, a run asked for meanwhile
runs after). It also runs once as a workspace opens (`onOpened`), when a window is focused (at most every 10 s), and
when a card is read for its Work section (`tasks:work`: that card, whatever its stage). A run takes the project's
runtime from `workflowFor` (above): `reconcile.ts` records what it observes (HeadMoved, Integrated by outside,
MergedInPart, Stale, CarriedOver, CommitAttributed, LeftTarget, Gone), and the table's moves, queue cancellations,
actions and wakes run only with `reconcileActs`, the switch `hive.workflow.enforce` (on by default; off, P3's
record-only). It
reconciles the project's unfinished cards, a card asked for, and Done cards whose target line moved. Every observed
fact has a dedupe key (`prev:`, `cycle:`, `commit:`, `part:`, `left:`, `gone:`; `stale:` and `carried:` per cycle and
revision), so two Hives write each once, and a writer that lost the race reads again and writes what is true now
(`observeHead`). Every delayed observation is written only in the cycle it was read in (`sameCycle`, checked under the
write's lock; a `HeadMoved` also after the very fact it was read after), so a head read before a card started again
never lands in its new cycle; shared-folder attribution, immutable once written, waits for the next run when the
folder's cards changed since it read them. `TargetMoved` records the card's target from the last head recorded this
cycle to the head now, read again under the lock from the ref files; a target that doesn't exist (git says so) is
recorded as null, so its deletion and its return are moves too, and an unreadable one records nothing. `Gone` is recorded for a line, the card's own
folder and the repository, only for what doesn't exist (`presence`: ENOENT; anything else is unknown). Done cards are
reconciled when their target moved: an event's line, or a target whose head isn't the one stored as last checked
(`board_meta` `workflow:<project>:target:<line>`; '' for a deleted target), so a reset while Hive was closed is found at
the next open or focus, with one read per target. The checkpoint moves only once all of that target's Done cards were
reconciled to the end (`ReconcileHooks.unknown` tells of a read that couldn't be made, and a failure counts too): one
left undecided is looked at again at the next run. Trailers name cards by their keys (`Hive-Card: HI-12`, #1294); the name form the adoption keyed cards by before (`hive-1263`) still finds them (`cardByKey`) where the name is no project's key.
Platform reads are made outside the lock; `wf.write` stores the ruleset its facts name in its own transaction
(`currentRuleset(false)` reads without storing). A run stops once its workspace closes or its window opens another; its
watch goes as the workspace closes.

**Rulesets.** Compiled from options, stored once by hash (`rulesets` table); a card's `Started` fact names its
ruleset. Pieces are looked up by id: an unknown id refuses to compile, and a ruleset from a newer Hive is read-only.

**Merge queue.** One worker per repository, holding `repoLock`. Entries come from `IntegrationRequested` facts (each
with an entry id; cancelled, failed and integrated entries are skipped); the order is rebuilt from facts at start,
after reconciling any entry with `IntegrationStarted` and no outcome. The test merge happens in the queue's own
worktree on `refs/hive/queue/<entry>`; merge checks are progress runs attributed to Hive; the target advances by
compare-and-swap (`update-ref` with the expected old value), and when the target is checked out in a folder, by the
**journaled** read-tree/update-ref protocol of SPEC §16.9.2 inside the folder fence: conditions checked before the
folder is touched (branch, ref, nothing staged, no unstaged changes in the merged files), each phase written to the
`IntegrationStarted` fact before it runs, a recovery table on restart, and a terminal "needs you" state that pauses
the queue (never `merge --ff-only`, which has no expected value). The repository lock (a lock file in the common git
dir, replacing the in-process `.git/hive-merge` lock of `withFileLock`, `fsutil.ts:512`) is held only for the
advance, never across the test merge (hooks, signing) or the merge checks, and never while an entry is paused. Every
submitted revision is pinned by `refs/hive/cards/<key>/<n>` until its card is archived; strict updates live only on
the queue's ref.

**Checks.** A run records its tested checkout and counts for a card's submission under SPEC §16.13's rules (the
checkout contains the card's revision; nothing written in the tracked tree during the run). `hive-progress --check
<name> --isolated` runs in a **check copy** from the review-copy pool, the remedy when a shared folder is busy.

**Slots and sessions.** `slots.ts` owns the worktrees under `<Workspace>.worktrees/<Project>/` and lends them by
**lease** (a `slot_leases` row: slot, card or lane, builder, from, to), one open lease per slot, taken under the slot's
lock. Sessions record their folder and lease; `sessions.ts` resumes a session only in its folder (as today) and only
while its lease is open or the slot is free at its last revision, so a reused slot never resumes the wrong work, and
Resume All skips the rest. `AgentDef` loses `worktree`. Review copies are detached worktrees from a small warm pool,
leased to one reviewer for one submission; reviewers' sessions live in the project folder, and their launch grants
the review-copy pool's folder through the provider adapter (`extraDirs`: `--add-dir`, Codex's writable roots by `-c`),
never the CLI's config.

**The card JSON contract** (`src/main/schema/cardRows.ts`): `composeCard(decomposeCard(n, doc))` stringifies to exactly
the document the card's row holds today, so the Agent API's card (tasks.ts `clean` of it), Export Board and a 0.9.3 Hive
reading an export see the same bytes. Each field of Hive's form goes to its column or child table; anything else (a
field Hive doesn't know, a known one of another type, a string with a lone surrogate) is kept as JSON in `extra`. The
keys' order is Hive's (`CARD_KEYS`: clean's, with `projectId` after `project` and `archivedFor`/`archivedBatch` last)
with optional fields present when they have a value and the required lists present even when empty; a card in another
order, or with a field missing or an optional list kept empty, keeps its key list in `layout`. A list entry not of
Hive's form keeps its exact JSON in its row's `raw`. On the live board's copy (20 Oct: 1179 cards) every card
round-trips, 103 with a layout of their own; written in about 0.3–0.5 s and read back in about 0.1 s. Cards written by
1.0 are of Hive's form. The API adds `key` and `stage` from the card's columns **after** the document's fields, so
today's JSON is unchanged but for the two fields at its end: additive, no API version.

**Where cards live (#1209).** The cards step (`schema/cardsStep.ts`, v5 in the 1.0 group, after #1212's v4) renames 0.9's `cards` aside,
makes the step's tables, copies every card in through `decomposeCard`, checks each composes back to its document before
the group commits, and drops the old table. `boardStore.ts` is still the only module that touches card rows, behind
the same calls (`cardDoc`, `cardDocs`, `putCard`…): a full read is `readCardRows` and `composeCard`; the readers of a
few fields of many cards (`archivedSummaryDocs`, `holdDocs`, `cardPlaces`) read only the columns and child tables those
fields need (`readCardRows`' `columns` and `parts`) and take each field with `cardField`, which honours `extra` and
`layout`, so they give what the 0.9 queries over the documents gave. The query columns keep what 0.9's index held where
readers picked cards by it: `archived` is 1 for `true` or `1`, `ord` is the order as a REAL column held it (a number
literal in a string as its number). `putCard` writes only what changed (#1210: `writeCardChanges`, against the card's rows read in the same transaction: its own row when a column changed, each list and list of entries compared place by place, so a comment is one insert and an edit one update; the rows end as a whole rewrite would leave them); `costDocs` gives costs only a card's title, project, column, holds and history;
`deleteCard` deletes the card and its rows go with it. Every read is one SQLite snapshot (`readSnapshot`, and
`readCardRows` on its own): a card's row and its child rows are separate statements, and another process committing
between them would otherwise give a card neither version saved (HR4, #1209 round 1). A board waiting for its upgrade (`Board.legacy`: a `doc`
column) is read from its documents as before. Tests and the e2e helpers read and write cards through the same module
(`tests/boardDb.ts`; `tests/e2e/boardRows.cjs`, which loads `cardRows.ts` with Node, so it imports nothing), and
`tests/boardDb.ts` `as09()` puts a board made by this build back as 0.9 left it.

**The fact store (#1215).** `workflow/factStore.ts` keeps one project's part of the workspace's hive.db (the 1.0 group's
facts step, v7: #1208's facts tables and what the runtime keeps beside them, Darren's rule of 20 Oct applied by the
Assistant: typed tables, never JSON values). A `CardRecord` is the board's card: its number (`id`), its key
(#1294: `HI-12`, its project's key now and its number there, #1219's; the scope's name and its number for a card
without one; `cardByKey` takes a key or an old key through #1219's resolver, `#N`, or that name form, but only for a prefix no
project holds or held as a key: a key no card has here is none, never the board's card with that number), title, labels and `blockedBy` from the card's rows, and the runtime's
columns of the row outside the card's JSON document (`stage`, `kind`, `target`, `pre_workflow`, and `card_paths` for
None's declared paths and pre-fill), so `tasks.ts`' saves of the document keep them and the Agent API's card is
unchanged; its `lane` and `reviewer` are its lane's (below). `stage` empty (a card no 1.0 rule has moved) reads as its column's stage;
`setStage` writes the stage and the column, its category (§16.4.3). **One lane record (#1291):** the runtime's lanes
are `lanes.ts`' (`lanes`, `lane_cards`: the lane's agents, state and list), with what only the runtime keeps beside them,
keyed by the lane's id: `lane_runs` (the ruleset in force when it started the lane, the card in flight, a list change
queued) and `lane_pending` (that queued list). A card's lane is the newest running lane of its project with it in its
list or its queued one, and its reviewer that lane's. The runtime ends a lane as `lanes.ts` does (state `ended`); its
`startLane` takes `lanes.ts`' lane of that id, or makes one by Hive (`tests/workflow`; #1270 wires the app's). `lanes.ts`
writes a changed lane again whole (deleted and inserted), so `lane_runs` and `lane_pending` have no foreign key and go
when the lane leaves the table (`storeCodec.ts` `onRemove`); and since the runtime writes lane rows too, a lanes save
compares with the table, never its own last save (`shared`). A target's queue pause is a table of its own per project
(`workflow_queue_pauses`) until P7 makes it the queue's; scalars (a line's last head seen, a folder's installed manifests) are `board_meta` rows keyed
`workflow:<project>:<key>`. A store reaches the database one of two ways (HR4's #1215 round 1: a connection's open
transaction is no sign it is the caller's). **On the board** (`FactStore.forBoard(ws)`): its writes go through the
board's own guard (`boardWriteOp`, writeOp's): only inside the caller's change of that board, in that change's async
context, and only while its transaction is live, so a fact commits with the card change it causes and is undone with
it, and once SQLite has undone the change nothing more is written; its reads are the board's (`boardRead`): the
change's own inside one, else the reader, each on one snapshot. **On a connection of its own** (`FactStore.open(file)`,
opened through the board's migrations: another Hive, a restart, `tests/workflow`'s runtime): a write is its own
transaction (`BEGIN IMMEDIATE`: another Hive's write waits for it), which what the store does inside it joins (it is
synchronous, and nothing else uses the connection), and fails whole once SQLite has undone it; a read outside one is
a read transaction of its own. Either way a record, a list, a lane or a pause is read on one snapshot, never mixing
two commits. An observed fact whose dedupe key is there already returns null, and the caller reads again.

**The recorder** (`workflow/recorder.ts`, #1216; P3 records, nothing is refused). Every card change is saved by

(folder, line, base, target, builder, kind, and the ruleset: the project's options in `project.json`'s `workflow`,
compiled and stored, named on the fact and on every fact of its cycle) only for a new work cycle, none yet or one that
ended Done: a card back in Doing for its review's fixes, or out of Hold, goes on in its cycle, its base, submissions and
rounds kept (HR4's round 1); into Review (or returned for review), `Submitted` (revision, base, head, the files changed
since the cycle's base, the candidate key, round, the builder's received decision generation, same revision, the
summary comment's id; a no-code card's has no revision, base, head, key or files); a review's start `ReviewStarted`
and its verdict `Verdict` on the latest submission, with the generation its reviewer had received; `Blocked` and
`Unblocked`; and each change of the card's decisions, added, its words changed or removed (`removed`), a `Decision`
with the next generation (monotonic, from the facts). **Receipts** (`DecisionsReceived`) record what an agent was
given, never more (HR4's rounds 1 and 2): a card read in full (`GET /v1/tasks/:n`, `tasks.readTaskSeen`) and a decision
line received (`decisionWakes.ts`: `newDecisionsOn` reads the board with `tasks.allTasksSeen`, and the delivery's
`meta.gens` saves each card's) carry the card's decision generation **read in the same snapshot as the decisions
given** (`decisionGenerations`), and the receipt records that generation, never one looked up later (a decision
changed back to earlier words is still a later generation), once, in a change of its own, while the workspace (and the
card's project) is still the one it was for. The actor is the change's
(`recording`/`recordingAs`, an AsyncLocalStorage set by every tasks.ts entry point that takes one): `user`,
`assistant`, `agent:<id>`, or `hive` for Hive's own; a move's cause `user` from the window, `intent` from an agent's
or the Assistant's tools and the API, `derived` for Hive's. **Platform reads are made before the change** ("The one path": slow reads outside `boardWrite`):
`updateTask`, `updateTasks` and `createTask` plan which cards a change may start or submit from the board's columns
(`cardHeads`, no document read) and read their folders with git (`platform/git.ts`: branch, head, merge base with the
target, files, candidate key); a batch's are made before its lock and its cards changed by the locked path, so no read
runs inside a change. A fact whose reads are missing or for another agent records them as not read. A read that fails
never refuses: its field is null and `platform.unknown` names it with what couldn't be read (a project with no options
yet names its ruleset so). A card from before 1.0 (`pre_workflow`, #1218 marks them) gets no facts until it starts,
which clears the mark (Darren, #1119 decision 4) and records the decisions it has then, once. **A fact that fails to
write fails the change whole** (HR4's round 1), a batch's too (`FactWriteError`; `isStorageError`, which the batches'
per-card catches pass on, as SQLite's own errors: part of the card may be written): a card and its facts never
diverge. `boardWrite` then says the change was undone part way when SQLite undid it, whichever error the change passed
on. The window reads a card's facts with
`tasks:facts`. Not yet: None's manifests (P5).

**The adoption** (`workflow/adoption.ts`, SPEC §16.17): `adoptWorkspace` runs after `board:upgrade` and at each open (`WorkspaceService.onOpened`), one at a time per workspace, until board_meta `adoption` says it has handled every card once. Per project: its options through `mutateProjectConfig` (only when project.json has none) and its compiled ruleset; its cards in flight read with git first, then written in one board change, each in a fact-store transaction (`writeAdoption`, deduplicated `adopted`); the rest marked `pre_workflow` (`markPreWorkflow`). Only cards up to board_meta `adoption_upto` (written by the 1.0 group's last step, and by the import of card files) are its. Under the lock each card is checked again (`adoptionCardNow`, and the agent's folder in project.json): a card started or marked meanwhile is skipped, one changed meanwhile counts as `changed` and is classified again by another run (`adoptWorkspace` makes up to three), and the done mark waits until none is left. Like the actions worker, a run belongs to the workspace as it began (`alive`, passed to `boardWrite`).

**The actions worker** (`workflow/actionWorker.ts`, SPEC §16.4.5): `boardStore.onBoardCommitted` tells it of every
change that commits, and it runs the workspace's pending actions (one run at a time per workspace; one asked for
meanwhile runs after) in id order; the workspace's open (`WorkspaceService.onOpened`) runs those a crash or a close left
pending. Each action runs in one of two ways (#1266), as its handler registered (`onAction(kind, fn, once)`):
**delivered** (`wake`, loopWakes.ts; `wakeOnDecision`, decisionWakes.ts), checked still pending in a board change of
its own, then its handler runs, whose delivery carries the action's id (`deliveries.action`, unique: `actionDelivered`
finds one made, in memory or in hive.db, another Hive's too), then it is marked done (failed when the handler throws;
never tried again); **repeatable** (`notify` and `laneNotice`, workflowNotices.ts), leased by one claim
(`lease_owner`, a token per claim, `<process>/<uuid>`, and `lease_until`, 2 min: `take`, a conditional update; renewed
while the handler runs; one another claim holds is left and tried again when its lease passes), its handler giving its
effect to `dispatch(effect)` (`attempts`, counted under the token while the lease holds, then the effect at once: an
uncertain dispatch), completion fenced by the token, a refused dispatch left pending and taken again after a second
(`cooling`), done after two uncertain dispatches; the commit listener starts a run only for what this process could
take, so no run starts runs for nothing; or **claimed** (every kind with
no handler, marked done as the no-op it is: `prepareReviewCopy`, `releaseSlot`, `enqueue`, `pin`, `prepareSlot`,
`endLaneIfDone` until P5 and P7). deliveries.ts saves a host's deliveries by compare-and-set (`saveDeliveryChanges`):
only what the transaction changed, each from its row as the store last read or wrote it (`Store.base`, read with the
record in one SELECT and one read transaction: `readDeliveriesWithBases`); a row another Hive changed since fails the
save (`StaleDeliveries`), and the transaction reads the rows again and plans again on them. The recorder
writes the loop's handoffs as `wake` and `wakeOnDecision` actions with the facts (`loopWakes` in recorder.ts), for a
card in a loop only; `tasks.ts` has no handoff path of its own (`onLoopEvent` is gone). A
run belongs to the workspace as it was when it began (its lifetime and path): once that workspace closes or its window
opens another, the run stops, checked after every wait and inside each board change before the board is touched
(`boardWrite`'s `alive`), and between an action's claim and its handler (a listener of the claim's commit may close
it), so it never opens a closed board again nor writes another workspace's (whose actions are numbered from 1 too),
and no handler runs for a workspace that has gone. A run asked for while one goes on joins it with its own workspace
(HR4's #1215 round 2): when the run's workspace has gone, the newest that asked and is still open takes over what is
left, so a window still open on the board never loses its request to one that switched away.
**`delivered` is gone** (#1266, the 1.0 group's step 10): a wake's delivery carries the action's id in #1211's typed
`deliveries` (unique `action`), and a notice is claimed instead. The runtime's own executor (`Workflow.runActions`, for

Observed facts name the observed fact they follow (`prev`) and (card, kind, prev) is unique, so two Hives observing one
workspace write each transition once, while a later repeat of the same values is still recorded; a writer that loses

## Removing projects

`main/projectRemoval.ts` hides, removes or deletes a project (`project:removalInfo`, `project:remove`, `project:restore`, `project:forget`, `project:takeRemovedData`). Hidden and removed projects are listed by folder name in `workspace.json` (`hiddenProjects`); `WorkspaceService.listProjectPaths()` and `isProjectPath()` leave them out, so everything that lists or names projects (the renderer, the Agent API, the board) stops seeing them without changes of its own. **Remove** packs the project's handovers (found with `projectHandovers()`, as the MCP server finds them) and cards into `<project>/.hive/removed` with a `manifest.json`, archives the cards (`archivedFor: 'project-removed'`) and moves the handovers to the Recycle Bin; **Restore** or the banner (`ProjectInfo.removedData`, from the manifest) unpacks it: the archived originals come back in the workspace they left, copies with new numbers anywhere else (`importCards()` maps the references). **Delete** sends the folder to the Recycle Bin first (watchers paused with `files.suspendWatching()`, resumed if it fails), then worktrees, handovers and cards, reporting what couldn't follow as `warnings`. Every way runs under a per-project guard with the project's starts fenced (`sessions.fenceStarts()`, checked in `assertStartsAllowed`); agents are stopped and the worktrees (`branchStatus(..., { strict: true })`, which throws when git fails), handovers (`projectHandovers(..., { strict: true })`, by exact name in the header) and cards are read again after the stop. `checkedWorktrees()` only lets through folders `git worktree list` gives for the project that don't contain the project or workspace and aren't another project. The dialog is `components/ProjectRemoval.tsx`, with the Settings → Workspace list and the restore banner.

## Tests and checks

- **Unit tests** (`tests/*.test.ts`, Vitest) cover pure logic: migrations, settings resolution, parsers (with CLI transcript fixtures in `tests/fixtures`), prices, kept files and path guards. `electron` resolves to `tests/electron-stub.ts` (vitest alias), so they need no Electron binary.
- **End-to-end suites** (`tests/e2e`, `npm run e2e`) drive the dev build with Playwright `_electron`; see `tests/e2e/README.md`. They need the CLIs and sign-ins, so they run locally, not in CI.
- **Lint**: oxlint with `.oxlintrc.json` (typescript-eslint doesn't support TypeScript 7 yet). `npm run lint` fails on warnings and runs in `npm run build`.
- **CI** (`.github/workflows/ci.yml`): typecheck, lint and unit tests on Windows for every push to `main` and pull request.

## Windows app identity

The installed app uses the app user model ID `com.hive.desktop` (the Start menu and desktop shortcuts carry it, and each window sets it with `setAppDetails`), which gives the taskbar button and notifications the Hive Desktop name and icon. Dev and test builds run as `electron.exe` and use `com.hive.desktop.dev`, registered under `HKCU\Software\Classes\AppUserModelId` as "Hive Desktop Dev". Sharing one ID made Windows show Electron's name and icon for the installed Hive. The displayed name is "Hive Desktop" (`productName`, `shared/appName.ts`; #443), while the folders keep the name Hive had before: the install folder `%LOCALAPPDATA%\Programs\Hive` comes from `executableName` (`Hive.exe`), and main sets the profile folder `%APPDATA%\Hive` itself (`profileFolder()`), since Electron would take `productName` for it. The app ID keeps the installer's uninstall entry, so an update replaces the old install.

## Packaging and updates

`electron-builder.yml` builds an NSIS installer. `@lydell/node-pty` ships prebuilt N-API binaries (no native rebuild), unpacked from the asar archive together with `out/main/hive-mcp.js`, which both CLIs run through Hive's executable with `ELECTRON_RUN_AS_NODE=1`. Its Agent API calls use Node's `http`/`https` (`mcp/agentApiCall.ts`), not `fetch`: undici's 300 s limit on a reply's headers cut longer waits short (#371), so each call has its own deadline instead, a wait's being its longest plus a minute.

`updater.ts` wraps electron-updater. It turns off electron-updater's own auto-download and starts downloads itself, so *Download automatically* and skipped versions are honoured; `autoInstallOnAppQuit` follows *Install updates*. State changes go to the renderer as `update-state` events (`UpdateState`); the status bar item, update dialog, About and Settings (`components/Updates.tsx`) all render from that one state. **Restart and Update** sets a flag and calls the normal `requestQuit()`; `quitNow()` ends with `installNow()` (`quitAndInstall(silent, runAfter)`) instead of `app.quit()`, so the quit dialog, *wait for agents* and transcript backups all still apply. With `HIVE_UPDATE_FEED` (unpackaged builds only) the updater uses a generic feed from a config file in the profile, a separate download cache (`hive-test-updater`, or `HIVE_UPDATE_CACHE`'s `hive-test-updater-<k>` for an e2e lane), and never installs. Releases are published by `scripts/release.mjs` — see `RELEASING.md`.

## Permission mode of a running session

`LiveSessionState.permissionMode` is what the session is really in (Claude Code described here; Codex's comes from `thread_settings_applied` in its rollout and switches through its `/permissions` menu, see Providers). It starts as the launch mode and is updated from two sources: `readFooterMode()` in `sessions.ts` reads Claude Code's footer with `footerMode()` (`shared/claude.ts`) from the session's rendered screen: a `TerminalScreen` (`terminalScreen.ts`, `@xterm/headless`, one screen with no scrollback, resized with the pty through `spawnPty`'s `onResize`, disposed on exit) takes in the output, since Claude Code may redraw only the characters that changed (it does with `NO_COLOR`), which a text tail of the output misses, and `handleHook()` reads `permission_mode` from every hook. `setPermissionMode()` writes Shift+Tab (`ESC [ Z`) and waits up to 1.5 s per press for the footer to change, stopping when the target shows, the mode stops changing or the cycle comes round again. `canSwitchLive()` says which targets need `restartInMode()` instead (stop, wait for exit, `start({ resumeId, permissionMode })`), and `canSwitchModeLive()` (`shared/providers.ts`) wraps it: never to or from the CLI's own setting (`cli-own`, `shared/cliOwnMode.ts`, #1284), where Hive passes no mode flag and so doesn't know the mode; such a session keeps `permissionMode` `cli-own` for its whole launch, and `observeMode()` records what its footer, hooks or status line show only in `modeObserved`, which `modeInEffect()` (`shared/cliOwnMode.ts`) gives to what depends on the mode the CLI is in (`statusInput().reviewed`, `guardCandidate()`, the no-guardrails warnings). The permission mode is left out of the launch signature, so a changed setting doesn't raise "restart to apply"; instead `liveInfo()` calls `noticeModeSetting()`, which compares the effective mode with the one the session was configured with and, once per change, batches a "Switch Now" toast (`session.applyPermissionModes` → `applyModeSettings()`).

## Keyboard shortcuts

`Command.keybinding` in `commands.ts` is the default. `commandKeybinding(id)` resolves the one in force with `resolveKeybinding()`: the selected project's `config.keybindings` (only for categories in `PROJECT_KEYBINDING_CATEGORIES`), then `settings.keybindings`, then the default; `null` means none. Everything that shows or matches shortcuts (palette, menus, tooltips, `matchKeybinding`, the terminal's `isAppShortcut`) goes through it. `eventToKey()` names keys by `KeyboardEvent.code`. The editor (`components/Keybindings.tsx`) records in a capturing keydown listener and sets `recordingKeys` so the global handler in `App.tsx` stands aside. Global overrides are written with `settings:setKeybinding` (the settings deep merge can't delete a key); project ones replace the project's whole `keybindings` object.
