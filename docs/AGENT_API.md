# Hive Agent API

The Agent API lets AI agents, scripts and other tools talk to Hive: list projects and their session status, read and write shared notes, create handovers, send notifications and (optionally) drive sessions.

There are two ways to use it:

1. **The built-in `hive` MCP server** — every session started from Hive gets it automatically. Agents just call the tools. No setup needed.
2. **The HTTP API** — for scripts and anything else. Described below.

> The API only listens on `127.0.0.1` and every request (except `/v1/health`) needs a bearer token. Requests that carry a browser `Origin` header are rejected, so web pages cannot call it.

## Connecting

| | |
|---|---|
| Base URL | `http://127.0.0.1:47821` (port configurable in **Settings → Agent API**) |
| Auth | `Authorization: Bearer <token>` |
| Token | Settings → Agent API → Access token, or `%APPDATA%\Hive\agent-api.json`; for an app that only shows Hive, a **viewer token** (below) |
| Finding Hive | `%APPDATA%\Hive\agent-api-discovery.json`, while the API listens (below) |
| Format | JSON request and response bodies (`Content-Type: application/json`) |

Sessions started from Hive receive these environment variables, so an agent can call the API with no configuration. An agent's token works like the workspace token, except on the task board, where it confines the agent to its own project's cards (see **Task board**):

| Variable | Value |
|---|---|
| `HIVE_API_URL` | Base URL of the API |
| `HIVE_API_TOKEN_FILE` | Path of a JSON file whose `token` is the agent's own bearer token for this launch (not the workspace token in `agent-api.json`): the API knows from it which project's agent is calling, and it stops working when the agent stops. Hive writes a new one at each launch. The token itself is never in the environment (HI-2262: until 1.0, also `HIVE_API_TOKEN`), so read the file in the command that uses it |
| `HIVE_PROJECT` | Name of the project the session belongs to |
| `HIVE_AGENT` | Name of the agent running the session (e.g. `Agent 1`) |
| `HIVE_PROJECT_PATH` | Full path of the project |
| `HIVE_WORKSPACE` | Full path of the workspace |
| `HIVE_PROVIDER` | The provider running the session: `claude-code`, `codex` or `copilot` |
| `HIVE_SESSION_ID` | The session ID, when it is known at launch (Claude Code; Codex chooses its own ID with the first prompt, so its sessions don't get this) |
| `HIVE_RUN_ID` | An ID for this launch of the agent, unique even before the session ID is known |

### Viewer tokens and the discovery file

An app that shows Hive, such as Apiary, reads it with a **viewer token**: read-only, for the whole workspace. The user makes one in **Settings → Agent API → Viewer tokens**, named for its app, and pastes it into the app once; revoking it there refuses its next request and ends its open event stream. Viewer tokens are kept in `%APPDATA%\Hive\agent-api-viewers.json`, never in a project.

- A viewer sees what the workspace token sees: every `GET` route and the event stream (`GET /v1/events`), every project. `GET /v1/status` gives its `caller` as `{ "role": "viewer", "name": "Apiary", "scope": "workspace", "readOnly": true }`.
- **Every other request is refused (403)**, before its body is read or its route looked up: every `POST`, `PUT`, `PATCH` and `DELETE`, including the waits (`POST /v1/tasks/wait`, `POST /v1/agents/wait`) and progress reports. It changes nothing.
- It works while the Agent API is on, as the workspace token does.

The **discovery file**, `agent-api-discovery.json` in Hive's profile (`%APPDATA%\Hive`; the development build's is `%APPDATA%\Hive-Dev`), tells another app where a running Hive's API is, without reading Hive's private `config.json`:

```json
{ "app": "Hive", "version": "0.6.1", "api": 4, "url": "http://127.0.0.1:47821", "port": 47821, "pid": 12345, "startedAt": "2026-10-11T19:30:00.000Z", "note": "…" }
```

It holds **no token**. Hive writes it when the Agent API starts listening (at start, or when it is turned on or its port changes) and removes it when the API is turned off and when Hive quits. A Hive that ended without quitting (a crash) leaves it behind, naming a process that is gone: check with `GET /v1/health` before using it.

### Example (PowerShell)

```powershell
$t = (Get-Content $env:HIVE_API_TOKEN_FILE | ConvertFrom-Json).token
Invoke-RestMethod "$env:HIVE_API_URL/v1/projects" -Headers @{ Authorization = "Bearer $t" }
```

### Example (bash / curl)

```bash
curl -s -H "Authorization: Bearer $(node -p "require(process.env.HIVE_API_TOKEN_FILE).token")" "$HIVE_API_URL/v1/projects"
```

### Errors

Errors return a non-2xx status and `{ "error": "message" }`. The message is in English, whatever language Hive shows: the window shows the same refusal in the user's language, and replies never carry that translation.

| Status | Meaning |
|---|---|
| 400 | Invalid request (missing field, bad JSON, invalid session ID, `agent` needed because the project has several) |
| 401 | Missing or wrong token |
| 403 | Blocked (cross-origin request, a disabled feature such as session input, a change only the user makes, such as archiving a card or putting Done in order, or any request but a GET with a viewer token) |
| 404 | Unknown route, project, card, skill or file, or one outside the caller's scope (another project's card looks missing to its agents) |
| 409 | Conflict with the current state (no workspace open, the project has no agents or already as many as its Maximum agents allows (the workflow option, the user's team size: HI-2001), agent already running or starting or busy, conversation open in another agent, session archived, provider turned off or not installed…) |
| 500 | Unexpected error; details are in Hive's log. A refusal by a rule or limit is never a 500 (HI-1952): one is a fault to report |
| 413 | Body larger than 2 MB, or a skill file larger than 512 KB |

## Several windows

Hive can show several workspaces, each in its own window (**File → New Window**). The API serves all of them:

- A request is for one workspace: the one named by the `X-Hive-Workspace` header (its folder path, URL-encoded) or the `workspace` query parameter (its name or path), else the only one open. A name that two open workspaces share (`C:\Clients\foo` and `D:\Clients\foo`) is refused with 409, listing both paths: name the workspace by its path instead. A path finds the workspace by where its folder is, so another name for it (a junction, an 8.3 short name) works too. The `hive` MCP server sends its session's workspace, so an agent's tools always see its own workspace.
- `{name}` in `/v1/projects/{name}` is a project in the request's workspace. With several windows open and no workspace named, a name is looked up in every open workspace: a name found in two answers **409**; say `<workspace>/<project>` instead (`/` encoded as `%2F` in the path: `/v1/projects/work%2Fapi`).
- Calls about a whole workspace (`/v1/workspace`, shared notes, the task board, skills without a project, MCP servers) answer **400** when several are open and none is named.

## Endpoints

### Health

`GET /v1/health` — no token required.

```json
{ "ok": true, "app": "Hive", "version": "0.1.0" }
```

### Status

`GET /v1/status` — what is running and who you are to it: the app's version, the API's contract version (`api.version`, which goes up when a route or field changes in a way a client would notice), the caller (`role`: `agent` with its `project` and `agent` name, confined to that project; `assistant` with its workspace and `control` level; `viewer`, a read-only viewer token, with its `name`; or `api`, the workspace token), the guidance Hive gives sessions (`guidance.revision`, and each of the request's workspace's Hive skills with who it is for, its content hash, and for a bundled one whether this copy is Hive's or edited and whether a newer version is there to take; just after the workspace opens, read once Hive has brought them up to date, as a launch reads them), each provider's install info, the request's workspace (`null` if several are open and none is named), every open workspace (`workspaces`) and running sessions. Start here before calling anything else.

```json
{
  "app": { "name": "Hive", "version": "0.3.1" },
  "api": { "version": 5 },
  "caller": { "role": "agent", "project": "web", "agent": "Agent 1", "scope": "project" },
  "guidance": { "revision": "3f2a9c41d07be512", "skills": [{ "name": "work-on-card", "audience": "agents", "revision": "9b1c…", "bundled": "same" }] },
  "providers": [
    { "provider": "claude-code", "found": true, "version": "2.1.283", "source": "PATH", "updateAvailable": false, "loggedIn": true },
    { "provider": "codex", "found": true, "version": "0.159.0", "source": "PATH", "updateAvailable": false, "loggedIn": true }
  ],
  "workspace": { "name": "work", "path": "D:\\work" },
  "workspaces": [{ "name": "work", "path": "D:\\work" }],
  "liveSessions": [{ "workspace": "work", "project": "api", "agent": "Agent 1", "provider": "claude-code", "sessionId": "6f1c…", "status": "working" }]
}
```

A skill's `revision` is a hash of its files' content. Hive keeps it between calls and hashes a skill again only once its files have changed (a file written, added, removed or renamed), so polling the status only lists the skills' folders and checks their files' sizes and times, and never gives an outdated revision. A skill's name, description and audience come from the first 64 KB of its `SKILL.md`. Hive uses the first 1000 entries of the workspace's skills folder. A skill whose header can't be read, or whose audience is unknown, has `audience: "none"` and a `problem` (nobody gets it). A skill too big to check (over 64 MB, 2000 files and folders, or folders 12 deep) has an empty `revision` and a `problem` saying which; one that can't be read has an empty `revision`.

A workspace's Hive Assistant is listed in `liveSessions` with `"project": null` and `"agent": "Assistant"`. It isn't a project, so the project endpoints don't reach it.

`GET /v1/docs/agent-api` — this reference as the running Hive shipped it: `{ version, api, content }` (`content` is the Markdown). For a client that needs more than `/v1/status` without guessing routes.

### Workspace

`GET /v1/workspace` — `{ name, path, config }` for the request's workspace, or `null` if no workspace is open. `config` is the workspace's settings, without its MCP servers (HI-2059: `GET /v1/mcp` says where each is added).

`GET /v1/workspaces` — every open workspace (one per window): `[{ name, path }]`.

### Projects

`GET /v1/projects` — every project in the request's workspace; with several windows open and none named, every open workspace's projects. Each has `workspace` (its workspace's name). Projects hidden or removed from Hive (Project → Remove Project…) aren't listed and can't be named. `?view=short` lists each project without its path, ids, sessions and settings: `{ name, workspace, active, branch, agents: [{ name, provider, status, branch, backgroundTasks, watching?, progress? }] }` (`progress`: an open progress run in a few words, "e2e: 12 suites 4/12, about 6 min left").

`GET /v1/projects/{name}` — one project.

```json
{
  "name": "api",
  "path": "D:\\work\\api",
  "active": true,
  "branch": "main",
  "status": "waiting",
  "sessionId": "6f1c…",
  "statusMessage": "Claude needs your permission to use Bash",
  "restartNeeded": false,
  "agents": [
    { "id": "a-3f9c01d2", "name": "Agent 1", "provider": "claude-code", "workflowRole": "builder", "folder": "slot-b", "slot": "slot-b", "branch": "hive/AP/AP-12-retry-uploads", "status": "waiting", "sessionId": "6f1c…", "statusMessage": "Claude needs your permission to use Bash", "reviewing": null, "backgroundTasks": 0, "mcpServers": ["github"], "mcpChoice": "all", "launched": { "guidance": "3f2a9c41d07be512", "skills": { "work-on-card": "9b1c…" } } },
    { "id": "a-7b21e4aa", "name": "Reviewer", "provider": "codex", "workflowRole": "reviewer", "folder": "project", "branch": null, "status": "stopped", "sessionId": null, "statusMessage": null, "reviewing": null, "backgroundTasks": 0, "mcpServers": [], "mcpChoice": "only", "launched": null }
  ],
  "pairs": [{ "builder": "Agent 1", "reviewer": "Reviewer", "lane": "lane-3f2a9c" }],
  "mcp": { "available": ["github", "godot"], "added": ["github"], "on": ["github"] },
  "workflow": { "platform": "git", "preset": "pairAgent", "enforced": true, "options": { "review": "agent", "finish": "agentMerges", "folder": "slots", "preChecks": ["lint"], "commands": { "lint": "npm run lint" }, "…": "…" }, "setBy": { "project": ["review", "finish", "folder", "preChecks", "commands"], "workspace": ["style"] } },
  "settings": { "model": "opus", "effort": "inherit", "permissionMode": "inherit", "chime": "inherit", "mcp": { "added": ["github"] } }
}
```

`pairs` (#1531) are the project's builder and reviewer pairs, so a caller needn't guess who reviews whose work: each running lane's (`reviewer` null and `pool: true` for the reviewer pool, with its `lane`), then a builder and a reviewer in no running lane whose names end in the same number (HB2 and HR2), marked `byName: true`, only where that number gives one reviewer; `[]` when there are none.

`status` is one of `stopped`, `starting`, `ready`, `working`, `waiting`, `background`, `watching`, `finished`, `error`, `signin`. **signin** means its CLI refused the turn because the sign-in has expired (or an API key was refused): it waits for the user to sign in again, its `statusMessage` says so with the CLI's own words, and giving it a prompt is `409`; once the CLI is signed in again it is `ready`. **background** means the agent's turn has ended but background tasks it started (a test run, say) are still running, and it carries on by itself when they end (Claude Code). **watching** means its turn has ended with a card watch running (`POST /v1/tasks/wait` with `wake`): Hive wakes it when a watched card changes; its `statusMessage` is what for ("Waiting for HI-12 → Review": its cards by key, HI-1688), and it has `watching` (`{ cards, column?, changes, label, limitAt }`; short rows: the label). Each agent also has `backgroundTasks`, how many of those are running; Codex agents count theirs but stay `finished`, since Codex isn't told when they end. `reviewing` is an action the CLI's own automatic reviewer is checking while the agent works (Codex in **Approve for me**: "Codex asks to run …"), else null; nobody is asked, so it isn't a reason to tell the user. `provider` is the CLI the agent runs (`claude-code`, `codex` or `copilot`); each agent chooses its own, so a project can mix them. `mcp` is the workspace's MCP servers for the project: `available` (every server in the workspace, which any project can add) and `added` (those added to this project, which run there; HI-2059). `on` is `added`'s old name, kept for 1.0 and deprecated. `settings.mcp` is `{ "added": [...] }`, the same list. `mcpServers` lists the project's MCP servers the agent gets (those `added` to the project; Hive's own `hive` server besides, always): all of them when `mcpChoice` is `all` (the default), or those of them it was given when `only` (its settings' **MCP servers: Only these**; the names chosen are its `mcpServers` in `settings.agents`). `workflow` is the project's workflow options in force (SPEC §16.6; the project's Version Control → Workflow, #1278; card loops and file locks among them since HI-1766): `options` every option's value, `setBy` which options the project, the workspace or Hive's settings set (the others are off, the version control's default), `preset` the preset they started from (null: none chosen), `enforced` whether Settings → Advanced → Workflow rules are enforced is on, and `invalid` (only when present) why the options can't be used, so every rule is off for the project. Agents read them; only the user changes them, and the Hive Assistant within its Control through `PATCH /v1/settings/project.workflow.<option>` (null inherits; a change that contradicts the others, or a value this version doesn't offer yet, is refused with why). It is `null` when the project's version control isn't known. `settings` is the project's configuration, with per-provider overrides under `providers` (its workflow options are `workflow`'s). `unusedWorktrees` (only when there are any) counts the project's git worktrees no agent works in, kept when their agents were removed: `{ "count": 3, "merged": 2 }` (`merged`: merged into the main branch and clean, so the user can remove them safely in the project's Overview). Removing them is the user's: there is no endpoint. A project has up to twelve agents (Settings → Advanced → Agents per project raises it, to 24 at most; adding one past it is refused, saying so), all equal, in the order they were added; a new project has none. The top-level `status`, `sessionId` and `statusMessage` are the first running agent's, and `agents` lists every agent. A running agent's `launched` is what it was given at launch: Hive's guidance revision, the content hash of each Hive skill's copy it reads, and `problems` for any skill it didn't get as asked (`{ "handover": "a folder of the user's in .agents/skills is named hive-handover" }`, or an old copy kept because it was in use), to compare with `GET /v1/status` (an agent launched by an older build, or before a skill changed, shows different ones); `null` when it isn't running. Agent ids are random (`a-…`) and never reused. Endpoints that act on a session take an optional `agent` — its `id` or name. Without one, the project's only agent is used; a project with several answers 400 (say which), one with none 409. In a path (`…/agents/{agent}/…`) it is left empty for that: `GET /v1/projects/alpha/agents//activity` (HI-2258: before, such a call found no route).

`POST /v1/projects/{name}/activate` — mark the project as being worked on.

`POST /v1/projects/{name}/deactivate` — mark it as not being worked on (fails with 409 while a session is running).

### Sessions

`GET /v1/projects/{name}/sessions` — Hive and external sessions for the project, newest first, each with usage and a re-cache estimate. A session a CLI started for another one (a Codex guardian review) has `sub: { parentId, kind }`: it isn't a conversation, and resuming it is refused (`409`).

`POST /v1/projects/{name}/sessions` — start a session. Body (all optional):

```json
{ "resumeId": "6f1c…", "name": "Fix login bug", "agent": "Reviewer" }
```

Omit `resumeId` to start a new session. Returns the live session state (which includes `agentId` and `cwd`, the folder it runs in). Fails with 409 if the agent is already running or starting, if that conversation is already open in another agent, or if it ran in a different folder than the agent works in, or if the project has no agents yet (agents are added in Hive); with 400 if `resumeId` isn't a session ID.

`POST /v1/projects/{name}/stop[?agent=…]` — stop one agent's session, or every running agent of the project when `agent` is omitted.

`GET /v1/projects/{name}/usage[?sessionId=…][&agent=…][&days=false]` — usage for the agent's live session (see above for which agent), else the most recent Hive session, or the one given. `days` breaks it down by local calendar day (`YYYY-MM-DD`): tokens, requests, prompts, compactions and that day's API-equivalent cost (`costUsd`, `costEstimated`); `days=false` leaves it out (it grows with every day the session runs). Session lists include the same.

```json
{
  "sessionId": "6f1c…",
  "provider": "claude-code",
  "title": "Fix login bug",
  "model": "claude-opus-5-5",
  "inputTokens": 1204,
  "outputTokens": 48211,
  "reasoningTokens": 0,
  "cacheWriteTokens": 190233,
  "cacheReadTokens": 2811093,
  "contextTokens": 84211,
  "requests": 57,
  "compactions": [{ "timestamp": "…", "trigger": "auto", "preTokens": 968490, "postTokens": 14813 }],
  "cacheTtlSeconds": 3600,
  "contextWindow": null,
  "costUsd": 4.82,
  "costEstimated": false,
  "lastActivity": "2026-09-28T12:30:00Z"
}
```

`costUsd` is the API-equivalent cost: reported by the provider (Claude Code), or estimated by Hive from its price table (`costEstimated: true`), or `null` for a model without a price. It is not what a subscription plan charges. `reasoningTokens` (Codex) are included in `outputTokens`; `contextWindow` is the model's window when the provider reports it (Codex always; Claude Code while the session is running).

`POST /v1/projects/{name}/input` — type into the running session. **Disabled by default**; enable *Allow sending input to sessions* in Settings → Agent API.

```json
{ "text": "Run the tests and fix any failures", "submit": true, "agent": "Agent 2" }
```

`submit` (default `true`) presses Enter after the text.

`POST /v1/projects/{name}/handover` — hand one agent's work over to another, which may use a different provider (**Hand Over to…** in Hive). Also needs *Allow sending input to sessions*, and Hive's tools in sessions.

```json
{ "from": "Agent 1", "to": "Reviewer", "handover": true }
```

With `handover` (the default), `from` must be running and idle: it is asked to write a handover with `hive_create_handover`, and Hive waits until a new handover for the project exists (not just for the agent to stop). Then `to` starts a new session (or, if it is running and idle, gets the message in its current one) and reads the latest handover. The call returns `{ "ok": true }` at once; the handover can take minutes, and problems are shown as notifications in Hive. The new session's record has `handedOverFrom`, the session whose work it took over. With `to` the same as `from`, the agent carries on in a new conversation: once the handover exists, Hive stops it, starts a new conversation and gives it the handover, which is how a long transcript becomes short again.

### Agents and providers

These read-only calls are open to every caller:

`GET /v1/providers` — the coding-agent providers: whether each is turned on and installed (`enabled`, `installed`, `version`, `problem`), and the `models`, `efforts` and `modes` a connection can use, and whether it can take `context200k`. `models` are the ones the installed CLI reports (else the fallback list in Settings), and `efforts` the effort fallback list: a model may take fewer levels. `connections`: the CLI's connections usable in the caller's workspace (`id`, `name`), in the order of accounts (below). From api.version 12 (HI-2108) there is no `isDefault`: there is no default provider (decision A).

Each agent's `folder` (#1451) is where it works now (its running session's folder, else where a new conversation of its would start), short: a slot's name, `project` for the project folder, `home: <name>` for a retired home, or the path of a 0.9 worktree not migrated yet; `slot` the slot's name while it is in one, and `branch` that slot's line (the card last started there; a carried slot's own branch), else null. No agent has a worktree of its own in 1.0.

`GET /v1/projects/{name}/agents/{agent}/activity[?detail=true]` — what one agent is doing: `folder` and `launchFolder` (where it is now and, when that differs, where a new conversation would start, each `{ at, why }`: `at` named as in the project's agents, `why` one of `session` (its running session is there), `lease` (its card's or lane's slot), `carried` (its carried slot, or its 0.9 worktree) or `project`), `slot` and `branch` as there, `model` and `effort` while it runs (HI-1996: what its CLI reports, else what its launch gave it after the agent's, project's, provider's and connection's choices, else `"default"`: its CLI's own), `status`, `statusMessage`, `retryWaits` (HI-1996, only once this launch has waited for its CLI to retry a rate-limited or failed model request: `{ "waits": 2, "seconds": 460, "latest": { "since": "…", "seconds": 60, "tries": 3, "status": 429 } }`, the waits counted from each one's first try to its end, the one under way to now with `ongoing: true` and its `retryAt` when its CLI says; `status` null when none was named, `network: true` when its service couldn't be reached: a slow round told from a throttled one), `reviewing` and `backgroundTasks`, with `detail=true` `runtime` (the facts its status stands for, or null when it isn't running: `lifecycle` starting, running, signin or stopped; `turn` running, over, unknown or none; `maintenance` compacting or null; `attention` waiting, question or null; `composer` held (a line Hive typed it hasn't taken) or free; `backgroundTasks`; and `silentMinutes` while its state is unknown: a running turn Hive has heard nothing of for a while, with no sign of its end, which counts as busy and isn't given work until the user marks it idle), `transcriptMB` (its conversation's transcript, or null) and `transcriptWarnMB` (the size past which Hive flags it, or null), `currentTask` (the start of its last prompt, 300 characters), `latestReply` (the start of its latest reply, 500 characters), `toolCalls` (how many tool calls since that prompt) and `recentTools` (the last three, each summary up to 100 characters; a Codex code-mode script counts as the calls it made, each named as the same call made directly, when its Codex recorded them), `clipped` (only when a text was cut: `currentTask` and/or `latestReply`, its whole length in characters), `lockedFiles` (relative to its folder), its branch and worktree, its session, `watching` (only while it has a card watch: `{ cards, column?, changes, label, limitAt }`), `progress` (only while it has an open progress run: see Progress below), `userTypedSecondsAgo` (when the user last typed in its terminal), and `inbox` (only when something was left for it: `unread`, `overdue`, and its latest `deliveries`, five or twenty with detail, as `GET …/deliveries` gives them, with `more` when there are older ones). `detail=true` gives the prompt and reply up to 2,000 and 3,000 characters and the last ten tool calls (200 characters each). Neither is the whole conversation: `toolCalls` and `clipped` say what was left out, and the API gives no more of another agent's conversation than this. `{agent}` is the agent's name or id.

`GET /v1/projects/{name}/agents/{agent}/launches/{run}` — `{ "running": true }` while `{run}` (a launch's `HIVE_RUN_ID`, which its shell has) is still that agent's running launch, else `false`: Hive closed under it, or the agent stopped or restarted since (#1008). A test run started in an agent's shell records its launch, and a run waiting for a test slot asks, to say when the holder was left over. Open to every caller, as agents' status is; an agent the project hasn't is `404`.

`POST /v1/agents/wait` — waits until agents stop working (finished, idle, waiting for the user or stopped), or `timeoutSeconds` (5–600, default 300). An agent waiting on its background tasks (`background`) still counts as working, since it carries on when they end; `"ignoreBackground": true` stops waiting at the end of its turn instead. An agent with a card watch (`watching`: its turn has ended and it waits for cards to change, `POST /v1/tasks/wait`) doesn't count as working, and its `statusMessage` is the watch's label ("Waiting for HI-12 → Review"). One that needs the user to sign in again (`signin`) is waiting for the user. An agent just given a task counts as working until its CLI takes it: a prompt Hive typed (`POST …/prompt`) in the last 30 s, or the task it was started with (`…/start`, `…/prompt` with `newConversation`, a new agent's `prompt`), which its CLI takes only after it is ready, so a wait called in between doesn't answer "ready" before the task has begun. Without `agents`, it waits for every busy agent in the workspace. The reply, headers included, comes only when the wait ends: give your HTTP client a longer timeout than the wait (Node's `fetch` stops waiting for headers after 300 s).

With `"wake": true` it is an **agent watch** (#416), for an agent's or the Assistant's own token: it replies at once, `{ "watching": "Waiting for B6 to finish", "limitAt": "…" }` (with `replaced`, the label of a card watch it replaced; with `dropped`, the agents an agent watch it replaced followed and this one doesn't, as `"Name (project)"`, #1530), or `{ "already": ["B6 (hive) is idle: \"…\""] }` and no watch when an agent named isn't working now (which ends the caller's earlier watch too: `replaced` and `dropped` say so there as well). Hive then gives the caller a wake (a delivery it reads with `hive_inbox`, rung by the doorbell, #650) when a watched agent finishes its turn (with `ignoreBackground`, also while its background tasks still run), waits for the user, or stops, naming every agent that did and the start of its latest reply (`[Hive] B6 (hive) finished: "The installer is built…". Your agent watch has ended: carry on …`), or when `limitMinutes` (1–1440, default 120) pass with none. The line is delivered as a card watch's is (only while the caller is idle and the user isn't typing there; Enter again once if its CLI didn't take it), and the caller shows `watching` meanwhile. It is the caller's one watch: a card watch replaces it, and it replaces one. `"cancel": true` ends it. Without `agents` it watches every agent working now (`already` is `["No agent is working"]` when none is), at most 32 (a project's most, 24, and more), never the caller itself (`400`). In both forms, a prompt Hive has just typed into an agent that its CLI hasn't taken yet counts as working, so a wait right after `hive_prompt_agent` waits for that task. A project agent may watch any project's agents (their status is open to it), but its line leaves out the reply of another project's agent.

**The user's replies** (#418): the Hive Assistant's watches (not an agent's) are also woken when the user sends an agent a prompt from its pane, telling the first line (120 characters): an agent watch on that agent (`[Hive] User replied to B1 (hive): "C, the hive cell"…`) and a card watch on a card that agent has or reviews (`[Hive] User replied to B1 on #399: "C, the hive cell"…`); with a name in Settings → General → Your name, that name instead of `User` (`[Hive] Darren replied to B1…`), in one line with whatever else changed. A prompt counts as the user's when its CLI takes it soon after the user's own Enter in that pane, later than any line Hive typed there (a task, a wake). A watch started after a wake counts a reply in between; one already told isn't told again. Each reply is told once, with the cards it concerns, and fitted with the rest within the line's size. Nothing is kept or told with Settings → Assistant → *Tell the Assistant when I reply to an agent* off, also a reply already waiting in a wake (on by default; the Assistant can't change it).

```json
{ "agents": [{ "project": "web", "agent": "Agent 2" }], "timeoutSeconds": 120 }
```

Returns `{ "timedOut": false, "waitedSeconds": 41, "agents": [{ "project": "web", "agent": "Agent 2", "status": "finished", "statusMessage": null, "backgroundTasks": 0 }] }`.

### Connections <a id="connections-preview"></a>

From api.version 12 (HI-2108; HI-2105's design). An **account** is a sign-in Hive keeps (Claude Code, Codex), a server (a base URL and key), or GitHub Copilot's one sign-in on the PC. A **connection** is a named setup on an account (its model, effort, context, permission mode and extra arguments, each absent for the CLI's own), as many per account as wanted. Agents and the Assistant run on a connection, and nothing else decides how they launch: its CLI follows from it. Each workspace chooses which accounts are on; accounts have one order for every CLI, Hive-wide, and connections an order within their account.

`GET /v1/connections` and `GET /v1/connections/{id or name}` — the connections, as the caller may see them, and the accounts they are on. None ever includes a token, a key or where a login is kept.

| Caller | Sees |
|---|---|
| A project agent | `connections`: only those usable in its own workspace (`id`, `name`, `account`: its account's name, `cli`, and the values it sets: `model`, `effort`, `context200k`, `mode`); `accounts`: only those on in its workspace (`id`, `name`, `cli`, `kind`, `signedIn`). Asking after another connection, by id or name, is `404` |
| The workspace token, the Hive Assistant | Every connection, in the order, with the same fields, `extraArgs`, and `usable: false` on one whose account is off in the caller's workspace; every account, with `on` (in the caller's workspace), `order`, `email` and `plan` |

Both lists come with `usage` (HI-2195): for each account the caller sees that has figures or a usage move, `{ "account": "Anthropic-1", "limits": [{ "label": "weekly", "usedPercent": 95, "resetsAt": "2026-11-02T09:00:00.000Z" }], "move": { "percent": 98, "limit": "weekly", "to": "Anthropic-2" } }`: its limits still in their period, and its usage move (`limit`: `weekly`, `fiveHour` or `any`), which the user sets in Settings → Accounts & Connections. At that share its agents move to the matching connection on the other account, once their turn is over and once per limit period, and never back on their own (SPEC §11.2, Usage moves).

`POST /v1/connections` and `PATCH /v1/connections/{id or name}` — the Hive Assistant makes a connection on an account that exists (`account`, its id or name; `name`), or changes one: `name`, `model`, `effort`, `mode`, `context200k` (`"on"`, or `"off"`/`""` for 1M) and `extraArgs`, each `""` or `null` for the CLI's own. Only with Settings → Assistant → Control → Change settings on (`403` otherwise, asked again at the change); a model and effort that don't go together, or a mode the CLI lacks, are `409`; a server account's connections take no effort or context. Accounts (sign-ins, servers, keys) are the user's alone. Each change is listed in the Assistant's panel (`add-connection`, `update-connection`); undo doesn't take it back. Agents running on a changed connection take it when restarted. The reply is the connection as listed.

**An agent's connection** (`connection` on `POST` and `PATCH /v1/projects/{name}/agents…`) is an id, or a name: a name binds only when it is unique among those usable in the workspace (two share it: `409`, use its id; none: `404`). It sets the agent's CLI: another CLI's connection is a change of CLI, refused while the agent runs, and its last conversation is cleared. Left out, a new agent gets the first usable connection in the order (decision A), and a PATCH keeps the saved one; `null` or `""` gives it its CLI's first usable one. Saving checks it is usable in the workspace, in the same write as the rest of the change.

**The old settings are refused** (decision D: removed, not aliased): `provider`, `model`, `effort`, `mode` and `context200k` on these calls are `400`, the reply naming the connections on the account concerned (the agent's, or the one a new agent would go on): "An agent no longer takes model, effort: it runs on a connection, … On Personal: Personal, Personal · High. …". Make or change a connection instead.

**Status:** each agent of `GET /v1/projects/{name}` has `connection` (the one chosen: `{ id, name, problem? }`, where `problem` is `missing` or `off` when it can't be used here, and `name` is null for a project agent then; `null`: none yet), `launchedConnection` (the account its run is on: `{ id, name, note? }`, `note` `offFallback` or `missing` when its connection couldn't be used and its CLI's first usable one runs it, or null) and `switchPending` while it switches at its next safe point. An agent whose connection is removed or on an account off here launches on its CLI's first usable connection and says so (decision H).

### Deliveries and the inbox

Everything Hive has for an agent to read is a **delivery** (#647): a record with an `id` (`m12`, unique in its project), its target agent and conversation, its `kind` (`task`, `rebrief`, `card-event`, `answer`, `handover`, `control`), who it is from, its card, what it says and its `state`. It is saved in the workspace's database (`.hive/hive.db`, #1018: under its project, or the Assistant's) and restored when Hive starts. Every way Hive has into an agent makes one (#649): `hive_message_agent` (`rebrief`), `hive_prompt_agent`, `hive_start_task` and starting an agent with a prompt (`task`), card, lane and agent watches and loop wakes (`card-event`), the user's decisions (`answer`), handovers (`handover`), and the Assistant's mode notices, a lock's go-ahead and the carry-on after a sign-in (`control`).

States: `queued` (waiting to be offered), `offered` (Hive typed its doorbell into the agent's terminal, one short line naming it and what else waited by id, never what they say: `[Hive] New in your inbox: 1 message (m12). Call hive_inbox to read it, act on it, then ack it.`), `received` (the agent read it with `hive_inbox`, `receivedVia: "inbox"`: the only receipt, #650; `receivedVia: "typed"`, its CLI taking a line that carried its whole text, is only in records from before), `acked` (the agent says it acted on it); or ended without that: `cancelled` (by whom), `refused` (its sender may no longer send it: Settings → Assistant → Control turned down, or the Assistant's launch that left it has ended, whose refusal is also in the Assistant's activity list), `expired` (not received within 24 hours, its agent is in another conversation now, or the launch it was for has ended), `stale` (#652: tied to a card round, `card` and `round` on the delivery, and that card has moved on: passed, done or archived, out of Doing and Review, or another review failed; `detail` says which, `#699 passed review`, and the Assistant's activity list records one it sent). `uncertain`: offered when Hive stopped, or when its agent's launch ended before it was read: it may not have reached the agent, and is offered once more, its doorbell saying so (`(m12 again: Hive restarted while offering it, so it may repeat.)`), then left uncertain. A doorbell the agent's CLI took, with the agent idle again without reading it, rings once more, never a third time; once typed, a doorbell is never cleared or taken back (#652), and what it names that has ended meanwhile is simply not given when the agent reads its inbox. One that no longer holds as it was offered (what it was made from changed) is made again when it is read. A `card-event` or `control` delivery is done once received; the other kinds wait for the agent's ack, once it has read them (an id alone, as a doorbell names it, acks nothing). A project agent with no inbox (the Agent API or its built-in hive server off) is given no delivery: every one is refused with the reason ("B1 has no inbox: turn on the Agent API"), never typed instead; only the user's own Start from Hive is typed as their input. One of those not acked 30 minutes after it was made is **overdue** (`overdue: true`), shown in the agent's pane too. A sender's permission is worked out again from the saved sender and the settings at every step; no token is saved.

`POST /v1/inbox` — the calling agent's (or the Assistant's) own inbox: `{ items, unacked }`, `items` being its deliveries not received yet, oldest first, each `{ ids, kind, from, card?, text, at }` (a card's events coalesce into one item, `"3 changes, read the card"`), now received; `unacked` the ids received before and not acked. `{ "ack": ["m12", …] }` acks those (at most 200) and replies `{ acked, unknown, unread }`: only what the caller has read (#650); one not read yet is `unread`, unchanged (read it first); an id that isn't the caller's, or one cancelled, refused or expired, is `unknown`, like one that doesn't exist; acked again, it is still acked; it lists and receives nothing. `{ "ack": [...], "read": true }` (#1531, opt-in) does both in one call: the ack first, by the same rules, then the read: `{ acked, unknown, unread, items, unacked }`, what the read gives received, never acked (an item is acked only by a later call, once acted on); `"read"` is a boolean, and `true` without `ack` is a plain read. A change that couldn't be saved fails (`500`) and isn't made. Other callers get `400`.

`GET /v1/projects/{name}/agents/{agent}/deliveries[?limit=n]` — an agent's deliveries: `{ unread, overdue, deliveries, more? }`, the newest `limit` (20 by default, at most 200), each `{ id, kind, from, card?, text, state, created, offered?, received?, receivedVia?, acked?, ended?, detail?, overdue? }` (`text` the start of what it says, 300 characters). A project agent reads its own project's only.

With the Agent API turned off, the server still runs and answers the Assistant alone; other callers get `403`.

The changes below are the Assistant's only: other callers get `403`.

### Settings

Hive's settings, as Settings and Project Settings describe them (one catalog of every setting: `src/shared/settingsCatalog.ts`). Anyone with a token can read them; only the Hive Assistant changes them.

`GET /v1/settings` — every setting a row: `id`, `title`, `value` (as shown: `on`/`off`, a number, `inherit`, `(empty)`), `default` (only when the value differs), `desc` (its first sentence, cut at a word within 60 characters) and `readOnly: true` for those only the user changes. `query` keeps those whose id, place in Settings or text has every word; `scope` one of `app`, `provider`, `workspace` (no value settings yet) or `project`; `project=<name>` adds that project's own settings (ids `project.…`, and `project.<provider>.…`), which need it. Buttons, statuses and lists (Reset, the Agent API's token, Hidden projects…) aren't settings and aren't listed.

`GET /v1/settings/{id}` — one in full: `path` ("Settings → Sessions → Warn when a transcript is over"), `shownAs` (where the user sees it, in the language Hive shows, only when that isn't English: the rest stays English), `scope`, `value`, `default`, `takes` (its range, options or type), `desc`, `tip`, `helps` (when it is worth suggesting), `restart` (when a change applies, if not at once), `readOnly` (why the Assistant can't change it), `docs` (the user guide's heading). A table's value is its JSON (cut at 3,000 characters); in the listing it is its size. The Assistant's own settings with each provider are entries of their own (`assistant.<provider>.model`, `.effort`, `.permissionMode`, `.extraArgs`, `.use200kContext`): read-only to it. A project's setting takes `?project=<name>`.

`PATCH /v1/settings/{id}` `{ "value", "project"? }` — the Hive Assistant only (others: `403`), and only with **Settings → Assistant → Control → Change settings** on (`403` otherwise, at once when the user turns it off). The value is checked as Settings checks it (`400` with the range or options), and the change is made as Settings makes it. Never for a sensitive setting (`403`): permission modes, the Agent API, what Hive runs (CLI paths, extra arguments, a project's setup command, background sessions, pre-release updates) and the Assistant's own settings (Control above all). A project's number or list takes `null` to inherit Hive's. An effort level must be one the effort picker offers for the model that would run (`takes` lists them), or `""` (the default; `inherit` for a project). Tables take JSON: `board.colors` an object of column → `#rrggbb` (only those named change), `<provider>.prices` the whole table of model → `{input, cachedInput, output, cacheWrite?}`, `<provider>.modelFallback` and `.effortFallback` the whole list of `{value, label}` (`older` for models); `null` puts back Hive's (for prices, as **Reset to defaults** does: the shipped models removed from the table come back too, and the change lists them). Shortcuts are read-only for now. The permission, and that the request's Assistant session (its launch's token) is still the running one, are checked again at the moment of the change, under the project's lock for a project's setting (for Revert, also that the value is still what the change set). The reply's `changed` says whether anything changed; for a table, `old` and `new` are the entries that changed. Replies with `old` and `new` (as shown) and `restart` when it applies later. It counts as one of the Assistant's changes, and its panel lists it with old → new and a **Revert** button (which the user, not the API, uses).

### Undoing the Assistant's changes

From api.version 8 (#1282, SPEC §16.14). Hive keeps each change the Hive Assistant makes through this API for 7 days, grouped by the user's message it came from: a card's fields (title, description, labels, blocked, links, agent, column, project) and the cards it made, a lane it started or changed, an agent's settings, a Hive setting, an agent it started, and a template it loaded (the project's agents and layout, and its workflow options: from api.version 11, HI-1502). It keeps them with what each replaced. Prompts, messages and comments, and what can't be taken back (a project made, an agent added), are listed with why.

`GET /v1/assistant/changes` — the Assistant only (others: `403`): its newest 10 messages' changes, newest first: `[{ "group", "at", "changes": [{ "id", "what", "card"?, "fields": ["labels"], "final"?: "why it can't be undone", "undone"?: true }] }]`.

`POST /v1/assistant/undo` `{ "change": "<id>" }` or `{ "group": "<id>" | "latest" }` — the Assistant undoes its own change, or every change of a message's, newest first. `latest` is its newest message with a change left to undo. A change of its own (Control agents), listed in its panel (`undo`).
- Each field goes back to what the change replaced only while it still holds what the change wrote, checked at the moment of the write. One that someone has changed since is left as it is, never overwritten.
- A card it made is archived, unless someone else has changed it since.
- A column move goes back through the card's rules, as a move with the override reason `undo`.
- A lane it started is abandoned; a lane's list, reviewer, rounds, wait or name go back.
- An agent it started is stopped only while the launch it started still runs (what it did stays).
- A template it loaded: the project's agents (with their ids, so their conversations come back) and layout go back only while they are exactly as the load left them, none of them runs and no other project's agent has one of their names now (then it fails, said, to try again); its workflow options only while they are those it saved. The replaced agents' cards and lanes stay as the load left them.
- A Hive setting goes back only while Change settings is on. A provider's removed models go back only if they too are unchanged.
- Its control level and its launch are checked again at each write: turned down to Look and advise, or its session ended, partway through a message's changes, the undo stops there and is refused, the changes undone so far kept.
- A card's decision, comment or place in its column can't be undone: those changes are listed with why. So is every change of its that changed nothing undo puts back (an intent's facts, withdrawn messages): none is left out.
- A card's project goes back with its agent, both or neither, only while its agent and review are as the move left them; a move back never stops a review started since. A provider goes back with everything a provider change resets, never while the agent runs.
- A change is marked undone only when every field went back or was skipped for good; one that failed (`failed`) can be undone again.
- An id that isn't one of its changes (they are its own only) is `404`, as is a message with none.

Replies `{ "results": [{ "change", "what", "card"?, "undone": ["labels"], "skipped": [{ "field", "why": "changed" | "gone" | "ended" | "failed", "error"? }], "final"?, "already"?: true }] }`.

### Shared notes

Shared notes live in the workspace's `.hive/shared` folder. Paths are relative to that folder and cannot escape it.

`GET /v1/shared` — the notes tree.

`GET /v1/shared/file?path=handovers/2026-09-28-api-auth.md` — `{ path, content, revision }`. The revision is a short hash of the note's text.

`GET /v1/shared/handovers?project=api` — the project's handovers, newest first, as `[{ path, modified }]` (paths as `/v1/shared/file` takes them; which handovers are a project's is below, under the hive tools). Without `project`, every handover. An unknown project is `404`.

`PUT /v1/shared/file?path=conventions.md` — create or replace a note:

```json
{ "content": "# Conventions\n…", "append": false, "expectedRevision": "3f9a0c1d2e4b" }
```

Set `"append": true` to add to the end of an existing note. `expectedRevision` is optional: with it, the note is written only if it is still at that revision (checked and written under one lock, so two writers that read the same text can't both pass); otherwise nothing is written and the reply is `409` with `{ error, revision }`, the note's current revision (`null` if it no longer exists): read it again, merge, and retry. Without it, the note is written as before; given but not a revision (empty, `null`, not a string), it is refused with `400` and nothing is written. The reply is `{ ok, path, revision }`, the note's new revision.

`POST /v1/shared/handovers` — write a dated handover note into `shared/handovers/`:

```json
{ "project": "api", "title": "Auth refactor", "content": "## State\n…\n## Next steps\n…" }
```

Returns `{ ok: true, path }`. Hive shows a notification with a link to the note. Hive writes the note's header (`# <title>`, project and date, in local time with UTC in brackets). An agent's `hive_create_handover` also passes `agent` (its id) and `agentProject`, and the Hive Assistant is known by its token; the header then adds `- **Author:** <agent> (<CLI>)` (or `Assistant`) and `- **Session:** <id>`, the conversation it was written in. The Assistant's first handover in a workspace whose journal is off also returns `suggest`, the line asking it to suggest the journal to the user once (#1032); never again for that workspace.

### Documents by section

For long plans and notes (#817): a Markdown document's outline, then only the sections needed. `path` is a project file, relative to the project (`docs/PLAN.md`), or a shared note as `shared:<path>` (`shared:plans/i18n.md`).

`GET /v1/docs/outline?path=docs/PLAN.md&project=api` — `{ path, size, headings: [{ level, text, slug, line, size }] }`: every heading in order, with its level (1–6), its text as shown, its slug, its line (from 1) and its section's size in characters (the heading to the next heading of its level or higher, so subsections included). `size` is the document's.

`GET /v1/docs/section?path=docs/PLAN.md&heading=core-contracts&project=api` — `{ path, heading, content }`: that section's text, from its heading line, with its subsections. Without `heading`, the whole document: `{ path, size, content }` (over 30,000 characters with headings, its text before them and its top headings as `subsections`, `partial: true`). `heading` is `#` and a slug (`#core-contracts`: exactly that section; of two "Setup" headings, `#setup` is the first and `#setup-1` the second), a heading's text (any case, with or without its `#` marks and a space) or a slug without `#`. A section over 30,000 characters that has subsections comes as `{ path, heading, content, subsections, partial: true }`: its text before its first subsection, and its direct subsections' headings; `&full=true` gives all of it. Text several sections share is `409` with `{ error, matches }` (each with its own slug, to ask for as `#<slug>`); an unknown one is `404` with `{ error, closest }` (up to five headings). Neither ever replies with an empty section.

**Headings and slugs.** Headings are ATX headings (`#` to `######`, up to three spaces in) outside fenced code (```` ``` ```` and `~~~`) and front matter (a `---` block at the very top); setext headings (underlined with `===` or `---`) aren't counted. A slug follows GitHub's rule: the heading's text as shown (links as their words, code and emphasis marks dropped), lower case, every character that isn't a letter, a digit, a space, a hyphen or an underscore removed, each space a hyphen; a slug used before in the document gets `-1`, `-2`… in order (the second "Setup" is `setup-1`).

**Which files.** Markdown only (`.md`, `.markdown`, `.mdx`), up to 4 MB, inside the project folder (or the shared notes), never through a link or junction out of it, and never in `.hive` (read shared notes as `shared:`) or `.git`; anything else is `400`, a missing file `404`. `project` names the project; a project agent's token may leave it out, and reads its own project only (another project's is `403`, as with its sessions), in the folder it works in now (#1451: its running session's, its slot, else where it would start). Other callers read the project folder's copy, and so does a project agent with `&from=project` (the hive tools' `from: "project"`): the copy a card's Read first references are shown and sized from (#818). For `shared:` paths, the notes are the request's workspace's, as for `/v1/shared/file`: an agent's or the Assistant's own, whatever the request names; the workspace token names one with `?workspace=` (or `X-Hive-Workspace`) when several are open.

### Task board

The workspace's board: cards in six columns, `hold` (On Hold), `todo`, `doing`, `review`, `passed` and `done`, kept in the workspace's board database (`.hive/hive.db`, #1017; the cards' JSON is the same as when they were files). `hold` is parked work, `passed` is work whose review passed and waits to be merged, and `done` means merged. Callers can read and change cards and move them between the columns, `done` included; each move is in the card's history with who made it. Putting a card in `hold` (moving it there, or creating it there) is the user's, the Assistant's and the workspace token's: a project agent's own token gets `403`; it may move a card out of `hold`. Agents are asked (their session contract and the skills) to move a card they were given to `doing` before they start on it (also one back from `review`, `passed` or `done` with more work), to move finished work to `review` with a comment saying what they did (also a card that was in `passed` or `done`), as a reviewer to move a card that passes to `passed` with the verdict, to move a card to `done` once its work is merged or when the user asks, and to leave `hold` to the user. Creating a card in `done` and putting `done` in order are the user's (`403`). Archived cards can't be changed (`403`), and archiving and deleting are only in Hive: a `PATCH` with `archived` is refused (`403`), and there is no call to archive cards in bulk.

**Card keys** (#1219, #704). Each project has a key of 2–4 letters (`HI`, `AM`), and its cards are numbered in it: `HI-12`. A card's JSON has `key` (absent for a card with none: one about the workspace, a project with no key yet). A card's number (`number`, the `#N` everywhere before 1.0) stays its id and a permanent alias, and `{n}` and the hive tools' `number` still take it as a bare number (HI-1661: never shown, only taken); give its key, in any case (`HI-12`, `hi-12`), an old key of its project, a key it had in another project before it moved, or `#12`. So do `blockedBy`, `links`, `before`, a reorder's `cards`, `POST /v1/tasks/wait`'s `cards`, a lane's `cards` and the merge slot's `cards`. A key no card has is `404` (`Unknown card HI-99`), and so is, for a project agent, another project's key: it can't tell whether that card exists. So does a progress run's `card` (`POST /v1/progress`, `hive-progress --card HI-12`), and a batch's `numbers`, where a key or `#N` no card has is refused as that card and the others change (the batch is checked whole first: over 100 cards, or a field it can't set, refuses it all before any key is looked up). Existing cards keep their number in their project (`#1061` is `HI-1061`); a new card takes its project's next number; a card moved to another project takes that project's next, its old key kept as an alias (and its old number again if it comes back). Replies, errors, wakes, the inbox and the doorbell name a card by its key alone, `HI-1230` (HI-1661: never with its number; `#1240` only for a card with no key, and for another project's card to a project agent). Replies whose text the hive tools word from their JSON (a listing's `blockedBy`, a reorder, a batch, a wait, the inbox, the merge slot, a lane (each lane in a listing), a message tied to a card) carry `names`: each card's name by its number. Keys are given by Hive (suggested from the folder's name) and changed by the user in Project Settings, the old key kept as an alias.

**Who sees what.** The workspace token (scripts) and the Hive Assistant see and change the whole board, as the user does. A project agent, calling with its own token (in `HIVE_API_TOKEN_FILE`), sees and changes only its project's cards; who it is comes from the token alone, never from the request:

- `GET /v1/tasks` lists its project's cards; asking for another project (`?project=`) is `403`.
- Another project's card, or one with no project, answers as if it didn't exist: reading, changing, commenting on or moving it is `404` (`Unknown task #63`), and naming it in `blockedBy`, `links`, `before` or a reorder is `400` (`there is no card #63`).
- A new card is its project's (also when `project` is left out); another project, or `""`, is `403`, and so is changing a card's `project`.
- A card of its own that waits for or links to another project's card shows that card as a number, listed in `elsewhere`; changing `blockedBy` or `links` keeps those.
- `position` and a reorder place its cards among its project's cards in the column (the top or bottom of those); other projects' cards keep their places. The place a short reply gives (`3rd of 5`) counts its project's cards.
- Another project's agents' conversations hold that project's cards (a card started on an agent is its prompt), so for another project, `GET /v1/projects/{name}/agents/{agent}/activity`, `GET /v1/projects/{name}/sessions`, and `POST /v1/projects/{name}/input` are `403`, and the event stream (`/v1/events`) leaves out their session events. Their status (`/v1/projects`, `/v1/projects/{name}`, `/v1/agents/wait`) stays open; an agent watch's line leaves out what another project's agent said.

An agent runs as the user, so it could read the workspace token from disk: this keeps agents to their own project's work rather than containing a hostile one.

`GET /v1/tasks[?project=web][&column=review][&archived=true][&q=words]` — the cards on the board in order (by column, then position), or the archived ones. `q` (from `api.version` 7, #1237) is the board's search: the cards whose title, description, project, agent's name or labels contain it (any case), or a card by its number (`%2312`) or key (`HI-12`, `HI-` for a project's); words of three characters or more go through the board's full-text index, so only the cards found are read. `GET /v1/tasks/{n}/attachments/{name}` (HI-1751) — one of the card's attachments (`attachments` in its JSON), by its `name` or its file's name, read through Hive: for text (UTF-8), a page of it, `{ "name", "file", "size", "kind": "text", "offset", "content", "next"? }`, up to 64 KB from the byte `offset` (`?offset=`, a whole number from 0 to its size; `400` otherwise), each page ending on a whole character, `next` the offset of the page after (absent at its end), so the pages' contents joined are its text (a byte-order mark left out). Who may read it is as for the card (`404` for a card a project agent can't see, as for a missing one). The hive tools' `hive_read_task` gives it with `latestComment: true`.

`GET /v1/tasks/{n}/facts[?view=full]` — the card's facts (1.0: what happened to its work, each recorded by Hive or observed in its folder, oldest first): `{ "number": 12, "stage": "review", "preWorkflow"?: true, "facts": [{ "seq": 4, "kind": "Submitted", "at": "…", "actor": "agent:a-3f9c01d2", "what": "3f9c01d, round 2, 3 files" }] }`. `?summary=true` (#532), on this and on `GET /v1/tasks/{n}`: each comment as its **summary**, its first line that isn't blank (at most 300 characters), with `"length"`, the whole comment's in characters, when there is more: `{ "at": "…", "by": "HR1 (hive)", "text": "Round 1: FAILED: 2 findings: …", "length": 4210 }`; each of `forYou`'s `text` the same way. Reports and verdicts lead with a one-line summary, so a reader that needs only the gist reads that and asks for the whole when it acts on it. `hive_read_task` gives it with `summary: true`.

`POST /v1/tasks` — add a card. `title` is required; `description`, `project`, `agent` (name or id, in that project), `column` (not `done`; not `hold` for a project agent), `labels`, `blocked` (a reason), `blockedBy` and `links` (card numbers) and `context` are optional. `context` (#818) is the doc sections the card's agent reads first: up to ten references by file and heading, never a line number (`docs/PLAN.md#setup`, `shared:plans/notes.md#open-questions`, or a whole Markdown file), as `/v1/docs/section` takes them; anything else is `400`. When the card starts, its prompt lists them with each section's size (`Read these first: …`), not their text. Created in `doing` by an agent without `agent`, it is given to that agent. `kind` (1.0, #1277) is `code` (the default) or `no-code` (work with no commits: a decision, a write-up, a trial; it is submitted with a summary); from a project agent or the workspace token `no-code` is only proposed: the card stays `code` with `kindProposed: "no-code"` until the user or the Assistant confirms it. `skipReview` (1.0, #1625) is the user's reason the card skips review (its submission then finishes it: a no-code card is Done, a code card goes on to its merge, the merge checks kept), only where its rules review (else `409`); the Assistant's needs the reason (empty: `409`); from a project agent or the workspace token, with its own reason, it is only proposed (`reviewSkipProposed`). `lane` (1.0, HI-2167) puts the new card on a lane as it is made, so nobody guesses its key: a builder's name or id puts it last on that builder's running lane (no running lane: `laneRefused`), and `{ "builder", "reviewer", "brief", "name", "position" }` puts it on the builder's running lane, or starts one with it when there is none; `position` is `last` (the default) or `next` (before the lane's first card still in Todo). **Long titles** (1.0, HI-1872). A card title is short (about 70 characters: the outcome or the problem; the detail in the description). `POST /v1/tasks`, and `PATCH /v1/tasks/{n}` with `title`, never refuse a long one (up to 200 characters, as before): past Settings → Advanced → Suggest a shorter title past (80 characters by default, 0 off), the reply has `nudge`, one line: `"Titles over 80 characters are cut in git and on the board: consider a shorter one (the detail belongs in the description)."`, which the hive tools add to their reply as its last line. A title of any length naming what belongs in the description gets it too (HI-2061): a path (`src/main/foo.ts`, `C:\Users\…`), a file name (`AGENTS.md`), a card (`#12`, or a key of one of the workspace's projects, `HI-12`) or a measurement (`300 s`, `20 MB`, `95 %`), at most three named as written: `"A title says the outcome or the problem in words: retitle it without \"src/main/foo.ts\" and \"300 s\" (hive_update_task with title), keeping them in the description."` (HI-2260), after the length's sentence on the same line when both apply. The length's setting at 0 turns off only the length's. The user's own titles get neither.

**Card attachments** (1.0, HI-1700). `POST /v1/tasks`, `PATCH /v1/tasks/{n}` and `POST /v1/tasks/{n}/comments` take `attachments`: local file paths to keep with the card, at most 10 and 100 MB in all, each at most Settings → Advanced → Card attachments: largest file (25 MB). Each is copied in (the same file is kept once per card) and linked in the change's comment, or at the end of the card's description without one, as `![name](attachment:<id>)`; the whole change is refused (`400`), nothing written, when one isn't a file, is too large, or comes from where the caller may not attach: a project agent only from its project's folder, slots and review copies and the system temp folder (never another project's, nor any `.hive` but its own `attachments`); the Assistant and the workspace token from the workspace, every project's folders, the Assistant's home and the temp folder. `PATCH` with `attachments` and `project` is `400` (move the card first). A card's JSON (`GET /v1/tasks/{n}`) has `attachments` when it keeps any, newest first: `{ path, name, size, by, at, from, missing? }` (`from`: "comment by HR4 at …", "description", "attached from a session"), and its description's and comments' links to them read as those paths.

`PATCH /v1/tasks/{n}` — change a card and/or comment on it: any of `title`, `description`, `project` (a card that changes project always leaves its agent, and the history says whose it was; naming an `agent` in the same change is `400`: give it to one of the new project's agents in a change of its own), `agent` (empty takes it from its agent), `column`, `position` (`top` or `bottom` of its column) or `before` (the card it goes in front of, which has to be in the column the card ends up in; `null` the end), `labels` (replaces its labels), `addLabels` and `removeLabels` (#1131: lists of labels added where missing, at the end, and taken off where present, its other labels kept; one there already or missing changes nothing, and the history says only what was added or removed; with `labels` in the same change, or a label in both, it is `400`), `blocked` (empty clears it), `blockedBy`, `links`, `context` (replaces the list; `[]` clears it), `decision` (records a decision the user made about the card: it is attributed to the user, with the caller as who recorded it; only the user changes or removes decisions, in Hive), `answers` (HI-1932, with `decision` only, the Assistant's or the user's: up to 20 of the card's open requests, by their ids in its `forYou`, that the user's decision answers; they are closed with it in one write, each answered by the decision (its id and who recorded it kept with the answer), their askers woken, and a line each in the card's history; only a question can be: an approval, Hive's own requests and the round limit's choice are `400`, as is a request not open, any other field or a comment in the same change, or no decision; a project agent's is `403`; any of these, and nothing is written, the decision included), and `comment`. A card's `decisions` come first in its JSON (absent when it has none). A project agent's replies to any call carry an `X-Hive-Notice` header (URL-encoded) when a card it works on (in `doing`, its agent), reviews, or reviewed before and is back in `review` (or such a card when the call began, unless the call read it: moving a card to `review` still hears of one) has a decision recorded by someone else, or changed by the user, since it last read the card in full (`GET /v1/tasks/{n}`), else since its work began or its last verdict on it: "[Hive] #12 has 1 new decision since you last read it: …". The hive tools add it to their reply as a last line. When an agent moves a card into `doing` from another column without `agent`, it is given to that agent (the history says "Given to …"), also when another agent had it; a card already in `doing` keeps its agent. An explicit `agent`, including empty, wins, and the Assistant and other callers give it to nobody. A project agent (its own token) can't move a card that is in `doing` with a different agent to `review` or `done`: `409` ("… is in Doing with Alma, who is working on it: newer work is in progress …"), checked against the card as it was, so an `agent` in the same change doesn't get round it. Its own agent, the Assistant and the workspace token can.

**A card's kind (1.0, #1277).** `PATCH` takes `confirmKind` (`true`: the proposed kind becomes the card's; `false`: it stays `code`), the user's or the Assistant's, `409` when nothing proposes one, and `kind` (`code` or `no-code`), a change after the card was made: an exception to its rules, the Assistant's only with `override: { "reason" }` (else `409`), recorded as an `Override` fact (`card.kind`). Project agents and the workspace token get `403` for either.

**Review: Skip (1.0, #1625).** `PATCH` takes `skipReview`: the user's reason, in their words (the Assistant's; it answers an open `reviewSkipProposed` too, recorded with the Assistant's reason, never the agent's), or `false` to review it after all (and keep the review an agent proposed to skip); anything else is `400`, an empty reason `409`. Decided before the card is submitted: in Review or past it, `409` saying the way on (in Review, the user's override of the move). Project agents and the workspace token get `403`. The card adds `reviewSkipped` (`{ "by": "user" | "assistant", "reason": "…" }`) while it skips review, and `reviewSkipProposed` (the agent's reason) while a proposal is open, after `kind`.

**Moves through the workflow rules (1.0, #1265).** With Settings → Advanced → *Workflow rules are enforced* on (the default), the Assistant's `column` moves of a card from 1.0 go through the card's workflow rules (its project's options, SPEC §16.7): a move to a column its rules have runs what the move stands for (into `doing`, the card's start; into `review`, a submission of its revision) and records it in the card's facts (`GET /v1/tasks/{n}/facts`). A move that would skip a rule (into `done` with no review or merge, say) needs `override`: `{ "reason": "why" }` (the reason not empty), recorded on the card with the rules it skips (an `Override` fact); without it the move is refused with `409` and a refusal: `{ "error", "refused": true, "rule": "move.needsOverride", "message", "next", "change"?, "override": "the user or the Assistant" }` (three English sentences: what was refused, the next step, where the rule is changed), and a `Refused` fact. Project agents and the workspace token (scripts) can't pass `override` (`403`): a project agent's moves are its intents (below), and scripts' moves keep the checks from before 1.0. A move to a column the card's rules don't have (`review` in a project with no review) is made as before 1.0. `POST /v1/tasks/batch` takes the same `override` for every card (with `column`); a card refused is listed with its refusal's message, `rule`, `next` and `change` (HI-2238), the others change.

**Nobody on it (1.0, HI-2062).** The Assistant's move of a card into `doing` that would leave it with nobody on it (no agent on it, none named, or `agent` empty) is refused with `409`, `"rule": "move.doingNobody"`, whose `next` names the user's three choices: nobody on it (the move again with `override` and the user's reason, recorded as an `Override` fact naming `move.doingNobody`), an agent on it (`agent`), or an agent started on it (`hive_start_task`). Its `message` also names any other rule the move skips, which the same reason overrides. It applies with the workflow rules off too, and to each card of `POST /v1/tasks/batch`. `POST /v1/tasks` with `column: "doing"` and no `agent` is refused with `409` (make it in `todo`, then move it). The user's and project agents' moves aren't refused for it.

**A project agent's moves and reviews, for one transition** (1.0, #1268, SPEC §16.17; until the skills move to the card intents, below, and these are retired). With the rules enforced, a project agent's `column` move of a card from 1.0 (with its own token) is the intent it stands for, through the same rules: `doing` is the card's **start** (the card given to the agent, or to the one `agent` names), `review` its **submit** (the `comment` its summary), `passed` a passing **verdict** on its latest submission (its review started first), `done` **report merge**, `todo` **put back** (the `comment` its why). `review`: `"start"` is **start review** of the latest submission, `"passed"` and `"failed"` a **verdict** on it with the `comment` (a failed card goes back to `doing`, its builder's, as the verdict moves it; a `column` beside a verdict is left to the verdict). The short reply adds a line naming the tool to use next time (`As submit: next time call hive_submit`); a move its rules refuse is `409` with that intent's refusal (as above) and a `Refused` fact, and nothing of the change is saved. The rest of the change (labels, blocked, a decision…) goes with the intent's first write, the comment with the write that records it. A batch translates each card's move; a card a project agent creates in `doing`, `review` or `passed` is made in `todo` and moved by its intent in the same change, refused whole (in a column its rules don't have, it is made there, as before). Every new cycle is a start, under its rules: `doing` from `todo`, from `done` (the card reopened), from `hold` when it never started, and with `agent` naming another agent (started for it). Each translated change is one write: refused or failing part way, nothing of it is saved. As before 1.0: a column the card's rules don't have (`review` in a project with no review), a review there, any move of a card in such a column or in `hold` while being worked on, a move back into `doing` from `review` or `passed` (fixes, the same cycle), a move to the column a card is in (a failed card from before 1.0 returned to `review` is its submission), another agent's card in `doing` moved on (`409`), cards from before 1.0 until they start, and every move with the rules off.

Reviewing a card: `review` in the body. `"start"` marks the card as being reviewed by the calling agent (it has to be in `review`, and `review: "start"` goes on its own, without `column` or `agent`): the card keeps its agent and gains `review` (`{ "agent", "agentName", "since" }`). `"passed"` or `"failed"` ends it, with the verdict as the `comment`; `"passed"` with `"column": "passed"` moves it to Passed as well (what reviewers do), or with `"column": "done"` to Done; `"failed"` sends the card back to `doing`, still its builder's (who holds it again for its fixes), as `POST /v1/tasks/{ref}/verdict` with `"pass": false` does, whatever the workflow rules (HI-1946); `"failed"` with any column but `doing` is `400`, and nothing of it is saved. Only a project agent, with its own token, reviews its project's cards (`403` for others); another agent's `start` while one is reviewing is `400`, naming it, and only the reviewer gives the verdict, while its review is going: a verdict after the review ended (the card left `review`, or the reviewer's session ended) is `400`, so start a new review first. The review stops when the card leaves `review` or its project, and when the reviewer's session ends or it is removed. A card failed before HI-1946, when a `"failed"` verdict left it in `review`, may still be there: its own agent, with its own token, sending `"column": "review"` returns it for review (history "Returned for review, round N"), which wakes a wait for it to move into `review`; once per failed verdict, and any other move to the column a card is in is no change. Card views add `reviewStalled` while a review goes on but its reviewer has gone or isn't running; `?view=short` rows add `reviewing` (`{ "name", "stalled"? }`).

Placing a card with `position` or `before` adds a line to its history when it moves it. A `before` card in another column, or both `position` and `before`, is `400`; placing a card in Done is `403` (the order of Done is the user's).

`GET /v1/tasks` returns cards in board order: by column, then top first. That order is their priority.

`POST /v1/tasks/reorder` — put cards in order: `column` (`hold`, `todo`, `doing`, `review` or `passed`) and `cards`, card numbers highest priority first. The listed cards go to the top of the column in that order; the column's other cards keep their order below them. Every listed card has to be in that column already (move it first with `PATCH`), or nothing changes and the answer is `400`; `done` is `403`. Returns the column's cards in their new order.

```json
{ "column": "todo", "cards": [14, 9, 12] }
```

`POST /v1/tasks/batch` — change up to 100 cards with one call: `numbers` (their card numbers) and the fields every one of them gets, with the meaning each has on `PATCH`: `column`, `position` (`top` or `bottom`), `blocked`, `labels`, `addLabels`, `removeLabels` or `agent`. To tag cards, use `addLabels` (each card keeps its own labels); `labels` replaces every card's. `labels` with `addLabels` or `removeLabels` is `400` before any card changes. A title, comment, decision or link goes on `PATCH` for its own card; any other field here is `400`. An empty list, more than 100 cards, or a card listed twice is `400`, and nothing changes.

Each card is changed as `PATCH` would change it: under its own lock, authorised against the card as it is then, with its own history line. A card that can't be changed is refused and left as it was, and the other cards still change: an unknown card, or another project's (both answered as missing), an archived one, one in Doing with another agent, one an agent may not put On Hold. So a batch is not all or nothing: each card is. `position` applies to each card in turn, so the last listed ends at the top; to set an order, use `POST /v1/tasks/reorder`.

For the Assistant, each card is listed in the Assistant's panel on its own. Each card is checked again just before it is saved, after its last read and under its lock: if the control level was turned down, or the Assistant's session replaced, while the batch was working on it, that card and the rest after it are refused and nothing of theirs is saved.

```json
{ "numbers": [14, 9, 12], "column": "todo", "reply": "short" }
```

### Merge slot

One merge at a time into a project's branch, so the branch can't move while an agent checks and merges (the **merge-ready** skill says when to take it). A slot is per project and branch; `branch` defaults to the branch the project folder is on (what Hive's Merge dialog merges into). Only a running agent of the project, with its own token, can claim or release its slot. Scripts and the Assistant can read it. An agent asking about another project gets `403`.

`GET /v1/projects/{name}/merge-slot?branch=main` — the slot: `{ project, branch, holder, waiting }`. `holder` is `null` when the slot is free, else `{ kind: "agent" | "user", name, cards, since, until, taken }` (times in epoch ms; `taken` is `false` while it is an agent's turn that hasn't claimed it again yet). `waiting` lists who waits, in order.

`POST /v1/projects/{name}/merge-slot/claim` — `{ "branch": "main", "cards": [305], "timeoutSeconds": 240 }` (all optional; 240 by default, at most 290, under the 300 seconds after which Node's `fetch` stops waiting for a reply). It waits in the call until the agent holds the slot, then replies `{ held: true, until, extended, slot }`. On timeout the reply is `{ held: false, position, holder, slot }`: the agent keeps its place for 2 minutes, so claiming again carries on in line. Claiming while holding extends the hold. A hold lasts 60 minutes; a Progress run the holder keeps reporting to (`/v1/progress`) keeps it longer. A hold that runs out goes to the next in line and is reported to the user. An agent whose hold ended without its release (it expired, or the user released it) gets `lost: { branch, why, at }` in its next reply. A claim naming a card whose own rules say Hive merges it is refused before the slot is touched, as its `report-merge` would be (`409`, `rule: "merge.hiveMerges"`, a `Refused` fact on the card): the merge queue merges it. A claim naming no card, or cards the agent merges, is unchanged, and so is the user's Merge dialog. With *Workflow rules are enforced* off, nothing is refused.

`POST /v1/projects/{name}/merge-slot/release` — `{ "branch": "main" }`: `{ released: true, next }` (who has it now), `{ left: true }` (it was waiting, and has left the line) or `{ none: true, holder, yours }` (`yours`: the project's slots the agent does hold or wait for, `[{ branch, held }]`). Without `branch`, it releases the agent's own hold or place in line when it has just one, whatever branch the project folder is on now (an agent that claimed `main` and then checked its own branch out there releases `main`); with none, the branch whose hold it lost, else the folder's branch.

A slot is released when its agent's session ends. Hive's Merge dialog takes the slot for the length of the user's merge, and waits while an agent holds or waits for it.

### Lanes

A **lane** is Hive's record of a card loop: a builder and a reviewer taking a project's cards in order (the **card-loop** skill registers it). It is bookkeeping, never a gate: nothing waits on a lane, and a loop works the same without one. A project agent starts its own lane, as its builder, joins its builder's lane, as its reviewer, and sees its own project's lanes; the Hive Assistant (Control agents) and scripts start lanes for any builder and see them all.

A lane is `{ id, project, name, builder: { id, name }, reviewer, cards, current, state, pausedOn, rounds, waitMinutes, startedBy, startedAt, updatedAt, endedAt, mergeCommit }`:
- `cards` are in the lane's order, each `{ number, title, column, blocked, round, reviewing }`: `column` is `gone` for a card archived, deleted or moved to another project, and `round` is 1 plus the reviews it has failed.
- `current` is the card being worked: the first in Doing that isn't blocked, else the first in Review, else the first not in Passed or Done.
- `state` is one of:
  - `active`;
  - `paused` while it waits for the user: its first card not in Passed or Done is blocked and no other card is in Doing or Review (`pausedOn`); back to `active` when that card isn't blocked or another one is worked;
  - `ended` once every card is in Done, or when the builder ends it after its merge;
  - `abandoned` when its builder or reviewer is removed from the project, or it is ended unmerged.
- An `ended` or `abandoned` lane's `cards` (and `current`) are as they were when it ended, not as the board has them now: another lane may be working those cards. A lane that ended without a record of them (before Hive kept one, or a damaged record) gives each card's `column` as `unrecorded` (not known) and `current` as null.
- An agent that is stopped keeps its lane: quitting Hive and restarts stop agents too.
- A builder has one running lane: starting a lane that shares a card with its running one updates that lane (a card added, the order changed, a reviewer given), and one sharing none ends it (`ended` when it has no card left to do, every one Passed, Done or gone, else `abandoned`).
- Ended lanes are listed until their builder starts another, or for an hour, and kept for a day.

`GET /v1/lanes` — the lanes running or recently ended, oldest first (`?project=` narrows them; `?all=true` gives every lane kept). `GET /v1/lanes/{id}` — one lane. Each running lane has `status` (#1270; null when it goes on as it is): `{ "reason", "card", "blocked"? }`, `reason` one of `blocked`, `hold`, `you` (a request for the user), `roundLimit`, `notMerged`, `merging`, `stale`, `reviewer` (no reviewer on a card in Review), `listChanges`, `lineUpdate` (#1271: the next card waits while Hive brings its builder's branch up to date after a squash merge; meanwhile its start is refused, `lane.lineBehind`); the first six pause it (`state: "paused"`, `pausedOn` the card). `queued` is a list change waiting for the card in flight, else null. With Settings → Advanced → Workflow rules are enforced off, the only status is a blocked or held card.

`GET /v1/lanes/next` — the calling agent's running lane (as its builder, else its reviewer): `{ lane, next: { card, title, carryOn } | null, waits }`: the card to start (`carryOn: false`) or carry on with, or, while the lane is paused, `next: null` and why (`waits`, a status). One card at a time: the next card starts only once the one before it is Done (a start before then is refused, `lane.oneAtATime`). With no running lane, `404`: when the agent's lane ended or was abandoned in the last 10 minutes, its error says so and not to start it again (HI-2273), else to start one. `queue` (1.0, #1354; only when there are some): the lane's passed cards Hive merges, each `{ card, line }` with where it is in the merge queue (the card's `merge`), which the next card waits for.

`POST /v1/lanes` — `{ "cards": [483, 481], "reviewer": "R1", "rounds": 10, "waitMinutes": 360, "name": "lanes and loops" }` starts a lane, or updates the builder's running one. The calling agent is its builder; the Assistant and scripts add `project` and `builder` (a name or id). A `reviewer` Hive doesn't know starts a new lane without one (the reply's `note` says so) rather than refusing; for the builder's running lane it is refused (`404`, HI-2273), naming the lane's reviewer (or its pool, or none yet), nothing changed, so a guessed name never drops a lane's reviewer. A generalist (`workflowRole` `generalist`, HI-686) is never a lane's builder or reviewer: naming one either way, here or in `join`, is refused (`400`), nothing changed. `pool: true` (the Assistant's and scripts', HI-1581; an agent's own lane is refused, `403`) starts it reviewed by the project's reviewer pool, with no reviewer of its own: refused (`400`) with a `reviewer`, where the project's Reviewers option isn't a shared pool (or workflow rules are off), and where nobody but the builder reviews, as Start Lane refuses it. Rounds and the wait left out are the project's workflow options (Card loops: its own, else the workspace's, else Hive's workflow defaults), else 10 and 360 minutes. Replies `{ lane, did: "started" | "updated", replaced }`: `replaced` is the builder's earlier lane, if starting this one ended it. A changed list for a running lane while one of its cards is in flight is queued (`lane.queued`, and `note` says so) and applies once that card is Done; the builder is told then (#1270). `applyNow: true` (HI-1995) applies it at once instead, in two steps: when the card in flight is no longer the new list's first own open card, Hive puts it back in Todo (as `put-back` does, its line and work kept), then edits the list, which applies at once between cards. Refused (`409`, nothing changed) while that card is in Review, Approved or merging, its builder is in a turn (working, starting, waiting for the user, background tasks), or its folder has changes not committed. If the lane ends or its list changes between the two steps, the edit is refused (`409`, the put back staying and said) and nothing is resumed or recreated. `note` starts `Applied now:`; the builder is told in its inbox and goes on with `hive_lane next`. With the card still first, or the rules off, it changes nothing. With workflow rules on, any list for the builder's running lane edits it, one sharing no card too; with them off, a list sharing no card ends that lane and starts another, as before. With the rules on, the builder's own start (the calling agent's, HI-2169) never takes a card off its lane: the cards of its list (its queued list, when it has one) that the new list leaves out stay, after the given ones, and `note` names them; the Assistant, the user and scripts take cards off. When the Assistant starts one and no card watch of its own covers the lane's last card, `note` says to watch it (#402). A new lane the Assistant or a script starts (not the builder's own) starts its stopped agents as Start Lane in the window does (HI-1900): a stopped builder's slot lent first where it works in slots (none free: the lane waits for one, and its stopped agents start once it is lent), then each stopped agent with the lane's brief. An idle builder (between turns, not on a watch) where cards aren't built in slots gets the lane in a new conversation with its brief, its last kept in its Sessions history (HI-2232), or once it is free if it isn't at its launch; `note` says so, and the caller doesn't prompt it. Any other builder or reviewer already running, idle or busy, is left as it is, never refused or given a new conversation (HI-1934): the lane is recorded for it. With workflow rules on, Hive gives a running builder the lane's first card itself once it is free (HI-2029), so the caller doesn't prompt it; the caller tells a running reviewer about the lane, and with the rules off the builder too. `note` says who started and where, or that it waits for a slot, and names each agent left running, with which to tell. A running lane updated while its builder isn't running gets its builder started on it, and `note` says so. `brief` (HI-1795, text, at most 4,000 characters) is the builder's brief, kept with the lane: where its cards are built in slots, every placement of one of them carries it after the card's prompt, in the conversation that works the card; outside slots it is delivered to the builder once per change (a `rebrief` in its inbox), never into the conversation it was running as its lane began (its next one gets it; an edit reaches the lane's working conversation), a replaced or cleared one's delivery not yet received cancelled. Left out, a running lane keeps its own; `""` clears it; the same text changes nothing. `note` says where it goes. Left out on a new lane, it is the brief (and, with no `name`, the name) of the builder's lane that ended in the last 10 minutes, all merged (HI-2097: a list change that raced the lane's end), and `note` says so. A new lane leaves out a card already Done (`note` names it); a list of only Done cards is refused (`409`). A card in `cards` made by someone other than the caller since the caller's turn began (a project agent's or the Assistant's; a script has none), in the last two minutes (HI-2167), gets a warning in `note`, naming who made it and how long ago (a project agent's: only its project's cards, another's said no more of than a card that doesn't exist): a guessed key may have found another agent's card; a new card goes on a lane through `POST /v1/tasks`' `lane`.

`POST /v1/lanes/join` — `{ "builder": "B1", "cards": [483, 481] }`: the calling agent joins the builder's running lane as its reviewer (a script adds `project` and `reviewer`); with `cards`, only a running lane that shares one (a builder's earlier lane, its cards passed and waiting for the merge, is another loop). With no such lane yet, one is started from `cards` as the builder's start would, and the builder's own start then updates it. Replies `{ lane, did: "joined" }`.

`POST /v1/lanes/{id}/end` — `{ "abandoned": true }` stops it unfinished (the user's and the Assistant's), or `{}` ends it. A lane ends by itself once every card is Done, its `mergeCommit` the last card's result revision from its facts; an agent's `end` is refused until then (409) and its `mergeCommit` is ignored, the reply's `note` saying so (#1270); the Assistant's or a script's is kept where the cards' facts name no merge. Only its builder or reviewer ends it among agents. With workflow rules off, as before: an agent ends it, its `mergeCommit` recorded as given.

`POST /v1/lanes/{id}/fresh-start` — `{}`: tries again the new conversation of a lane's agent that Hive stopped trying to start (HI-2034). A lane's start gives each of its agents a new conversation with the lane's brief; one busy then (in a turn, or with a prompt Hive just typed not taken yet) is started once it is free, within Settings → Advanced → *Lanes: longest Hive waits to start a busy agent afresh* (10 minutes). Past that, or after Hive closed while starting it (with no proof the new conversation began), Hive stops trying. The lane's `status` is then `startWait` with `why: "fresh"` and `freshBlocked` (`timeout`, `uncertain` or `failed`), and its cards wait: none goes to the old conversation. This retries each such agent, once it is free, with a new wait. Replies `{ retried }`, how many. The user's (the lane's row: **Retry New Conversation**) and the Assistant's, within Control (`lane-fresh-start`); a project agent is refused (403).

`lane-ended` (the event stream, #1270): a lane ended with every card Done, once: `{ workspacePath, lane, project, results: [{ card, revision }] }` (`revision` null: Done with nothing merged).

The event stream sends `lanes-changed` (`{ workspacePath }`: read the lanes again) when a lane changes, or one of its cards does.

### Merge queue

From api.version 9 (#1353). With a project's workflow set to **Hive merges**, Hive merges each approved card into its target branch through that target's **merge queue**, one card at a time (SPEC §16.9). Anyone who may read the project reads its queues (a project agent its own project's: another's is `403`); pausing, resuming, taking a card out and retrying its merge are the user's (in Hive's window) and the Hive Assistant's within Settings → Assistant → Control (Control agents): a project agent is refused (`403`, saying whose they are), and so is a script (`403`). Each change the Assistant makes is in its actions (`queue-pause`, `queue-resume`; a card's as `update-task`).

`GET /v1/queue?project=alpha&target=integration` — the project's queues (`project` is required but for a project agent, whose own project it is; `target` narrows to one), each:

```json
{ "project": "alpha", "target": "integration",
  "paused": { "reason": "user", "card": null, "files": [], "by": "assistant", "at": "2026-10-22T09:12:00.000Z" },
  "runBy": "Hive", "runHere": true,
  "testing": { "card": 12, "key": "AL-12", "title": "…", "entry": "AL-12/e7", "revision": "…", "expected": "…", "step": "checks", "started": "…", "run": "…" },
  "queued": [{ "card": 14, "key": "AL-14", "title": "…", "entry": "AL-14/e5", "revision": "…", "at": "…" }],
  "recent": [{ "card": 9, "key": "AL-9", "title": "…", "entry": "AL-9/e4", "outcome": "returned", "at": "…", "reason": "checks", "transient": false, "hasLog": true }] }
```

- `paused` is `null` while it runs. `reason` is `user` (Pause queue; `by` the `user` or the `assistant`) or Hive's own (`by` `null`): `needsYou` (an advance into a checked-out target was interrupted in a state Hive won't guess about, or an earlier runner's process or folder is still there: `files` names them; for an advance, `stuck` says where it stands: `branch` the folder is on, the target's `ref`, `expected` and `result`, the journal's `phase` (`done`: merged, but the folder was switched to another branch in that instant), each listed file's `side` (`expected`, `result` or `other`) and the `commands` that finish or undo it, each with its `purpose`, its `place` (the `project` folder or the target's `folder`), its `args` as they are and `command`, the line for PowerShell), `approval` (Merge into a checked-out branch is Ask each time: the card waits for the user's Approve in For you, `files[0]` the folder), `checkedOut` (from a Hive before 1.0's checked-out merges: Resume clears it), `rulesOff` (Settings → Advanced → Workflow rules are enforced is off), `targetMovesFast` (the target moved three times in a row while a card was tested), `uncounted` (its checks passed without counting three times), `identity` (no commit identity for the merge), `folderBusy`, `wrongBranch`, `staged`, `unstagedChanges`.
- `runBy` is the profile of the Hive running the queue now (`null`: none), `runHere` whether it is this one.
- `testing` is the card being merged now: its step (`testMerge`, `checks`, `advance`; `null` when another Hive runs it), the target's head it is tested on (`expected`), since when, and the progress run of its check (`run`, `GET /v1/progress`).
- `queued` waits in order; `recent` holds the latest 20 outcomes, newest first: `merged` (`result`, the target's new head; `by`: `hive`, or `outside` for a merge done by hand that Hive saw), `returned` (to its builder: `reason` `conflict`, `checks`, `hook`…, `transient` for a check that couldn't start, `files` a conflict named, `hasLog` when Hive kept its output, which the card's work shows) and `cancelled` (`reason`: `removed`, `stale`, …).

`POST /v1/queue/pause` — `{ "project": "alpha", "target": "integration" }` (`target` left out: the project's only queue): the queue stops before its next card; a card being checked finishes its checks and waits, unmerged. A queue Hive paused already keeps its pause. Replies with the queue.

`POST /v1/queue/resume` — the same body: the pause is cleared and the queue runs again, `{ "resumed": true, "queue" }`. When what paused it is still there and Hive can see it (the target still checked out, the rules still off, the interrupted advance's files still changed, an earlier runner's process still running), it stays paused, `{ "resumed": false, "queue" }`.

`POST /v1/queue/remove` — `{ "card": "AL-12", "reason": "The user wants it later." }` (`reason` required): the card leaves the queue (an override, `IntegrationCancelled`), back to Approved, and is never merged, after a restart too; its builder is woken. Refused (`409`, `queue.advancing`) once its merge has begun. Replies as a card intent (`{ ok, card, from, to }`).

`POST /v1/queue/retry` — `{ "card": "AL-12", "reason": "A flaky test, known." }` (`reason` required): Retry merge, an override that queues a card the queue returned (a red check too) with its approved revision unchanged, once per revision (`409`, `move.notFromHere`, otherwise). Replies as a card intent.

The event stream sends `queue-changed` (`{ workspacePath, project, target }`: read the queue again) when a target's queue changes: a card queued, its step, an outcome, a pause.

### Release Slot

From api.version 9 (#1561). The two releases an agent's ⋯ menu offers in Hive's window (SPEC §16.10.3), by slot name: a **carried slot** (an agent's 0.9 worktree, kept for it as a slot since the upgrade) stops being kept for it, and a **held writer** (an agent's run that has ended but still holds its slot, because Hive doesn't know that everything it started there has ended: Hive closed unexpectedly with it running, or its processes were kept running) is cleared. Anyone who may read the project lists them (a project agent its own project's). Releasing is the user's (in Hive's window) and the Hive Assistant's within Settings → Assistant → Control (Control agents): a project agent is refused (`403`), and so is a script (`403`). Each release the Assistant makes is in its actions (`release-slot`), and undo can't take it back.

`GET /v1/projects/{name}/slots/releasable` — what the project has to release:

```json
{ "project": "alpha",
  "carried": [{ "slot": "hb2", "agent": "B2" }],
  "held": [{ "slot": "slot-a", "agent": "B1", "run": "3f9a1c…", "hive": "gone (process 4120)",
             "processes": { "list": [{ "pid": 5150, "label": "node serve.js" }], "more": 0 } }] }
```

`held` lists the writers Hive's window offers Release for: the run is over in this Hive (`hive`: `this Hive`) or its Hive has gone (`gone (process n)`). `processes` is what Hive lists of what that run left running (its leftovers, or, its Hive gone, those of its processes the notice that Hive closed unexpectedly lists that still run); `null`: Hive doesn't know.

`POST /v1/projects/{name}/slots/{slot}/release` — `{ "kind": "writer", "confirm": { "slot": "slot-a", "run": "3f9a1c…" }, "end": true }`:
- `kind` is `carried` or `writer`; left out when the slot has only one of them (`400` when it has both, `409` when it has neither).
- A carried slot's lease ends (its folder and branch stay; Hive lends it to new work once it is clean). `409` when it is no longer kept for an agent.
- A held writer needs `confirm`, the slot and the run the user agreed to release, as the listing gave them (`400` without it). `end: true` ends the processes listed for its run first; if Windows doesn't let Hive end them, nothing is released (`409`). Refused (`409`) while its run is still live in this Hive (its session, or the processes it left still followed), while another Hive holding it still runs (or can't be told), and when its writer is no longer that run (a release or a start meanwhile: one of them wins, the other is refused).
- Replies `{ "project", "kind", "slot", "agent", "ended"? }` (`ended`: the listed processes were ended first).

### Pausing the team

From api.version 11 (HI-2081, SPEC §16.10.9). Before an update, a workspace's **team** (every agent of its projects) can be paused: Hive starts no lane card and no new conversation by itself, sends no card events, watch wakes or reviews from the pool (a message or the user's answer still goes), starts no merge queue entry, and tells each running agent once to finish its turn, end its runs and commit. The user's Pause the Team (in Hive's window) pauses every open workspace; the Hive Assistant pauses and resumes its own workspace only, within Settings → Assistant → Control (Control agents). Project agents are refused (`403`). Each pause and resume the Assistant makes is in its actions (`team-pause`, `team-resume`), and undo can't take it back.

`GET /v1/team` — the workspace's pause and, while it is paused, what still runs (a fresh scan; none is made for a workspace that isn't paused):

```json
{ "paused": true, "pausedBy": "assistant", "since": "2026-10-30T05:00:00.000Z", "parked": false, "safeToInstall": false,
  "running": [{ "project": "alpha", "agent": "B1", "state": "busy", "what": "npm run e2e (Progress run, 4 min)" },
              { "project": "alpha", "agent": "R1", "state": "unknown", "what": "its processes can't be read now" }],
  "others": ["Another open workspace isn't paused: the user pauses it from its window, or with Pause the Team."] }
```

- `parked`: every agent stopped, or idle (ready, finished or watching) or at a question for the user, with nothing of Hive's records left: no start of it under way (before its session exists), no background task its CLI reports, no open Progress run, no held slot writer, and no process its launches left running (an earlier launch's too). Hive doesn't look into the CLI's own process tree: a server started from a shell, outside Hive's records, is the user's to end. `state` `unknown` (its status unknown, leftovers not all listed, the workspace's projects unreadable, its pause not saved) is never parked. Your own turn isn't counted when you ask about your own workspace; what you left running is.
- `safeToInstall`: this workspace parked, and every other open one paused and parked. Another open workspace is only ever one line in `others`, with none of its agents.

`POST /v1/team/pause` and `POST /v1/team/resume` — `{}`: reply as `GET /v1/team`. Resuming hands out what the pause held (each wake offered again if still due) and lets lanes start their cards again. A pause outlives a crash or a plain quit; only Hive's restart for the update it was paused for lifts it by itself.

### Templates

From api.version 11 (HI-1502, SPEC §16.10.6). The Hive Assistant's alone: it lists a project's agent templates, plans a load and loads one, as **Load template** does in Hive's window, and (HI-2109) chooses the connections of a project's existing agents, as **Choose Connections…** does. A script, the user's token or a project agent is refused (`403`) before any template is read. Listing and planning are reads; loading and choosing connections need **Control agents** (Settings → Assistant → Control) and are undoable (`POST /v1/assistant/undo`). A template keeps no connection, model or effort (HI-2109): each agent's `provider` is only the CLI it suggests, and the connections are chosen as it loads.

`GET /v1/projects/{name}/templates` — the templates the project can use: Hive's own, the workspace's and its own.

```json
{ "project": "alpha",
  "templates": [{ "scope": "hive", "file": "team-3x3.json", "name": "Team 3×3", "agents": 6, "workflow": ["none", "git"] },
                { "scope": "project", "from": "alpha", "file": "pair.json", "name": "Pair", "agents": 2, "workflow": ["git"] }] }
```

`POST /v1/projects/{name}/templates/plan` — what loading one would do; nothing is changed. The body names it and what to load with it:
- `template` (required): its file, else its name (any case). `scope` (`hive`, `workspace`, `project`) narrows it; `from` is the project a project's template is kept in, when it isn't this one. None is `404`; several of one name are `409`, naming each one's scope and file: name one by them.
- `names`: new names for some of its agents, `{ "<key>": "<name>" }`. A key is the agent's place (`"1"` for the first), its name as made for this project (`AL-B2`), or its name in the template (`{key}-B2`) when only one agent has it. A key that names no agent or several, two keys for one agent, a place out of range and a name that isn't text are `400`, listing the keys there are. The names are checked as the window checks them (none empty, none too long, none twice).
- `connections` (HI-2109): which connection each agent gets, `{ "<key>": "<connection>" }`. A key is `"*"` (every agent), a role exactly as written here (`builder`, `reviewer`, `either`, `generalist`), an agent's place (`"1"`, as in `names`), or an agent's name, any case (as made for this project, or in the template); an agent's over its role's over `"*"`. An agent whose name is a role's word (`reviewer`) is named by its place. A value is a connection's id or name among those usable here (`options` in the reply). An agent none names gets the first connection on the CLI its role suggests, else the first usable, as the window's dialog starts with. A key that is no role, place or agent, a name several of its agents share, two keys for one agent, a place out of range, a connection not usable here and a name two connections share are said in `blocked` (and refused by the load).
- `workflow` (default `true`): whether its workflow options would be set.

```json
{ "project": "alpha",
  "template": { "scope": "hive", "file": "team-3x3.json", "name": "Team 3×3" },
  "remove": ["Ann", "Rob"],
  "create": [{ "name": "Coder", "template": "AL-B1", "role": "builder", "connection": "Claude · High", "pairedWith": "AL-R1" }],
  "taken": [{ "name": "Bea", "project": "beta", "suggestion": "Bea 2" }],
  "options": [{ "id": "c-3f9c2e1b", "name": "Claude · High", "cli": "claude-code", "account": "Personal" }],
  "blocked": [],
  "workflow": { "platform": "git", "applies": true, "needsGit": false, "dropped": [],
                "changes": [{ "key": "review", "now": "none", "next": "agent" }],
                "missingCommands": ["unit"], "identityOff": false, "problems": [] } }
```

`taken` is each name another project's agent has, with a free one to give in `names` (agent names are unique across the workspace). Each `create` entry's `connection` is the name of the connection it would get (null with none usable here: it is made without one, on the CLI it suggests, and gets one once an account is); `options` lists the connections usable here, in the order. `blocked` is why it can't be loaded now: an agent running or starting, a `connections` answer that can't be used, more agents than the project may have, and, with `workflow` on, a workflow for Git only in a project with no version control (`needsGit`: setting up Git is the user's, in the window) or options that can't be saved here (`problems`). `workflow` is null when the template has none for this project; `changes` is each option it sets that isn't so now, `missingCommands` the checks it names that the project has no command for (kept, for the user to set), `identityOff` that it turns the commit identity on and the project's git config has none.

`POST /v1/projects/{name}/templates/load` — the same body: **replaces every agent of the project** with the template's, and its layout. Refused (`409`) with a free name for each one taken, and for whatever `blocked` would list. It is the window's load: the project's agents can't start while it runs, and it publishes only if they are still those the plan read and none runs. With `workflow` on, the template's options for the project's version control are saved as the project's (Version Control → Workflow), from the same read of the template as its agents, once they are published; lanes and cards already under way keep their rules. Options changed meanwhile aren't saved, and the reply says so.

```json
{ "project": "alpha",
  "template": { "scope": "hive", "file": "team-3x3.json", "name": "Team 3×3" },
  "removed": ["Ann", "Rob"],
  "created": ["Coder", "AL-B2", "AL-B3", "AL-R1", "AL-R2", "AL-R3"],
  "renamed": [{ "template": "AL-B1", "name": "Coder" }],
  "connections": [{ "name": "Coder", "connection": "Claude · High" }],
  "workflow": { "platform": "git", "applies": true, "saved": true, "changes": [{ "key": "review", "now": "none", "next": "agent" }], "missingCommands": ["unit"], "identityOff": false, "needsGit": false, "dropped": [], "problems": [] } }
```

The removed agents' conversations stay in Sessions, their open cards go back and their lanes end, as when an agent is removed. **Undo** puts back the project's agents (with their ids, so their conversations are theirs again) and layout, and its workflow options: two changes, each undone only while it is still as the load left it, and while none of the agents runs. An old name another project's agent has now is never renamed: that change stays, said, to try again. The removed agents' cards and lanes stay as the load left them.

`POST /v1/projects/{name}/templates/apply` — **Choose Connections** (HI-2109): the project's existing agents given connections, nothing else changed (no agent replaced or loaded). The body: `connections` (required), as for a load; an agent none names keeps its own. Every answer is checked first: a key that is no role or agent is `400`, a connection not usable here or a name two share `409`, nothing changed. Each agent then changes through Agent Settings' save (its CLI with it), each change recorded for undo (its connection by id, with its CLI and last conversation when they changed: undo puts them back together, only while none changed since). The project's agents changing between the call's reading of them and its changes (one added, removed or moved) refuse it (`409`), nothing changed. A running agent keeps running on its old connection until it restarts (`restart`); one asked for another CLI's connection while it runs isn't changed (`skipped`, saying why).

```json
{ "project": "alpha",
  "changed": [{ "name": "AL-B1", "connection": "Claude · High" }],
  "restart": ["AL-B1"],
  "skipped": [{ "name": "AL-R1", "why": "it runs, and that connection is another CLI's: stop it first" }] }
```

### Skills and MCP

`GET /v1/skills[?project=name]` — the workspace's Hive skills, each provider's user (`level: "machine"`) and plugin skills, plus, if a project is given, the project's local skills, and then only the Hive skills its agents get (not those whose audience is `assistant`): `{ name, description, level, provider?, plugin?, audience?, bundled?, updateAvailable? }`, without folder paths. `audience` (Hive skills) is who gets it: `agents`, `assistant` or `all` (its `SKILL.md`'s `metadata.audience`; `agents` without one). `problem` (Hive skills) says why nobody gets it: its header can't be read, or its audience isn't `agents`, `assistant` or `all`. `bundled` is `same` or `changed` for Hive skills that ship with Hive, and `updateAvailable` marks a changed copy made from a version this Hive knows to be older than its own. A project agent may list only its own project's skills (`403` for another's).

`GET /v1/skills/{name}[?file=path]` — one of the workspace's Hive skills: `{ name, audience, file, content, files }`, its `SKILL.md` and the list of the files in its folder; with `file` (relative to the skill's folder, `/` between parts), that file instead (`{ name, audience, file, content }`). The whole path is checked before anything is read: an absolute path, `..`, an empty part or a link leading outside the skill's folder is `400`, a file it doesn't have `404`, a file over 512 KB `413` (also when it grew past that while being read: no more than 512 KB is ever read). `files` is in path order, without Hive's `.hive-copy` marker and without following links; it lists at most 200 files, looking at no more than 2000 entries or 8 folders deep, and has `filesTruncated: true` when there may be more (each can still be read with `file`). Reading a skill grants nothing: what a caller may do is still its token's.

`GET /v1/mcp` — MCP servers deployed to the workspace, each available to every project and the Hive Assistant, and running only where it is **added** (HI-2059: there are no on/off switches): `{ name, description, added, error }`. For the Assistant, scripts and the window, `added` is `{ projects, assistant }`: the names of the projects it is added to and whether it is added for the Hive Assistant, and `catalog` is `{ source, version }` for a server installed from an MCP catalogue (HI-545), else `null`. A project agent's call gets `added` as `true` or `false`, whether its own project has it, and nothing about other projects or the Assistant. Adding and removing servers is the user's (a project's MCP tab, the Assistant's view, the MCP view's Add to…): there is no endpoint. Before 1.0 the reply had `globallyEnabled` (the workspace's switch) and `assistant`; both are gone.

### Performance metrics

`GET /v1/metrics[?scope=workspace|project&project=name&from=…&to=…&trend=1&role=agent|assistant|api|viewer&provider=id&own=1]` — the workspace's performance metrics (Hive's API, its tools, its guidance and skill service) for a range (ISO times; default the last 24 hours): `{ scope, workspacePath, from, to, recording, projects, workspace?, skills?, app?, providers, notMeasured, dropped }`. `projects` has a part per project (`api`, `mcp`, `guidance`, `catalog` series); with `scope=workspace` (the default) there is also `workspace` (work of no project: the Assistant, scripts), `skills` (the skill service) and `app` (process-wide: refused requests, event streams, requests in flight). The parts add up to the totals once each. A project agent may only ask for its own project (`scope=project&project=<its project>`; anything else is `403`). Units: UTF-8 bytes, characters (UTF-16 code units), milliseconds (`count`, `totalMs`, `maxMs`, and a `histogram` over bounds of 1, 2, 5, 10, 20, 50, 100, 200, 500, 1000, 2000, 5000 and 10000 ms, plus one for longer). `providers` is the providers' own reported usage for sessions active in the range (each session's total; `unknown` counts sessions with none reported). Hive estimates no tokens. `notMeasured` lists what isn't measured. Labels are only Hive's route templates, its own tool names and provider ids (anything else is `(other)`). `project` is matched case-insensitively; a project scope's `dropped` counts only that project's dropped measurements, and `lossesUnattributed: true` says some losses in the range couldn't be attributed to any project (so this one's may be more; no count is given); a workspace scope has `droppedUntracked`, the count of those; `guidance[].skillsUnmeasured` counts delivered skills whose copy couldn't be measured (not in the sizes). `role`, `provider` and `own=1` (a workspace scope: the workspace's own work only) narrow every part, the trend and `providers` alike; `filters` echoes them with `notFiltered`, what they couldn't narrow (requests and tool calls aren't per provider). `coverage` (`rangeMs`, `observedMs`, `observedSince`, `stretches`, and `evictedThrough` when history in the range was removed to keep the metrics file under its size limit) says when Hive was recording this workspace: outside it nothing was seen (no data, not zero). `guidance[]` has `guidanceBytes` (core contract), `customBytes` (the project's additions), `roleBytes` and `modeBytes` (the Assistant's role and mode), each with its chars. `guidance[]` and `catalog[]` (the hive tool list as each session start's CLI got it: `starts`, `tools`, `toolsBytes`, and `toolsChars` over `charStarts`, the starts whose characters were counted; of the starts that reported its parts, `partStarts`, their characters `partToolsChars`, and the tools' descriptions `descriptionChars` and their parameters' descriptions `paramChars`, the rest of `partToolsChars` being the schemas and the list's structure) are per `workflow`, the launch's workflow role (HI-2049): `builder`, `reviewer`, `either` (its part in the running lanes as it launched, builder of one and reviewer of another being `either`, else its own role) or `none` (a generalist, the Assistant); `unknown` for what was recorded before Hive counted it. In 0.9.3 each also has `personaBytes` and `personaChars`, the names `modeBytes` and `modeChars` had before it (deprecated: they go in the next release). `providers[]` rows are per provider and `role` (`agent`, `assistant`), with `running`, `contextSessions`/`contextAvgTokens`/`contextMaxTokens`/`contextWindow` (a snapshot, not a sum), and sessions with no usage counted in both `unknown` and `costUnknown`; `providersNote` says why it is empty (scripts have no sessions); `providersUnreadable` (of `providersHosts`) counts session histories that couldn't be read, so `providers` is partial. With `trend=1` the report also has `trend` (`{ start, observedMs, requests, failed, cancelled, requestBytes, responseBytes, toolCalls, toolChars, launches, guidanceBytes }` for every hour of a range up to 2 days, else every day, at most 200) and `trendStep` (`hour` or `day`), for the scope's parts. If the workspace closes or switches while the report is read, it is refused (`400`).

`POST /v1/launch/connected` — for the hive MCP bridge only (an agent's or the Assistant's own token, for its own launch; `403` for other tokens, `401` for an ended launch's): its CLI has connected the hive tools (#865), so Hive may type its lines (the doorbell) into the session. Returns `{ ok }`. Not itself counted as API traffic.

`POST /v1/metrics/mcp` — for the hive MCP bridge only (an agent's or the Assistant's own token; `403` otherwise): `{ calls: [{ tool, mode: "compact"|"detail", ok, chars, bytes, ms }], catalog?: { tools, toolsBytes, toolsChars?, descriptionChars?, paramChars? } }`, at most 50 calls. The catalog is counted on the workflow role of the launch the token is for (`unknown` once that launch has ended or another has replaced it); one without `toolsChars` (an older bridge) counts its start but no characters, one without the parts its characters but no parts. The parts come both or neither, with `toolsChars`, and add up to no more than it, or the catalog is refused. Returns `{ accepted, refused }`; a malformed entry is refused, not stored. Not itself counted as API traffic.

### Progress

Long runs (test suites, builds) report their progress for the Progress panel, which shows each one with its agent, a bar and the time left, and Hive's taskbar button.

`GET /v1/progress` — the Progress panel's runs, newest first, as the panel lists them (Recent from before a restart included), in their public form: `{ workspacePath, enabled, runs }`. Each run has its `id`, who reported it (`source`: `agent`, `assistant`, `api` or `hive`, Hive's own merge queue running a card's merge checks; `projectPath`, `agentId`, `provider`, and `agentName`: the agent's, `Hive Assistant`, `Script` or `Hive (merge queue)`), `title`, `titleFromCommand`, `total`, `step`, `estimateMs`, `expectedMs`, `state` (`running`, `stale`, `passed`, `failed`, `stopped`), `staleReason`, `stopReason`, `waiting` (whether it waits, `true`/`false`) with `waitingSince`, `exitCode`, `dismissed` (listed under Recent), `startedAt`, `updatedAt` and `finishedAt` (ms), and what it ran for when it says: `card` (`"#1061"`), `revision` and `testedCheckout` (full commit ids) and `check` (the check's name). A finished run for a card has `counts` (#1222): `{ name, counted, whyNot? }`, how it counted as a check of the card's revision, as its `CheckRan` fact says (`whyNot`: `notCheck`, `notContained`, `dirty`, `moved`, `changed` or `revisionChanged`; SPEC §16.13). **Left out, for every token**: the folder it ran in, the command line (its arguments can hold a token or a prompt), the step's name, what it waits for, its summary and its log's path: a reporter's own text, which can quote output. **A title leaves Hive only when it was given on purpose** (`hive-progress --title`, the title a reporter or script gives, Hive's own test runners'). A run started with no title of its own (`hive-progress` without `--title`) is titled with its command line inside Hive; here its `title` is `"a command"` and `titleFromCommand` is `true`, and no part of the command line is given. The run says so itself (`titleFromCommand`, from `hive-progress`); one that doesn't (an older `hive-progress`, a run kept from before) whose title begins as its command line does is taken for one too. A project agent's token gets its own project's runs only. With the panel turned off, `enabled` is `false` and `runs` is empty. `progress-changed` on the event stream sends the same list as it changes. A run belongs to whoever starts it, known by the caller's token: a project agent's token makes it that agent's, the Assistant's its own, the workspace token a script's ("Script"). Only that agent may update or finish it; the Assistant only its own; a script any run in its workspace but Hive's own (`hive`), which only Hive updates. Another caller's run answers `404`, as an unknown one does. Runs are kept in memory, per workspace: after Hive restarts, or once the workspace closes (or its window opens another), an old id is `404`, which a reporter should ignore.

`POST /v1/progress` — start a run. Returns `{ "id": "…" }`.

```json
{ "title": "e2e: 12 suites", "total": 12, "step": 0, "stepName": "about", "estimateMs": 360000, "command": "npm run e2e" }
```

- `title` (required, up to 120 characters): what is running.
- `total` (1–100000) and `step` (0–`total`): `step` counts **finished** steps. Without `total`, the panel shows a moving bar and the time.
- `stepName` (up to 120): the step running now.
- `estimateMs` (0–7 days): the estimated time **left**, counted from this report. The panel shows "about N min left"; past it, "finishing" for a minute and then "longer than expected", never "0 s left".
- `command` (up to 200): shown on hover.
- `titleFromCommand` (`true`/`false`): the title is the command line, as `hive-progress` sends when it has no `--title`. Such a title never leaves Hive: `GET /v1/progress` and the event stream call the run `"a command"` (below), since a command's arguments can hold a token or a prompt.
- `waiting` (up to 120): what the run waits for before it can go on, such as `"waiting for a test slot: held by B4"`. While it waits the panel shows that and how long it has waited, never a time left, with a still, hatched bar; it doesn't go stale meanwhile. The estimate is held: the time that was left is given back from the moment it stops waiting.
- `pid`: the reporting process (Hive's reporters send it). If that process is gone before the run finishes (killed with its command), Hive ends the run as **ended without a report** instead of leaving it to go stale.
- What it runs for (#1220), all optional: `card` (a card reference, `"#1061"` or its key, `"HI-12"`: a plain number is `400`; `null` for none), `folder` (the absolute path it runs in), `revision` (a commit: its id, a short id or a name git knows, which must be what is checked out in `folder`, else `400` "a3f2c1d isn't what's checked out here (b71e09a is)…"), `check` (the name of one of the project's checks) and `link` (the id `POST /v1/progress/resolve` gave: the run then gets what was resolved there, the checkout before its command started; an unknown, expired or another caller's `link` is resolved again from the rest). What is checked out is always read by Hive, never taken from the request. For a project agent, a run that names no card is for its card in Doing when it has exactly one (none with several), and one with a `folder` and no `revision` is for what is checked out there when it starts. The panel shows the card and revision under the agent; a run with none of these shows as before.

`POST /v1/progress/resolve` — `{ "folder", "card"?, "revision"?, "check"? }`: what a run would run for, checked before its command starts, as `POST /v1/progress` resolves it: `{ link, card, revision, testedCheckout, check: { name, command } | null, folder }`, or `400` with why (an unknown card or another project's, a revision that isn't checked out, a check the project has no command for). `check.command` is the project's configured command for that name (project.json's `workflow.options.commands`). `link` is for the start: pass it back in `POST /v1/progress` within 10 minutes (once). It changes nothing else, except that for a run for a card Hive reads then what the run is checked against (#1222: the folder's state as the command starts), for the start that passes `link` back; `hive-progress` calls it first.

`PATCH /v1/progress/{id}` — `{ "total"?, "step"?, "stepName"?, "estimateMs"?, "waiting"? }`: an update. `waiting` says what it waits for now (`""`: it waits no more). Returns `{ "ok": true }`. `total` (1–100000) may be set once, on a run started without one (a command that learns how many steps it has after it started): from then on the panel shows its steps, and a `step` already past it is lowered to it; on a run that has a total, `total` is `409`. Without `estimateMs` the deadline stays where it was (the time left keeps counting down); only a new `estimateMs` moves it. A few updates a second are shown; more are merged, not refused. An update after a run went stale (no report for longer than expected) makes it running again. A finished run is `409`.

`POST /v1/progress/{id}/finish` — `{ "ok": true|false, "stopped"?, "summary"?, "exitCode"?, "logPath"? }`: the run passed or failed; with `"stopped": true` it was interrupted (Ctrl+C) and shows as **stopped**, neither passed nor failed, whatever `ok` says. Returns `{ "ok": true }`. For a run that is a check of a card, it waits up to 8 seconds for the run to be recorded, then adds how it counted: `"check": { "name", "counted", "whyNot"?, "changes"?, "platform" }`. `whyNot` is one of `notCheck`, `notContained`, `dirty`, `moved`, `changed` or `revisionChanged`, and `changes` lists up to 5 of what stopped it counting: paths, `:reflog` (a commit or checkout) or `:edit` (an agent's edit). `hive-progress --check` prints a line with the reason when the run didn't count. `summary` (up to 500 characters) shows under a failed run; `exitCode` (a whole number) is the command's exit code, and `logPath` (up to 400) a log or run record it wrote: both show in the run's details in the panel.

At most 5 runs can be open at once per agent (per Assistant, per workspace's scripts), and a workspace keeps at most 30 runs whoever reported them: ended ones make room, oldest first, and when all 30 are open another start is `429`. A request that is refused (`400`) changes nothing. A run with no report for longer than expected goes **stale**: with steps and an estimate, a step's share of the time left plus 2 minutes; with only an estimate, the estimate plus 2 minutes; with neither, 10 minutes. An agent's run also goes stale when the agent stops. Dismissing a stale run in the panel ends it: it leaves the agent's status and the taskbar, and further updates are `409`.

With **Settings → General → Progress panel** off, every call is accepted and ignored: a start returns `{ "id": "…", "ignored": true }`, and updates and finishes `{ "ok": true, "ignored": true }`. A report that was already on its way when the setting was turned off (or off and on again) is ignored the same way, and keeps nothing.

An agent's open run shows in its status (`GET /v1/projects/{name}` agents, and its activity) as `progress`: `{ title, step?, total?, stepName?, waiting?, etaMs?, stale? }`, `etaMs` being the time left now (none while it waits).

#### Reporting a command: `hive-progress`

Every session Hive starts has `hive-progress` on its `PATH` (cmd, PowerShell and Git Bash), so a command needs no code to report:

```bash
hive-progress [--title "e2e"] [--card HI-12] [--revision <commit>] -- <command> [args...]
hive-progress --check <name> [--title …] [--card HI-12] [--revision <commit>]
```

It runs the command with its output passed through unchanged and ends with its exit code, and reports it as the agent's run: the title (the command line when none is given; Hive's session guidance asks agents for a few words saying what and why, such as `--title "e2e: full set before the release"` or `--title "unit tests"`, so the Progress panel reads as a description and its details show the exact command beside it), the finish (passed when the exit code is 0, otherwise failed with `exit code N`), and an estimate from how long the same command in the same folder took the last few times it passed (kept in Hive's data, never in the project). With no Hive variables, Hive unreachable or a refused call, it just runs the command, and it never fails because of Hive. `HIVE_PROGRESS=0` turns reporting off.

**What a run is for** (#1220). Before the command starts, `hive-progress` asks Hive what the run is for (`POST /v1/progress/resolve`), and the run carries it: `--card HI-12` names the card by its key (an old `"#1061"` still works, quoted: a shell takes an unquoted `#` for a comment), else it is the agent's card in Doing; `--revision <commit>` names the commit, which must be what is checked out where it runs (in a None project, the card's revision: its declared paths' hash), else it is the card's revision when it starts (#1233: on its own line, what is checked out in its folder; in a shared folder, its newest commit; in a None project, its paths' hash), or what is checked out where it runs for a run for no card or for a card not started yet. `testedCheckout` is what is checked out where it runs (a None card's: its paths' hash). A refusal (a revision that isn't checked out, an unknown card) ends it at once with exit code 2 and the reason, and the command never runs. A `--revision` is checked even when Hive can't check it (reporting off, outside Hive, Hive unreachable): `hive-progress` asks git itself, and refuses the same way, or when git can't read the folder. `--check <name>` runs **the project's command for that check** (its options name it) instead of a command of yours, titled by the check's name; with no command configured for the name, outside Hive or with Hive unreachable, it runs nothing and says why (exit code 2). `--isolated` (a check run in a copy of its own) comes with check copies later, and is refused for now. A Hive from before this links nothing, and the run shows as before.

**Steps.** A command (or any project's test runner) that prints lines like this gets real steps:

```
##hive-progress step=4 total=12 name=carddialog
```

`step` is the step starting now, from 1; `total` how many there are; `name` the rest of the line. A line `##hive-progress log=<path>` names a log or run record the command wrote (the rest of the line); `hive-progress` sends it with the finish, with the command's exit code (`npm run e2e` names its run record, or its logs folder). A line `##hive-progress wait=<what>` says the command waits (for a queue or a lock: Hive's test runners print it while they wait for a test slot), and `##hive-progress wait=` that it waits no more: the run shows as waiting, and the wait isn't counted in the command's usual time. A command that ends by Ctrl+C (Windows' `STATUS_CONTROL_C_EXIT`, or a shell's `130`) is reported as stopped, not failed, and so is one whose `hive-progress` gets Ctrl+C itself (however the command then exits: its exit code is passed on, and the run isn't counted in its usual time; if it doesn't end within 5 s, or on a second Ctrl+C, it is ended with everything it started); one whose `hive-progress` is killed (an agent stopping a preview server ends the whole process tree) shows as ended without a report. The lines are taken out of the output. `hive-progress` starts its run at the first step line that gives a total, or after 2 seconds, so a total printed early shows as steps from the start. A run started without one takes the first total printed later (sent once with `PATCH`); a different total after that is ignored, the steps aren't.

Hive's own test runners report the same way (`npm run e2e`, a step per suite; `npm test`, a step per file) when they run in an agent's session.

**Inside `hive-progress`.** The command it runs has `HIVE_PROGRESS_WRAPPED=1`, and the run is the wrapper's: a reporter in it should print step lines rather than start a run of its own, which would be a second row. Another `hive-progress` inside one just runs its command; Hive's own runners print step lines.

Agents use `hive-progress` unasked for commands likely to take over 30 seconds, unless **Settings → General → Agents show long commands in the Progress panel**, or the Progress panel itself, is off: Hive's session guidance tells them which.

### Developer console

What each CLI sends Hive (its hooks, status lines, transcript records, the terminal markers Hive reacts to, the lines Hive types into it, its launch and exit, its own API calls), each next to what Hive made of it (the status it set, the details it read), and Hive's own events in a workspace (Agent API calls, merge slots, watches waking agents, Progress runs, refused hooks). Read-only. These routes answer only while **Settings → Agent API → Let agents read the developer console** is on (otherwise `403`).

- **Who reads what:** a project agent (its own token) reads its own session only; the Hive Assistant reads its workspace's agents, its own session and Hive's events there; the workspace token and viewers read any open workspace's. A source the caller may not read, and one an agent names that doesn't exist, is `404` with the same message.
- **Naming a source:** `agent` (a name or id) and `project` (an agent's own project by default), or `source=assistant` or `source=hive` (the request's workspace). A project agent naming none reads its own session.
- **Capture:** only while the user has the developer console open on a source; reading starts nothing, and a read of a source no open console captures says so (`source.capturing: false`, no events). Each source keeps at most its newest 500 events or 1 MB, in memory only, and nothing once the console stops watching it.
- **Redacted:** strings are kept only at the paths listed for each kind of payload (a hook's envelope: its name, session id, tool name, mode, folder; a tool input's file path; a status line's model; a transcript record's type and model) and only when they look like an identifier, a path or a time; every other string, one word or many, becomes `<text: N chars>`, so a tool's arguments, an unknown record and an unknown field's id or name stay hidden. A secret or sign-in field (a token, authorization, a login, a device code) is `<redacted>` with everything under it, and a prompt's or message's subtree keeps none of its strings.

`GET /v1/console/sources[?offset=n&limit=n]` — the sources the caller can read, 50 a page (`limit` up to 100): `{ total, offset, sources: [{ label, kind: "session"|"assistant"|"hive", select, provider?, capturing, events }] }`. `label` is for display (cut and masked); `select` names the source exactly as a read takes it: `{ source: "hive" }`, `{ source: "assistant" }`, or `{ agent: <its id>, project: <its project's name> }`.

`GET /v1/console/events?agent=…&project=…|source=…[&since=n&limit=n&kinds=hook,statusline,…|&seq=n,n]` — what an open console has captured of the source: `{ source, events, newest, older?|newer? }`. `events` are rows `{ seq, at, kind, name, summary }` (`truncated` when a payload was too large and kept as its outline): the newest 30 the first time (`limit` up to 100), oldest first after `since` (pass the reply's `newest` to carry on; `newer` counts those still to come). `kinds` narrows them: `hook`, `statusline`, `transcript`, `terminal`, `input`, `launch`, `exit`, `api`, `hook-server`, `watch`, `merge-slot`, `progress`. With `seq` (up to 3), the events in full instead, each with its `raw` payload and `made` (what Hive made of it), plus `missing` for those no longer kept. `seq` numbers rise across every source. The console's own reads aren't events.

### Notifications

`POST /v1/notify` — show a notification in Hive.

```json
{ "title": "Build finished", "message": "All 212 tests passed", "level": "success" }
```

`level` is `info` (default), `success`, `warning` or `error`.

`target` (optional, HI-1961) is what a click on the notification opens, in the toast and in its row in the Notifications panel: an agent's pane, `{ "agent": "HB4", "project": "hive" }` (its name or id; `project` defaults to the calling agent's own, and the Assistant and scripts must give it), or a card's dialog, `{ "card": "HI-12" }`. At most one. A target that isn't there is refused (404), as is one naming both (400). The reply says what a click opens: `{ "ok": true, "opens": "HB4" }`. If the agent or card is gone by the time of the click, Hive says so ("HB4 isn't in hive any more") instead.

```json
{ "title": "HB4 needs an Enter in its pane", "level": "warning", "target": { "agent": "HB4", "project": "hive" } }
```

### Events (server-sent events)

`GET /v1/events` — a stream of events as they happen:

```
event: session-status
data: {"type":"session-status","state":{"projectPath":"D:\\work\\api","sessionId":"6f1c…","status":"finished",…}}
```

Event types:

| Event | Data | Means |
|---|---|---|
| `session-status` | `{ state }`: an agent's live state in its public form (below) | An agent's status changed |
| `session-exit` | `{ projectPath, agentId, sessionId, exitCode, failedToStart? }` (`true` when its CLI exited before the session started; not why) | An agent's session ended |
| `workspace-changed` | `{ workspace }` (its path) | Projects or agents changed (added, removed, renamed): read `/v1/projects` again |
| `notes-changed`, `skills-changed` | (none) | Read them again |
| `tasks-changed` | `{ workspacePath }` | Read the board again |
| `lanes-changed` | `{ workspacePath }` | Read the lanes again |
| `queue-changed` | `{ workspacePath, project, target }` | A merge queue changed: read it with `GET /v1/queue` |
| `progress-changed` | `{ workspacePath, runs }`: every run, in the public form `GET /v1/progress` gives | A progress run started, moved on or ended |
| `merge-slots-changed` | `{ workspacePath, slots }`: the slots held or waited for, each `{ project (its folder), branch, holder, waiting }` as `GET /v1/projects/{name}/merge-slot` gives it | A merge slot was taken, released or waited for |
| `notice` | `{ notice: { id, kind, title, projectPath, agentId? } }`: `kind` is `finished`, `waiting` or `notice`; `projectPath` is `null` for an app-wide one; `title` is in English, whatever language Hive shows | Hive told the user something (a banner or a Windows notification; not when notifications are off). Its body (an agent's last reply, its question) isn't sent |
| `notice-resolved` | `{ projectPath, agentId }` | That agent no longer waits for the user |
| `assistant-activity` | `{ workspacePath, action: { id, at, text, ok, error?, revertOf?, kind, project?, agent?, toAgent?, card?, cards?, lane?, column?, settingId?, connection? } }` | The Hive Assistant did something, or was refused (its panel's list). `text` is the line for people, without what it quotes (the prompt or message it gave an agent, a setting's old and new values), and may be reworded or translated: a viewer reads `kind` and its targets instead ([Assistant activity](#assistant-activity), since `api.version` 5) |
| `agent-added` | `{ projectPath, agentId }` | The Assistant (or a card it started) added an agent; it also comes as `workspace-changed` |

**Nothing private is sent, to any token.** Every payload is built from a list of the fields it may carry, so there is no prompt, message, question or reply text, no terminal or CLI output, no command line, no notice body and no setting's value. A `session-status` event's `state` has: `provider`, `projectPath`, `agentId`, `agentName`, `cwd`, `sessionId`, `runId`, `sessionName`, `status`, `statusSince`, `startedAt`, `unseen`, `mergeSlot` and `watch` (Hive's own words: "Waiting for the merge slot (B4 is merging #305)", "Waiting for HI-12 → Review", with the watch's `cards`, `agents`, `lanes`, `column`, `changes`, `since` and `limitAt`), `notWatching`, `question: { since }` (it asked something without stopping; not what), `reviewing: true` (an action under the CLI's automatic review; not which), `signIn: { since }`, `untakenLine: { since }` (a line Hive typed that it hasn't taken), `inbox: { unread: [{ id, from, at, state }], overdue }` (its deliveries not received yet: who from, when and their state, not what they say; and how many weren't acked in time), `permissionMode`, `modeSwitching`, `planMode`, `modelName`, `modelId`, `effort`, `costUsd`, `costEstimated`, `contextWindow`, `backgroundTasks`, `settingUp` and `lockedFiles`. Its status message (the CLI's own words) isn't sent: `GET /v1/projects` gives it. Events cover every open workspace, so the Hive Assistant's token is refused here (403); it follows agents with `hive_wait_for_agents`. The workspace token and viewer tokens get every event. A project agent's own token gets its own project's `session-status`, `session-exit`, `notice`, `notice-resolved` and `agent-added` only (another project's carry their session names, which can name their cards), `progress-changed` and `merge-slots-changed` for its own workspace with its project's runs and slots only, and no `assistant-activity`; the other events carry no more than a path and come to it as to anyone. A client that stops reading (more than 1 MB of events waiting) is disconnected.

```bash
curl -N -H "Authorization: Bearer $(node -p "require(process.env.HIVE_API_TOKEN_FILE).token")" "$HIVE_API_URL/v1/events"
```

### Assistant activity

Each `assistant-activity` action says what it was with fields, from `api.version` 5 (#763), so a viewer (Apiary walking the Assistant to an agent's desk or the board) never reads `text`. `kind` is one of the set below; a refusal (`ok: false`) has the kind it tried, and its `error` is Hive's own short reason (`Not allowed`, `Not allowed by Settings → Assistant → Control`, `Not possible now`, `The request was invalid`, `Not found`, `Refused`, `Dropped as stale`, `Failed`), never the error's own text, which can quote what the Assistant sent; nor does `text` carry one (an agent added whose start failed is "Added B2 to hive; it didn't start"). The Assistant's panel shows the whole message. Its targets come wherever Hive knows them, on a refusal too:

- `project`: the project, by name;
- `agent`: `{ id, name }`, the agent it acted on: the one a card is started on, given to or is with after a change (also in a batch), a hand-over's from, a lane's builder, the reviewer joining a lane. An agent that doesn't exist yet (one being added) isn't named until it does;

- `card`: a card's number; `cards`: a lane's, a reorder's or a batch's cards;
- `lane`: a lane's id;

- `settingId`: a setting's id (as `hive_list_settings` lists it), never its value.
- `connection`: a connection's id (HI-2108), never its values.

Nothing private is added: no prompt or message text and no setting's value, the same allow-list as the rest of the stream. A field Hive doesn't know when the action is refused (a new card's number) isn't there.

## The built-in `hive` MCP server

When **Provide Hive tools to sessions** is on (the default), Hive adds an MCP server named `hive` to every session it starts, whatever its provider. It wraps the API above. Its replies are kept short, since everything a tool returns goes into the agent's context: a change confirms what changed and what the agent can't already know (a new card's number, where a card is now), a listing gives one line per item, and full detail comes from the matching read tool or on request (`hive_list_tasks` with `details: true`, `hive_read_task` with `history: true`, `hive_session_usage` with `days: true`). Structured reads such as `hive_project_status` are compact JSON; notes and handovers are read as their text.

Its tools' descriptions are short too (HI-2012), since every session is given them all: what a tool does and the rule a caller can't guess, at most 300 characters (120 for each parameter's; `tests/e2e/toolLimits.cjs` holds the limits, checked by `replysize`). Each tool's cases, defaults and mechanics are in the bundled `use-hive-api` skill's `tools.md`, which agents and the Assistant read when they need them; this page keeps the routes.

Claude Code runs these without asking (they are Hive's own, and limited by the control level); Codex gets a 15-minute tool timeout for them, since waiting and asking the user can take minutes.

A handover belongs to a project when its file name is `handovers/<date>-<project>-<title>.md`, as `hive_create_handover` writes it. When another project's name begins the same way (`hive` and `hive-website`), the `**Project:**` line at the top of the handover decides. Hive records whose each handover is by the project's stable id as it writes it (older ones once, from what they say), so a project renamed in the workspace keeps its handovers, and a project that later takes its old name never gets them.

The server's instructions (for Codex, which doesn't show MCP server instructions to the model, Hive passes the same text as developer instructions) are Hive's short session contract: that handovers, shared notes, other projects and the board are Hive's and are reached with these tools rather than by searching the file system, which of Hive's skills covers which workflow (`work-on-card`, `review-agent-work`, and `coordinate-agents` for the Assistant), and the board's boundaries in a line, which hold even when a skill is missing. When the project has a handover, the instructions also name the latest one, so a new session knows it is there from the start. The tools' descriptions say what each takes, changes and answers; how to carry out a workflow is the skills'. `GET /v1/status` gives the revision of this guidance, and `GET /v1/projects/{name}` each running agent's `launched` revisions (its guidance and skills at launch).

The server is a small Node script bundled with Hive and run by Hive's own executable, so nothing else needs to be installed.

## Security notes

- The API binds to `127.0.0.1` only; it is not reachable from other machines.
- Any local program that can read the token can use the API. Regenerate the token in Settings if it leaks.
- Give an app that only shows Hive a viewer token, not the workspace token: it can read everything but change nothing, and revoking it cuts that app off alone. The discovery file holds no token.
- Session input is off by default because it lets one agent drive another project's session.
- The Hive Assistant's token is separate, replaced each time it starts, and limited to its workspace and to Settings → Assistant → Control.
- Shared-note paths are confined to `.hive/shared`.
