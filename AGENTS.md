# Hive — notes for agents

Hive is a Windows desktop app (Electron + TypeScript + React) for running coding agents (Claude Code, Codex) across the projects in a workspace. **You are probably running inside Hive right now**, developing Hive itself. These notes are for every agent working on this repository, whichever CLI runs it: Codex reads this file, and Claude Code reads it through `CLAUDE.md`.

- Product decisions: [docs/SPEC.md](docs/SPEC.md) — the source of truth. Update it when a decision changes.
- How the code fits together, and a code map of where each area lives: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
- User-facing docs (bundled into the app's Docs view): [docs/USER_GUIDE.md](docs/USER_GUIDE.md), [docs/AGENT_API.md](docs/AGENT_API.md), [CHANGELOG.md](CHANGELOG.md)

## Project conventions

- Design is settled before code: asked to discuss or plan, don't change code; list the open questions and confirm once answered. Once a build is agreed, go end to end (code, tests, docs), then **ask** before building the installer (`npm run dist`): more changes often come first. An installer the user will run goes in the **main checkout's** `dist`, not a worktree's (`npm run dist` in a worktree copies it there and says so; it notes when the main checkout is at another commit, and never replaces a different build without `--replace`). The user keeps older installers and archive folders in that `dist`: never delete or tidy them.
- **Name cards by key** (`HI-1661`) in commits, comments, docs, code comments and replies, never by the workspace-wide number (HI-1660 is `#1662`: a number quoted finds another card). The `#1149`-style references already in the docs and code are those old numbers: they still find their cards (search `#1149`, or a link), but write new ones as keys.
- Outside a card loop, **commit only when the user asks** ("commit", "ready merge"…): leave finished work uncommitted and say so. Commits use the no-reply address in the repo's git config (`git config user.email`), never a personal email. Never push unless asked.
- **Never run `prettier --write`** (or Prettier as a check): the repo isn't Prettier-formatted (no config), so it rewrites whole files (80 columns, double quotes, LF) where the code uses long lines and single quotes. Match the surrounding formatting by hand and check with `npm run typecheck` and `npm run lint` (oxlint) only. Before running any whole-file tool on a file with uncommitted changes, keep a copy.
- **Line endings** (`.gitattributes`, #149): git stores text as LF, and the working tree has your machine's ending (CRLF on Windows with `core.autocrlf`); write a file with one ending throughout, never LF lines into a CRLF file. `tests/lineEndings.test.ts` fails on a mixed file or a lone CR. Scripted edits are how files get mixed (Git Bash's `sed -i` strips CRs; a heredoc mangles a script's backslashes): make multi-line edits with your editing tool, and before committing run `git ls-files --eol | grep w/mixed`. To fix a mixed file, delete it and `git checkout -- <file>` (a plain checkout skips it as unchanged).
- User-visible behaviour changes go into SPEC.md and the user guide in the same change.
- Hive is released (0.1.0 first, 29 Sep 2026) on the public repository `Suremise/hive-desktop`; installed copies update from its GitHub Releases. Add user-visible changes (features, notable fixes) to an **Unreleased** section atop `CHANGELOG.md` as they're made; it becomes the next version's notes. Versions follow semver while in 0.x: 0.1.x for fixes, 0.x.0 for features, 1.0 once settings formats and the Agent API are stable. Don't bump the version, create GitHub releases or tags unless asked (RELEASING.md's **The user's OK** lists each step that needs it); releasing and the 1.0 path (integration branch, baseline install, RC, release) are in [RELEASING.md](RELEASING.md).
- Agent-facing tool replies are lean: a change confirms what changed, a listing returns short rows, full detail on request, without trimming context the agent needs (instructions, descriptions). Short forms: `src/shared/toolReplies.ts`; `tests/e2e/replysize.cjs` holds each tool's reply to a size.
- New user-visible features add a tip to `TIP_ENTRIES` in `src/shared/tips.ts`, in id order, with an unused `order` for where it's shown (a sentence or two, a user guide heading's id for Learn more, a command for Try it if any); `tests/tips.test.ts` checks the order and each id. Every user guide heading ends with its id, `<a id="its-slug"></a>`, kept when it is renamed, and links into the guide name the id (`tests/userGuide.test.ts`, #1535).
- **Translations** (#767, #768; design in the shared note `plans/2026-10-14-i18n-design.md`): text the user sees is a message, `msg({ id: '<area>.<name>', defaultMessage, description })` (description: a note for translators), kept as data and shown with `tr()` (`tRich()` for markup) when rendered or sent, never at module scope (it wouldn't follow a language change). Plurals and joins are ICU and `fmt` (`{n, plural, one {# card} other {# cards}}`, `fmt.list`), never `n === 1 ? '' : 's'` or a sentence glued from pieces. Numbers, sizes, token counts, percentages and dates go through `fmt`, `shared/units.ts` and `shared/dates.ts` (a plain `{n}` placeholder isn't localised: `{n, number}`), never `toLocaleString()` (`tests/i18nFormatting.test.ts` fails on a bare one; English named, `'en'`, is for what agents read). Agent-facing text (tool replies, guidance, wakes, the Agent API) and CLI-facing text stay English and are never messages: whole files are in `EXCLUDED` in `scripts/i18nGuard.mjs`; elsewhere mark the line `// i18n-ignore: <reason>` (the reason is required).
  - Numbers in plain placeholders: `npm run i18n:numbers` (`-- --changed`: the branch's files) lists each place passing a number to a plain `{x}` (via `tr`, `tRich`, `hiveError` and helpers taking a message), typing plain placeholders `string` in a copy of `src`. Apart, it lists values that may be numbers, calls of a message unknown where made (a `Msg` variable: check the messages it can be), and placeholders used both plain and as a plural. A review aid, not a check: ids, ports, exit codes and small counts stay plain; a count, size or amount that can reach 1,000 needs `{n, number}` or a plural. Numbers in JSX outside a message aren't checked. A helper's signature change can stop it: `tests/i18nNumbers.test.ts` then names the patch to update.
  - After adding or changing messages, `npm run i18n:extract` and commit `locales/en/` and `src/shared/i18n/values/` (generated: never edit them; a unit test fails when they're stale).
  - The guard (`npm run i18n:guard`, in `npm test` and CI) fails on new hard-coded text. `i18n/allow/` lists the text not converted yet, per file; the lists only shrink: after converting text, `npm run i18n:guard -- --prune <files>`. Never edit a list by hand or run `--init` again (CI compares them with the merge base's and fails one that grew); a file moved keeps its list (`git mv` it too).
  - Translations are `locales/<code>/<area>.json`: `npm run i18n:check` must pass (an extra key, broken ICU, a changed placeholder or a control character fails it; a missing translation shows English and doesn't), `npm run i18n:coverage` informs, and after translating `npm run i18n:coverage -- --record <code>` records the English they were made from.
  - **Every locale, in the same change:** a change that adds or changes text the user sees translates it into every language in `locales/` (all seven besides `en`) before it goes to review, and never ships English fallbacks for later. No check fails on a missing translation, so this is on the builder, and the reviewer checks it (`npm run i18n:coverage`).
  - A language's screens (`npm run e2e -- --lang <codes>`, one run at a time): read its `report.txt` first and open only the screenshots it flags or your change touches (#899).
- Fewer merge conflicts: `CHANGELOG.md` merges with `merge=union` (`.gitattributes`), so two new Unreleased entries both stay. Use union for nothing else: it silently keeps both versions of a changed line, breaking prose and code (for `package-lock.json`, rerun `npm install` after a conflict). After merging main, glance over the CHANGELOG for an entry that appears twice in two wordings. The tips and the e2e suite list (`tests/e2e/run.mjs`) are sorted by id/name so new entries land in different places; unit tests keep them sorted.
- Agent guidance has one owner per rule: the short always-present session contract in `src/shared/hiveGuidance.ts` (identity, where Hive's things live, board boundaries, which skill for which workflow), workflows in the bundled skills (`resources/skills`, `metadata.audience` says agents, assistant or all), arguments and side effects in the tool descriptions (`hive-mcp.ts`), and enforcement in the Agent API and the workflow's gates (SPEC §16.11). Don't copy a procedure into a prompt, mode or tool description, and don't restate a gate as a rule. This file holds only this repository's own conventions: what Hive enforces for every project (when a loop commits, when a card is Done, who merges and how, a lane's cards) is the gates' and the bundled skills', and where one of `.claude/skills` has a rule, this file points to it rather than stating it too; `tests/guidance.test.ts` checks the skills and tools the guidance names exist for that audience. After changing guidance, a skill, a mode or a tool description, run the scenarios that exercise what changed, before and after (`npm run scenarios -- --only <ids>`, `--save-baseline <name>` for before; compare benchmarks in Performance → Compare), naming the ids on the card and why they cover the change; and, when it could alter what agents do, the model trials, which the card then asks for, also `--only`, each scenario run at least twice (`--repeat 2`; compare with `tests/scenarios/BASELINE.md`). The full scenario set is for guidance-wide changes (the guidance diet, the skills split, tool descriptions: HI-2010, HI-2011, HI-2012) and an RC that could be published. After changing a bundled skill or mode, run `npm run bundled-history` (Hive updates workspaces' untouched copies from it; a unit test fails until it's run).
- Skills for developing Hive itself (verifying the UI, providers, releases, risky service changes) are in `.claude/skills` and `.agents/skills`, identical (a unit test checks): edit both. Their names never start with `hive-`: that prefix is Hive's own copies in `.agents/skills`, which git ignores.
- Personal, machine-specific notes belong in `CLAUDE.local.md` (git-ignored; Claude Code reads it), not here. `CLAUDE.md` only imports this file (`@AGENTS.md`): put shared notes here, so every agent gets them.

## Commands

```bash
npm install            # after cloning; also run: npx install-electron --no  (Electron downloads its binary lazily)
npm run dev            # dev build with hot reload — runs alongside the installed Hive (see below)
npm run typecheck      # tsc for main/preload/shared and renderer
npm test               # vitest unit tests (tests/); also run by CI (.github/workflows/ci.yml) on push/PR
npm run lint           # oxlint (.oxlintrc.json), fails on warnings; part of build and CI
npm run e2e            # end-to-end suites (tests/e2e) against the dev build — needs npx electron-vite build first
npm run test:clean     # remove what tests left in %LOCALAPPDATA%\hive-test and print its sizes (--dry-run lists only)
npm run scenarios      # do agents use Hive's skills and keep its rules, and what does Hive cost in them? (tests/scenarios: fake Claude Code by default, --provider fake-codex or fake-copilot (the real Copilot CLI offline); claude-code|codex for model trials, which cost tokens; each run writes benchmark.json for Performance → Compare)
npm run build          # typecheck + lint + production bundles into out/
npm run dist           # build + NSIS installer → dist/Hive-Setup-<version>.exe
npm run icons          # regenerate PNG/ICO from build/*.svg
npm run licenses       # regenerate THIRD_PARTY_NOTICES.md (also part of build)
npm run i18n:extract   # English catalogues and typed values from the code's messages (--check: only check); i18n:check, i18n:guard, i18n:coverage, i18n:numbers: see Translations
npm run release        # build + upload a DRAFT GitHub release — only when asked (RELEASING.md)
```

Hive is MIT-licensed (`LICENSE`). `THIRD_PARTY_NOTICES.md` is generated from what ships: the main process's `dependencies` plus the renderer libraries listed in `scripts/thirdPartyNotices.mjs` (`RENDERER`). When a new library is bundled into the renderer, add it there; commit the regenerated file. A unit test (`tests/licenses.test.ts`, so CI) fails when the committed file is out of date; `npm run licenses -- --check` checks without writing. Only add dependencies with permissive licences (MIT, BSD, ISC, Apache-2.0 and similar) unless the maintainer agrees otherwise.

npm 11 blocks install scripts by default; esbuild and electron-winstaller are approved in package.json. If a new dependency needs a script, `npm approve-scripts <pkg>`.

## Developing Hive from inside Hive

- `npm run dev` (unpackaged) uses its own profile `%APPDATA%\Hive-Dev` and Agent API port **47822**, and its title bar says **Hive Desktop Dev**. The installed app uses `%APPDATA%\Hive` and port 47821. Both can run at once.
- To update an installed copy: `npm run dist`, then quit Hive, run the installer, reopen and resume the sessions (conversations are kept). Leave running the installer to the user.
- Dev and test builds use the Windows app ID `com.hive.desktop.dev` ("Hive Desktop Dev"); never give them the installed app's `com.hive.desktop`, or Windows shows Electron's icon and name for the real Hive.
- Never kill Hive processes by name — the installed Hive hosting this session is also `Hive.exe`/`electron.exe`. Target processes by command line (e.g. paths containing `out\main` or a test profile).

## Gotchas

- **ELECTRON_RUN_AS_NODE**: shells started by the Claude Code VS Code extension inherit `ELECTRON_RUN_AS_NODE=1`, which makes `electron.exe` run as plain Node (`app` is undefined). Hive strips it from session environments, but if you see "Cannot read properties of undefined (reading 'setPath')", clear it.
- **PowerShell 5.1 encoding**: `Get-Content`/`Set-Content` read UTF-8 without a BOM as ANSI and corrupt characters like `—` and `·`. Edit files with your editing tools (or Python with `encoding='utf-8'`), never round-trip them through PowerShell text cmdlets.
- **zustand selectors** must not return fresh objects/arrays (`?? []`) — that loops forever (React error #185). Use a stable constant such as `NO_PROJECTS`.
- **`setActivity(view)` toggles** the sidebar when that view is already shown (it's the activity bar's click). To just show a view (from a command or action), use `showView(view)`.
- **Shortcuts**: never read `Command.keybinding` directly for display or matching; use `commandKeybinding(id)`, which applies the user's and the project's overrides.
- **Agents**: a project can have none, and all are equal (no built-in Agent 1, no `'main'` id). Calls that name no agent use `sessions.soleAgent()`; renderer code gets `null` from `focusedAgentId()` when there are none and uses `actions.quickAddAgent()`.
- **Several windows**: each window has its own workspace. `workspace.x(projectPath, …)` finds the right one by path, but path-less calls (`workspace.path`, `skillsDir`, `refresh()`…) need the current work's workspace (IPC and Agent API calls have it); background code uses `workspaceOf(projectPath)` or `inWorkspace(ws, fn)`. Send a window-specific event with `emitTo(win, …)`.
- **Hive Assistant**: its home `.hive/assistant` is a session host like a project (one agent, `assistant`) but is never in `workspace.projects`. Session code takes `workspace.assertSessionHost()`, not `assertProject()`; the renderer looks a session's project up by path with `findProject()` (includes `workspace.assistant`). It calls the Agent API with its own per-launch token (`assistantControl.ts`), governed by Settings → Assistant → Control, not Settings → Agent API; every change it makes goes through `assistantChange()` in `servers.ts` (level, the activity list, the record undo uses).
- **Main's thread carries every keystroke**: each pane's typing and every IPC reply go through it, so synchronous work there is felt as lag. That means `DatabaseSync` steps that can wait or fsync, `spawnSync`/`execSync`, `readFileSync`/`statSync` loops over many files, reading the whole board where a query would do, and heavy CPU. Such work goes to a worker thread, with a queue in the worker where its calls must stay in order. The pattern to copy is the repository lock's (HI-1680): `src/main/repoLockWorker.ts` runs the unchanged core, `repoLock.ts`'s `LockThread` talks to it (its code runs in-process in unit tests), and it is a build entry in `electron.vite.config.ts`. The usage history's worker (#1106) is the larger example. Only where it makes sense: small, fast work stays on main, where a worker's messaging would cost more than it saves. The evidence is hive.log's "main process was busy" and "on main's thread" warnings, which name what was under way (often waiting, not the cause), or a stall you measured. Measure before and after (main's longest stall, and a keystroke's echo where typing suffers, as `tests/e2e/repolocktyping.cjs` does), and put the numbers on the card. Asynchronous file calls don't hold the thread but share the process's 16-thread libuv pool with every window and worker (`threadPool.ts`, HI-1702): keep bulk file work a few calls at a time (`atMost`), and read hive.log's "A file call took … to end" warning as the pool full or the disk slow (timed off main's thread, so not main being busy).
- **Main's file system access is `original-fs`** (`original-fs/promises`), never `fs`: Electron's `fs` opens an `.asar` it stats as an archive and holds it until Hive quits (#246). Lint enforces it in `src/main`; a dependency doing file work in projects (it gets Electron's `fs`) mustn't stat their files.
- **Kept files** (`config.json`, `workspace.json`, `project.json`): read with `readKeptJson()` and write with `writeKeptJson()` (keeps a `.bak`, recovers damaged files), never `readJson`/`writeJsonAtomic`.
- **Deleting what the user can see** goes to the Recycle Bin through `trash()` (`src/main/trash.ts`), never `shell.trashItem` (a unit test fails); a test copy moves it to its suite's trash folder instead (#414), checked with `lib.trashed()`.
- **Test isolation**: tests never assume they're alone on the machine or inherit their shell. What a run uses of its own comes from the run context (`tests/e2e/runContext.cjs`, `lanes.mjs`, `build.mjs`): environments from an allowlist (`lib.hiveEnv()` for a test Hive, `lib.childEnv()` for the hive MCP server or `hive-progress`), a lane's ports and folders, the CLI test homes, and the dev build under a lock per worktree. Never build a child's environment from `process.env`, and give every child the runners, `lib.cjs` or the harness start themselves an `env` (`runContext.baseEnv()` for git and the build), so a shell's `GIT_DIR` or `NODE_OPTIONS` can't reach it (unit tests fail); a setting a run must pass on goes in `PASS_ENV`. After changing the runner, `lib.cjs`, the run context or the scenario harness, run `npm run e2e:concurrency` (and `-- --heavy` after changing `slots.mjs`). At most two heavy runs (a full or `--repeat` e2e run, more than five scenarios, a full unit run) go at once on the machine (`heavySlots` in `%LOCALAPPDATA%\hive-test\config.json` changes it, for the whole machine: tests/e2e/README.md): a third waits, not hung, printing who holds the slots ("e2e: waiting for a test slot" in Progress; `--no-wait` fails at once). Tests make temp folders with `tempDir()` (`tests/tempDir.ts`), by long, real paths, in `%LOCALAPPDATA%\hive-test\tmp` (also the unit run's `TEMP`, so Defender's exclusion covers it: #992; swept after a day), never under `os.tmpdir()` (a unit test fails): CI's is the 8.3 form `C:\Users\RUNNER~1\…` and Hive compares real paths, so such tests failed on CI only. A test that needs another name for a folder makes one with `tests/pathAliases.ts`: `junction()` works on any machine, `shortPath()` only where the volume makes 8.3 names. Unit tests run git with none of the shell's `GIT_*` variables (`tests/cleanGitEnv.ts`) and no global config, as CI does (`tests/noGlobalGit.ts`): a test whose Hive code commits or merges sets its repository's own `user.name` and `user.email`.
- **Tests**: e2e suites live in `tests/e2e` (its README says which suites start the real Claude Code and when, and how builder and reviewer split the runs). **Merge checks**, this repository's (#1010): a merge into main or an integration branch (such as `1.0.0`) runs typecheck, lint, the unit tests and the cards' own focused e2e suites (those their reviews ran, plus any suite the merge's conflicts touched), with `--build --record`, never the full set or `--affected` (an hour of e2e per merge held every lane up). Whoever merges runs them until the hive project moves to Pair after the 1.0 baseline (#1288); then they are the queue's merge checks (Project Settings → Workflow, G9). The full set (`--all`, the fake tier) runs on the integration branch when lanes go quiet (a phase's end, overnight with load capped, before a long pause; failures carded at once and bisected over the merges since the last full run), before every release, and on request. `--affected` stays a tool for picking suites, not a merge's gate. The real tier (suites that start the real Claude Code or Codex: `--real`) runs before a release and after a Claude Code or Codex update; a card whose change needs a real suite names it among its focused suites and runs it by name. A real suite skipped for the environment (usage limit, sign-in, network) doesn't block a merge, but the run record says so and the reviewer decides. Use `lib.cjs`, work under `%LOCALAPPDATA%\hive-test\e2e` (a runner's suites each in its lane's `lanes\<k>\<suite>`, so runners in different worktrees don't collide), never the real clipboard, profile or `~/.codex`. Probes of your own (scripts, screenshots, profiles outside a suite) and redirected output take a new folder each run, from `lib.probeDir()` (in `hive-test\scratch`) or your scratchpad, never in the lanes or logs, the project, a worktree or beside one (the worktrees' parent folder), or a project's `.codex`, `.claude` or `.agents` (a stray `.codex` with a reviewer's probe stopped every Codex agent's commands, #509; logs left beside worktrees outlived them). The runners prune what tests leave in `hive-test`, keeping what an open card cites by path (`npm run test:clean`, tests/e2e/README.md Housekeeping). Unit tests get `tests/electron-stub.ts` for `electron`. Lint is oxlint because typescript-eslint doesn't support TypeScript 7.
- **Tests per card** (HI-2003): narrow is the default. A round tests its change properly and doesn't re-run what it didn't change; the wide runs belong to the RC and the quiet-time runs.
  - **Each round, the builder:** typecheck and lint; the unit test files for what changed, plus those the change could break by import (`npx vitest run --changed <base>` follows imports); the e2e suites that cover the change, by name (`--affected` only to pick them: name the picked set on the card); `npm run test:waits`. A full unit run once, before the first submit only.
  - **A fix round:** only the suites that failed, plus those the fix touches.
  - **The reviewer** reads the builder's run record and re-runs only the new or changed tests and what it doubts, saying which on the card: no wide re-runs.
  - **Never on a card unless the card asks:** the full e2e tier (`--all`), the real tier (`--real`), `--repeat` beyond 5 (a flake card says its own count), or model trials. Scenarios with the fake provider still run when guidance, a skill, a mode or a tool description changes, but only those that exercise the change (`--only`, below); the full set doesn't run on a card unless it is guidance-wide.
  - **Full runs** are each RC that could be published (RELEASING.md, Steps 1 and 4) and the integration branch when lanes go quiet (above).
- **Tests wait for conditions, never for time** ([tests/README.md](tests/README.md)): poll what you expect to see (`lib.until`, `vi.waitFor`), never sleep and then check or read state once after an action; a timeout bounds a hung run and is never the fix; each test cleans up its own state and passes under load. `npm run test:waits` finds the sleeps a branch adds before a check: builders run it before Review, and reviewers fail a new or changed test that breaks the rules.
- **Flaky tests**: use the `investigate-flake` skill (`.claude/skills` and `.agents/skills`): it checks whether a flake still happens, reproduces it under load, fixes the wait with a condition, and proves the fix. Other lanes' flakes don't count against your card: card them.
- **The machine is shared** with other agents' lanes and the user's own Hive. Never load every core (at most half, in short bursts, said on the card first; #782 reached 95 °C). Load and flake runs add modest, bounded load: a few CPU spinner workers at most beside the run, never one per core (a saturated machine overheats, slows every lane and makes flakes look worse). No probe that can end processes beyond its own or show windows (#1027 ended another agent's command and popped windows): ask the user first or use Windows Sandbox (#1056). Start anything detached hidden.
- **Stopping a background run**: stopping the shell (Claude Code's TaskStop) leaves the `run.mjs` runner of `npm run scenarios` or e2e running, writing the same log and baselines. Find it by command line (relative: `run.mjs`, cwd the worktree) and end it, then check `baselines/` for a timestamped duplicate. Settle edits before starting a baseline you may need to stop.
- **A temporary worktree whose `node_modules` is a junction** to another checkout's: remove the junction first (`cmd //c rmdir "<worktree>\node_modules"`, no `/s`), check it's gone, then `git worktree remove --force`; git otherwise deletes through the junction into the real checkout's packages.
- **project.json / sessions**: change them with `workspace.mutateProjectConfig()`/`updateAgent()` and `workspace.mutateSessions()`/`upsertSession()` (in hive.db, #1061), which lock; computing a new value outside the lock and writing it loses concurrent changes (two agents finishing at once).
- **Logging**: wrap the user's own text in a log line (names, paths, card titles, prompts, error text that may quote them) in `userText()` from `logger.ts`, so Help → Copy Diagnostics leaves it out (`redactLog()` in `shared/redact.ts`).
- **Renderer errors**: a throw while rendering is caught by the nearest `ErrorBoundary`; don't rely on it — guard parsing of file content (e.g. `decodeURIComponent` on paths from Markdown) where it happens.
- **hive-mcp.js** and **hive-progress.js** run outside the asar (the CLIs start the first, the `hive-progress` shims on sessions' PATH the second), so they may only require Node built-ins and `out/main/chunks/*` (unpacked in `electron-builder.yml`); code they share with main is split into those chunks. After `npm run dist`, check them with `npm run e2e -- packaged-mcp packaged-progress` (against `dist/win-unpacked/resources/app.asar.unpacked/out/main/`).
- **Monaco 0.57** deep imports drop the `esm/vs/` prefix: `monaco-editor/editor/editor.worker?worker`.
- **CLI logins**: never automate key presses on Claude Code's, Codex's or Copilot's login screens in test sessions; warn the user before any test that may open a browser sign-in.
- Hive must only use the **standalone CLIs** (Claude Code, Codex, the Copilot CLI). Copies bundled in editor extensions are deliberately rejected (SPEC §11).
- **Never type `/effort` into a Claude Code session** (nor `/model`, whose pick also sets effort): besides switching the running session, it saves the level as the user's default for that model in `~/.claude/settings.json` (tested with 2.1.287). Effort and model changes go through Agent Settings and a restart (`--effort`, `--model`).
- **Providers**: never switch on a provider id in shared code or the UI; put the difference in the descriptor (`capabilities`) or the adapter. Hive never edits a CLI's own config files (`~/.claude/settings.json`, `~/.codex/config.toml`, `~/.copilot/`); Codex gets everything through `-c` overrides, Copilot through its command line, environment and a launch plugin.
- **A CLI's text, field names and timeouts are advanced settings** (#367): a pattern for a CLI's screen or messages, a field it sends, or a timeout Hive gives it goes in `ADVANCED_DEFS` (`src/shared/advanced.ts`) and is read with `advanced.pattern()`/`get()` (`src/main/advanced.ts`), never as a literal in an adapter, so a CLI change can be fixed in Settings → Advanced without a release. A CLI-facing one carries samples from a recorded fixture (`tests/fixtures/advanced`, its README says how to record one with test homes), which `tests/advanced.test.ts` checks the default against.
- **Codex hooks** run through PowerShell on Windows: only the exact `curl.exe … --data-binary "@-" "<url>"` form in `hookCommand()` works, and changing a hook's command, timeout or matcher changes its trust hash (`hookHash()`, tested against hashes from Codex in `tests/codex.test.ts`).
- **Testing Codex**: point `CODEX_HOME` at a test home (never the user's `~/.codex`); the maintainer signs in there once (tests/e2e/README.md). Codex's SessionStart only fires with the first prompt.
- **Testing Copilot**: point `COPILOT_HOME` at a test home (never the user's `~/.copilot`; the maintainer's signed-in one is `%LOCALAPPDATA%\hive-test\copilot`) and hide the GitHub CLI (`GH_CONFIG_DIR` an empty folder, `gh` off PATH): with no stored login Copilot signs in with `gh auth token`. Its login is in Windows Credential Manager per account, not in `COPILOT_HOME`: never run `copilot login` or `copilot logout` in a test. `COPILOT_OFFLINE=true` with `COPILOT_PROVIDER_BASE_URL` (a local stand-in model API) runs the real CLI with no sign-in.

## Driving the app for verification

**No shell deletes on computed paths** (`rm -rf "$(…)"`, `Remove-Item -Recurse $dir`): Claude Code can't check what they delete, so it asks (unattended, it denies after two minutes). Use a new folder per run instead: a probe's from `lib.probeDir('<what>')`, a suite's screenshots from `npm run e2e -- <suite> --keep-files` (in the run's new log folder); a folder that must be reused is emptied with `npm run e2e -- --clear-dir <folder>` (tests/e2e/README.md, Housekeeping).

How to build, drive the app with Playwright in a throwaway profile (`lib.hiveEnv()`), look at screenshots and close what you start is the `verify-hive-ui` skill (`.claude/skills` and `.agents/skills`). A 1.0 dev build upgrades a workspace's data one way (SPEC §16.17): never open the main checkout (the workspace the installed Hive runs) with one until the 1.0 baseline is installed (#1288).

Test copies run quiet: an unpackaged build with a test profile (`HIVE_USER_DATA`), however started, or with `HIVE_TEST_QUIET=1` (a packaged one only with it); `HIVE_TEST_QUIET=0` turns it off to look at a test window yourself. A packaged Hive a suite starts (`dist\win-unpacked`, boardupgrade's and upgradelane's 0.9) is kept off screen by `lib.cjs` too, and a test never starts the installed Hive (#1253: tests/e2e/README.md, Windows). Quiet copies open off screen, never take the focus, and raise no Windows notification, taskbar flash or chime, recording them to `HIVE_TEST_NOTIFY_LOG` when it is set. Check what a test copy would have notified with that log; never focus, maximise or `bringToFront()` a test window (stub the focus instead, as `inbox` does).
