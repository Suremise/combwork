# Combwork — notes for agents

Combwork (named Hive before 1.1) is a Windows desktop app (Electron + TypeScript + React) for running coding agents (Claude Code, Codex) across the projects in a workspace. **You are probably running inside Combwork right now**, developing Combwork itself. The repository, its board project and many code names are still `hive` (`HI-` keys, `hive/…` branches, `hiveGuidance.ts`, `hive.db`): name those as they are. History keeps the old name: commits and their `Hive-Card` trailers, and the CHANGELOG's sections before 1.1.0. These notes are for every agent working on this repository, whichever CLI runs it: Codex reads this file, and Claude Code reads it through `CLAUDE.md`. They hold what you'd get wrong here without being told; how-tos needed only for some tasks are in the dev skills (below), and what a check already enforces is a pointer.

- Product decisions: [docs/SPEC.md](docs/SPEC.md) — the source of truth. Update it when a decision changes.
- How the code fits together, and a code map of where each area lives: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
- User-facing docs (bundled into the app's Docs view): [docs/USER_GUIDE.md](docs/USER_GUIDE.md), [docs/AGENT_API.md](docs/AGENT_API.md), [CHANGELOG.md](CHANGELOG.md)

## Project conventions

- Design is settled before code: asked to discuss or plan, don't change code; list the open questions and confirm once answered. Once a build is agreed, go end to end (code, tests, docs), then **ask** before building the installer (`npm run dist`): more changes often come first. An installer the user will run goes in the **main checkout's** `dist`, not a worktree's (`npm run dist` in a worktree copies it there and says so; it notes when the main checkout is at another commit, and never replaces a different build without `--replace`). The user keeps older installers and archive folders in that `dist`: never delete or tidy them.
- **Name cards by key** (`HI-1661`) in commits, comments, docs, code comments and replies, never by the workspace-wide number (HI-1660 is `#1662`: a number quoted finds another card). The `#1149`-style references already in the docs and code are those old numbers: they still find their cards, but write new ones as keys.
- Outside card work (a card you were given, whose tools commit it), **commit only when the user asks** ("commit", "ready merge"…): leave finished work uncommitted and say so. Commits use the no-reply address in the repo's git config (`git config user.email`), never a personal email. Never push unless asked.
- **Never run `prettier --write`** (or Prettier as a check): the repo isn't Prettier-formatted (no config), so it rewrites whole files (80 columns, double quotes, LF) where the code uses long lines and single quotes. Match the surrounding code, and check with `npm run typecheck` and `npm run lint` (oxlint) only. Before running any whole-file tool on a file with uncommitted changes, keep a copy.
- **Line endings** (`.gitattributes`, #149): git stores LF, and the working tree has CRLF on Windows; write a file with one ending throughout. `tests/lineEndings.test.ts` fails on a mixed file or a lone CR. Scripted edits are how files get mixed (Git Bash's `sed -i` strips CRs; a heredoc mangles a script's backslashes): make multi-line edits with your editing tool, and before committing run `git ls-files --eol | grep w/mixed`. To fix a mixed file, delete it and `git checkout -- <file>`.
- User-visible behaviour changes go into SPEC.md and the user guide in the same change, and into an **Unreleased** section atop `CHANGELOG.md` (the next version's notes). Combwork is released on the public repository `Suremise/combwork`; versions follow semver in 0.x. Don't bump the version, create releases or tags unless asked: RELEASING.md's **The user's OK** lists each step that needs it ([RELEASING.md](RELEASING.md), and the `release-combwork` skill).
- Agent-facing tool replies are lean: a change confirms what changed, a listing returns short rows, full detail on request (`src/shared/toolReplies.ts`; `tests/e2e/replysize.cjs` holds each to a size).
- New user-visible features add a tip to `TIP_ENTRIES` in `src/shared/tips.ts`; every user guide heading ends with its id, `<a id="its-slug"></a>` (`tests/tips.test.ts`, `tests/userGuide.test.ts` say what's wrong).
- **Translations** (#767): text the user sees is a message (`msg({ id, defaultMessage, description })`, shown with `tr()` when rendered, never at module scope). Plurals and joins are ICU and `fmt`, never `n === 1 ? '' : 's'` or a sentence glued from pieces; numbers, sizes and dates go through `fmt`, `shared/units.ts` and `shared/dates.ts` (`{n, number}`, never `toLocaleString()`). Agent-facing text (tool replies, guidance, wakes, the Agent API) stays English and is never a window message: it is an agent message (`agentMsg`, said with `say()`, `src/shared/agentText`; `check:repo`'s agent-text guard fails new hard-coded agent text). CLI-facing text stays English. **Every locale, in the same change**: text added or changed is translated into all seven languages in `locales/` before review; no check fails on a missing one, so it's on the builder. How (extract, the guard's lists, check, coverage records, screens): the `translate-ui` skill.
- Fewer merge conflicts: `CHANGELOG.md` merges with `merge=union`, so two new Unreleased entries both stay. Use union for nothing else (it silently keeps both versions of a changed line; for `package-lock.json`, rerun `npm install` after a conflict). After merging main, glance over the CHANGELOG for an entry that appears twice in two wordings.
- Agent guidance has one owner per rule: the session contract in `src/shared/hiveGuidance.ts`, workflows in the bundled skills (`resources/skills`), arguments and side effects in the tool descriptions (`hive-mcp.ts`), and enforcement in the Agent API and the workflow's gates (SPEC §16.11). Don't copy a procedure into a prompt, mode or tool description, and don't restate a gate as a rule. This file holds only this repository's own conventions; where a dev skill has a rule, it points there. After changing guidance, a skill, a mode or a tool description, run only the scenarios that exercise it, before and after (`npm run scenarios -- --only <ids>`, `--save-baseline <name>` first), naming the ids and why on the card; and the model trials when it could alter what agents do and the card asks (`--only`, `--repeat 2`; `tests/scenarios/BASELINE.md`). The full set is for guidance-wide changes (HI-2010, HI-2011, HI-2012) and a publishable RC. After changing a bundled skill or mode, run `npm run bundled-history`.
- Dev skills (verifying the UI, flakes, providers, releases, risky service changes, translations) are in `.claude/skills` and `.agents/skills`, identical (a unit test checks): edit both. Their names never start with `cw-` (or `hive-`, its name before HI-2463): that prefix is Combwork's own copies in `.agents/skills`, which git ignores.
- Personal, machine-specific notes belong in `CLAUDE.local.md` (git-ignored). `CLAUDE.md` only imports this file (`@AGENTS.md`): put shared notes here.

## Commands

```bash
npm install            # after cloning; also run: npx install-electron --no  (Electron downloads its binary lazily)
npm run dev            # dev build with hot reload — runs alongside the installed Combwork (see below)
npm run typecheck      # tsc for main/preload/shared and renderer
npm test               # vitest unit tests (tests/); CI runs them on push/PR
npm run lint           # oxlint, fails on warnings
npm run check:repo     # the repo-wide checks a merge runs: i18n guard, tests that scan every file (under a minute)
npm run e2e            # end-to-end suites (tests/e2e) against the dev build; -- <suites> --build --record (tests/e2e/README.md)
npm run test:clean     # remove what tests left in %LOCALAPPDATA%\hive-test (--dry-run lists only)
npm run scenarios      # agents and Combwork's skills and rules, and what Combwork costs in them (tests/scenarios/README.md)
npm run build          # typecheck + lint + production bundles into out/
npm run dist           # build + NSIS installer → dist/Combwork-Setup-<version>.exe (ask first)
npm run licenses       # regenerate THIRD_PARTY_NOTICES.md (also part of build)
npm run release        # build + upload a DRAFT GitHub release — only when asked (RELEASING.md)
```

Combwork is MIT-licensed. `THIRD_PARTY_NOTICES.md` is generated from what ships: a library newly bundled into the renderer goes in `RENDERER` in `scripts/thirdPartyNotices.mjs` (`tests/licenses.test.ts` fails on a stale file). Only add dependencies with permissive licences (MIT, BSD, ISC, Apache-2.0 and similar) unless the maintainer agrees otherwise. npm 11 blocks install scripts: a new dependency needing one is `npm approve-scripts <pkg>`.

## Developing Combwork from inside Combwork

- `npm run dev` (unpackaged) uses its own profile `%APPDATA%\Combwork-Dev` and Agent API port **47822**, and its title bar says **Combwork Dev**. The installed app uses `%APPDATA%\Combwork` and port 47821. Both can run at once. Before 1.1 (HI-2461) the profiles were `Hive-Dev` and `Hive`: a build uses the old one while the new one isn't there (SPEC §4.3). The installer renames the installed app's; rename `Hive-Dev` to `Combwork-Dev` yourself, with every dev build closed.
- To update an installed copy: `npm run dist`, then quit Combwork, run the installer, reopen and resume the sessions. Leave running the installer to the user.
- Dev and test builds use the Windows app ID `it.surmise.combwork.dev`; never give them the installed app's `it.surmise.combwork`, or Windows shows Electron's icon and name for the real app. (Before 1.1, HI-2460, they were `com.hive.desktop.dev` and `com.hive.desktop`.)
- Never kill Combwork processes by name — the installed app hosting this session is also `Combwork.exe` (an installed 1.0, `Hive.exe`) or `electron.exe`. Target processes by command line (e.g. paths containing `out\main` or a test profile).

## Gotchas

- **ELECTRON_RUN_AS_NODE**: shells started by the Claude Code VS Code extension inherit `ELECTRON_RUN_AS_NODE=1`, which makes `electron.exe` run as plain Node (`app` is undefined). If you see "Cannot read properties of undefined (reading 'setPath')", clear it.
- **PowerShell 5.1 encoding**: `Get-Content`/`Set-Content` read UTF-8 without a BOM as ANSI and corrupt characters like `—` and `·`. Edit files with your editing tools (or Python with `encoding='utf-8'`), never round-trip them through PowerShell text cmdlets.
- **zustand selectors** must not return fresh objects/arrays (`?? []`) — that loops forever (React error #185). Use a stable constant such as `NO_PROJECTS`.
- **`setActivity(view)` toggles** the sidebar when that view is already shown. To just show a view, use `showView(view)`.
- **Shortcuts**: never read `Command.keybinding` directly; use `commandKeybinding(id)`, which applies the user's and the project's overrides.
- **Agents**: a project can have none, and all are equal (no built-in Agent 1, no `'main'` id). Calls that name no agent use `sessions.soleAgent()`; renderer code gets `null` from `focusedAgentId()` when there are none and uses `actions.quickAddAgent()`.
- **Several windows**: each window has its own workspace. `workspace.x(projectPath, …)` finds the right one by path, but path-less calls (`workspace.path`, `skillsDir`, `refresh()`…) need the current work's workspace (IPC and Agent API calls have it); background code uses `workspaceOf(projectPath)` or `inWorkspace(ws, fn)`. Send a window-specific event with `emitTo(win, …)`.
- **Combwork Assistant**: its home `.combwork/assistant` (`assistantHomeIn()`; `.hive/assistant` in a workspace not yet moved, HI-2462) is a session host like a project (one agent, `assistant`) but is never in `workspace.projects`. Session code takes `workspace.assertSessionHost()`, not `assertProject()`; the renderer finds a session's project with `findProject()`. It calls the Agent API with its own per-launch token (`assistantControl.ts`), governed by Settings → Assistant → Control; every change it makes goes through `assistantChange()` in `servers.ts`.
- **Main's thread carries every keystroke**: each pane's typing and every IPC reply go through it, so synchronous work there (`DatabaseSync` steps that can wait or fsync, `spawnSync`/`execSync`, file loops, reading the whole board where a query would do, heavy CPU) is felt as lag. Such work goes to a worker thread; the pattern, and how to measure before and after, are in the `service-changes` skill.
- **Main's file system access is `original-fs`** (`original-fs/promises`), never `fs`: Electron's `fs` holds an `.asar` it stats until Combwork quits (#246). Lint enforces it in `src/main`; a dependency doing file work in projects (it gets Electron's `fs`) mustn't stat their files.
- **Kept files** (`config.json`, `workspace.json`, `project.json`): `readKeptJson()` and `writeKeptJson()`, never `readJson`/`writeJsonAtomic`. **project.json and sessions** change through `workspace.mutateProjectConfig()`/`updateAgent()` and `mutateSessions()`/`upsertSession()`, which lock: a value computed outside the lock loses concurrent changes.
- **Deleting what the user can see** goes to the Recycle Bin through `trash()` (`src/main/trash.ts`), never `shell.trashItem` (a unit test fails).
- **Logging**: wrap the user's own text in a log line (names, paths, card titles, prompts, error text) in `userText()`, so Help → Copy Diagnostics leaves it out.
- **Renderer errors**: don't rely on the nearest `ErrorBoundary`; guard parsing of file content (e.g. `decodeURIComponent` on paths from Markdown) where it happens.
- **cw-mcp.js** and **cw-progress.js** (built from `src/main/mcp/hive-mcp.ts` and `src/main/progressReporters/hive-progress.ts`) run outside the asar, so they may only require Node built-ins and `out/main/chunks/*`. After `npm run dist`, check them with `npm run e2e -- packaged-mcp packaged-progress`.
- **Monaco 0.57** deep imports drop the `esm/vs/` prefix: `monaco-editor/editor/editor.worker?worker`.
- **Test isolation**: tests never assume they're alone on the machine or inherit their shell: a child's environment comes from the run context's allowlists, never `process.env`; temp folders from `tempDir()` in `%LOCALAPPDATA%\hive-test\tmp`, never `os.tmpdir()`, and every unit, e2e and scenario run's temp files (`TEMP`) in its own `hive-test\tmp\run-*`, gone when it ends (HI-2102); probes and redirected output in a new folder each run (`lib.probeDir()` or your scratchpad), never in or beside a project or worktree, or in a project's `.codex`, `.claude` or `.agents` (#509). The detail, and what a unit test already fails on, is [tests/README.md](tests/README.md)'s Isolation.
- **Tests**: e2e suites live in `tests/e2e` (its README says which start the real Claude Code, and how builder and reviewer split the runs). **Merge checks**, this repository's (#1010): a merge into main or an integration branch (such as `1.0.0`) runs typecheck, lint and `npm run check:repo` (the repo-wide checks, under a minute: the i18n guard and the unit tests that scan every file; a new such test goes in it, `tests/checkRepo.test.ts`), and the cards' own focused e2e suites (those their reviews ran, plus any suite the merge's conflicts touched), with `--build --record`, never the full set or `--affected`. The full unit run (`npm test`) is a release's checks (Tests per card, below), and on request; the full e2e set and the real tier run at checkpoints (tests/e2e/README.md, Which suites to run).
- **Tests per card** (HI-2003, HI-2477): two modes. **While building** is the default, for every card that isn't a release's: lean, so lanes keep moving. **Preparing a release** applies only when a release card or an RC is in hand: thorough. Either way a round tests its change properly and doesn't re-run what it didn't change.
  - **While building, each round, the builder:** typecheck and lint; the unit test files for what changed, plus those the change could break by import (`npx vitest run --changed <base>` follows imports); the e2e suites that cover the change, by name (`--affected` only to pick them: name the picked set on the card); `npm run test:waits`. No full unit run (`npm test`), before the first submit or after.
  - **A fix round:** only the suites that failed, plus those the fix touches. These are the checks the final code needs here.
  - **The reviewer** reads the builder's run record and re-runs only the new or changed tests and what it doubts, saying which on the card. It never asks for a full unit run or other wide re-runs.
  - **The merge queue** is unchanged: the merge checks above.
  - **Flake work:** at most 2 spinner workers and 3 repeats per repro (`--repeat 3`; the `investigate-flake` skill). A flake seen only under a full run's load waits for the release window, unless it blocks merges.
  - **Never on a card unless the card asks:** the full unit run, the full e2e tier (`--all`), the real tier (`--real`), `--repeat` beyond 3, or model trials. Scenarios with the fake provider still run when guidance changes, only those it covers (`--only`, above).
  - **Preparing a release** (RELEASING.md's checks, Steps 1 and 4): the full unit run, the full e2e set, the real tier, and the full scenario set where guidance changed. Everything that fails is fixed or explained before publishing, and flakes found there are fixed then. The integration branch's quiet-time full runs (tests/e2e/README.md, Which suites to run) stay as they are.
- **Tests wait for conditions, never for time** ([tests/README.md](tests/README.md)): poll what you expect to see, never sleep and then check; a timeout bounds a hung run and is never the fix. `npm run test:waits` finds the sleeps a branch adds.
- **Flaky tests**: use the `investigate-flake` skill. Other lanes' flakes don't count against your card: card them.
- **The machine is shared** with other agents' lanes and the user's own Combwork. Never load every core (at most half, in short bursts, said on the card first; #782 reached 95 °C). Added load is two or three CPU spinner workers at most beside a run, never one per core. Test runs share machine-wide slots: two heavy runs, one small run on the side slot, and real-model trials on a cap of their own (HI-2070; tests/e2e/README.md, Heavy runs queue). No probe that can end processes beyond its own or show windows (#1027): ask the user first or use Windows Sandbox (#1056). Start anything detached hidden.
- **Stopping a background run**: stopping the shell (Claude Code's TaskStop) leaves the `run.mjs` runner of `npm run scenarios` or e2e running. Find it by command line (`run.mjs`, cwd the worktree) and end it, then check `baselines/` for a timestamped duplicate.
- **A temporary worktree you made whose `node_modules` is a junction** to another checkout's: remove the junction first (`cmd //c rmdir "<worktree>\node_modules"`, no `/s`), check it's gone, then `git worktree remove --force`; git otherwise deletes through the junction into the real checkout's packages.
- **CLI logins**: never automate key presses on Claude Code's, Codex's or Copilot's login screens in test sessions; warn the user before any test that may open a browser sign-in.
- Combwork must only use the **standalone CLIs** (Claude Code, Codex, the Copilot CLI). Copies bundled in editor extensions are deliberately rejected (SPEC §11).
- **Never type `/effort` into a Claude Code session** (nor `/model`, whose pick also sets effort): it saves the level as the user's default for that model in `~/.claude/settings.json` (tested with 2.1.287). Effort and model changes go through Agent Settings and a restart.
- **Providers**: never switch on a provider id in shared code or the UI; put the difference in the descriptor (`capabilities`) or the adapter (the `add-or-change-provider` skill). Combwork never edits a CLI's own config files (`~/.claude/settings.json`, `~/.codex/config.toml`, `~/.copilot/`).
- **A CLI's text, field names and timeouts are advanced settings** (#367): in `ADVANCED_DEFS` (`src/shared/advanced.ts`), read with `advanced.pattern()`/`get()`, never a literal in an adapter, so a CLI change can be fixed without a release; a CLI-facing one carries samples from a recorded fixture (`tests/fixtures/advanced`).
- **Codex hooks** run through PowerShell on Windows: only the exact `curl.exe … --data-binary "@-" "<url>"` form in `hookCommand()` works, and changing a hook's command, timeout or matcher changes its trust hash (`hookHash()`).
- **Testing Codex and Copilot**: only in test homes (`CODEX_HOME`, `COPILOT_HOME`), never the user's `~/.codex` or `~/.copilot` (tests/e2e/README.md). Never run `copilot login` or `copilot logout` in a test: its login is in Windows Credential Manager per account. Codex's SessionStart only fires with the first prompt.

## Driving the app for verification

How to build, drive the app with Playwright in a throwaway profile, look at screenshots and close what you start is the `verify-combwork-ui` skill. A 1.0 dev build upgrades a workspace's data one way (SPEC §16.17): never open the main checkout (the workspace the installed Hive runs) with one until the 1.0 baseline is installed (#1288).

**No shell deletes on computed paths** (`rm -rf "$(…)"`, `Remove-Item -Recurse $dir`): Claude Code can't check what they delete, so it asks (unattended, it denies after two minutes). Use a new folder per run instead; a folder that must be reused is emptied with `npm run e2e -- --clear-dir <folder>`.

Test copies run quiet (off screen, never taking the focus, no notification, flash or chime) and never start the installed Combwork (#1253). Never focus, maximise or `bringToFront()` a test window: stub the focus, as `inbox` does.
